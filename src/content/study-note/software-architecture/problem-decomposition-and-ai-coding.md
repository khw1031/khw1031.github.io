> 한 줄: 좋은 분할의 기준은 크기가 아니라 **"소비자가 작은 계약만 알면 되는가"와 "이 단위 하나만 따로 검증할 수 있는가"**이며, AI 코딩에서 이 분할은 성능을 높이는 기법이 아니라 **오류의 발생 범위와 검증 비용을 제한하는 운영 방식**이다.

## 큰 그림

```text
주문 기능
├── 가격 계산: 장바구니와 할인 정책 → 최종 금액
├── 주문 저장: 주문 객체 → 저장 결과
├── 결제 실행: 결제 요청 → 승인 또는 실패
└── 화면 표시: 주문 결과 → 사용자에게 보여 줄 정보
```

각 단위의 입력·출력과 책임이 명확하면 할인 정책이 바뀔 때 가격 계산만 고치면 되고, 결제 업체를
바꿔도 화면이나 할인 규칙은 결제 업체의 응답 형식을 몰라도 된다.

## 핵심

유지보수의 어려움은 보통 코드의 **양**보다 **한 부분을 바꿨을 때 어디까지 함께 바뀌는지 알기 어렵다는
데서** 생긴다. 전선 뭉치가 벽 안에서 서로 엉켜 있으면 콘센트 하나를 고치려고 벽 전체를 뜯어야 한다.
단자함으로 구간을 나눠 두면 고칠 구간만 열면 된다. 독립된 단위는 이 변경 범위를 경계 안에 가둔다.

그래서 분할은 네 가지를 가능하게 한다.

1. **변경 전파 제한** — 한 구현의 변경이 무관한 코드까지 번지지 않는다.
2. **국소적 이해** — 전체 시스템을 머리에 올리지 않고도 한 부분을 고칠 수 있다.
3. **독립적 검증** — 작은 입력과 기대 출력으로 테스트할 수 있다.
4. **부분 교체와 복구** — 실패한 단위만 교체하거나 이전 상태로 되돌릴 수 있다.

## 깊이

**바이브 코딩에서 더 중요한 이유 — 추측의 폭발(필수).** LLM은 명세를 엄밀하게 실행하는 컴파일러가
아니라, 주어진 맥락에서 빈칸을 **확률적으로 메우는 생성기**다. "주문 기능 전체를 만들어 줘"처럼 범위가
크면 AI는 데이터 구조, 오류 처리, 상태 관리, 외부 API 형식까지 많은 결정을 동시에 추측한다. 이
추측들은 서로 의존하므로 **초반의 작은 오해가 뒤 코드의 전제가 된다.**

반대로 한 번에 하나의 독립된 문제와 판정 기준을 주면 작업의 모양이 이렇게 바뀐다.

```text
요청:      할인 정책에 따라 최종 금액을 계산한다
계약:      Cart와 DiscountPolicy를 받고 Money를 반환한다
판정:      정상 할인, 중복 할인, 최소 금액 경계 테스트를 통과한다
수정 범위: 가격 계산 모듈과 해당 테스트
```

이 범위에서는 AI가 추측할 것이 적고, 사람도 결과 전체를 검토할 수 있다. 실패해도 원인을 해당 단위에서
찾을 수 있고, 잘못 생성된 변경만 버리기도 쉽다. 즉 작은 독립 문제는 **AI의 성능을 마법처럼 높이는
기법이 아니라, AI가 틀릴 수 있다는 전제 아래 오류의 발생 범위와 검증 비용을 제한하는 운영 방식**이다.

여기서 **계약**과 **판정**을 함께 주는 것이 핵심이다. 범위만 좁히고 판정 기준을 주지 않으면 "작지만
맞는지 알 수 없는 결과"가 나오고, 검증 비용이 다시 사람에게 전가된다.

**작게 나누는 것만으로는 부족하다(필수).** 함수를 많이 만들었다고 독립성이 생기지 않는다. 다음은
**이름만 나뉜** 상태다.

- 여러 함수가 같은 **전역 상태를 몰래 바꾼다** — 호출 순서가 숨은 계약이 되어, 한 함수만 보고는
  옳은지 판단할 수 없다
- 한 변경에 **여러 파일을 항상 함께 고쳐야 한다** — 경계가 실제 변경 단위와 어긋나 있다는 증거다

반대 방향의 실패도 있다. **지나치게 잘게 나누면** 파일 탐색과 연결부가 늘어 이해가 더 어려워진다.
분할 자체가 목적이 되면 경계마다 붙는 매핑·주입·테스트 준비 비용이 이득을 넘어선다.

**판정 기준은 크기가 아니라 두 질문이다(필수).**

> 이 단위의 내부 구현이 바뀌어도 소비자는 작은 계약만 알면 되는가?
> 그리고 이 단위 하나만 따로 검증할 수 있는가?

둘 다 그렇다면 유지보수와 바이브 코딩에 유효한 분할에 가깝다. 두 질문은 서로를 보완한다 — 첫 질문은
**결합**을, 두 번째 질문은 **관찰 가능성**을 본다. 계약은 작은데 혼자 검증할 수 없다면 숨은 의존이
남아 있다는 뜻이고, 혼자 검증되는데 소비자가 내부를 알아야 한다면 계약이 새고 있다는 뜻이다.

**진단 순서(전문가).** 분할이 잘 됐는지 의심될 때는 코드 모양보다 이력을 본다. 최근 커밋들에서 **함께
바뀐 파일 묶음**이 선언한 경계와 일치하는지 보면, 이름만 나뉜 경계가 드러난다. 함께 바뀌는 것들이
서로 다른 모듈에 흩어져 있다면 경계를 그은 축이 틀렸다.

## 용어 풀이

- **결합(coupling)** — 한쪽의 변경이 다른 쪽의 변경을 강제하는 정도. 깨짐: 호출 횟수나 import 개수로
  측정하려 하면 숨은 전역 상태 결합을 놓친다.
- **계약(contract)** — 소비자가 알아야 하는 입력·출력·오류의 약속. 깨짐: 내부 자료구조를 그대로
  노출하면 계약이 아니라 구현 공개가 된다.
- **변경 전파(change propagation)** — 한 변경이 함께 수정해야 하는 코드로 번지는 것. 깨짐: 컴파일
  오류만 세면 런타임에서만 드러나는 전파를 못 본다.
- **국소적 이해(local reasoning)** — 전체를 머리에 올리지 않고 한 부분만 보고 옳은지 판단할 수 있는
  성질. 깨짐: 숨은 호출 순서 요구가 있으면 성립하지 않는다.
- **과분할(over-decomposition)** — 이득 없이 경계 수만 늘린 분할. 깨짐: "작을수록 좋다"를 규칙으로
  삼는 것.
- **바이브 코딩(vibe coding)** — 자연어 지시로 AI에게 코드를 생성시키며 진행하는 방식. 깨짐: 판정
  기준 없이 범위만 좁히면 검증 비용이 사람에게 그대로 남는다.
