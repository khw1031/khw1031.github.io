### Modular monolith의 서비스 경계와 배포 단위 분리

**핵심:** 서비스는 처음부터 별도 서버로 배포해야 하는 단위가 아니라, 특정 제품 업무의 변경과 책임을 소유하는 경계로 볼 수 있다. Modular monolith는 이 경계를 한 애플리케이션 안에 모듈로 유지하고, 운영상 근거가 생겼을 때만 독립 배포를 검토하는 구조다.

#### 배경

디자인 생성과 재무 계산을 같은 `apps/api` 프로세스에서 실행하면서도, 서로의 내부 구현을 직접 참조하지 않도록 구성했다.

#### 세부 내용

```text
하나의 실행·배포 단위

apps/api
├─ 디자인 생성 모듈
├─ 재무 계산 모듈
├─ 인증·권한 모듈
└─ 앱 셸
```

각 모듈은 자신의 업무 규칙과 공개 계약을 소유한다. 예를 들어 디자인 생성 모듈은 재무 계산의 내부 함수를 직접 호출하지 않고, 재무 계산 모듈도 디자인 생성의 adapter를 직접 사용하지 않는다.

Microservices와 달리 modular monolith는 함께 실행·배포되고 같은 프로세스 안에서 호출할 수 있어 운영 복잡도가 낮다. 다만 내부 경계는 유지한다. 서비스가 커지거나 운영 요구가 달라졌을 때, 이미 있는 경계를 바탕으로 독립 배포를 검토할 수 있다.

### FSD와 프론트엔드 modular monolith의 역할 구분

**핵심:** FSD는 프론트엔드 내부 코드를 기능과 레이어 기준으로 나누는 방법론이며, frontend modular monolith는 하나의 웹 앱 안에서 제품 기능의 경계를 유지하는 구조다. FSD는 그 구조를 구현하는 데 잘 맞지만, 백엔드 서비스 경계나 독립 배포를 자동으로 만들지는 않는다.

#### 세부 내용

```text
apps/web — 한 번에 빌드·배포되는 SPA

├─ app                         : 앱 시작, 라우팅, 전역 Provider
├─ features/design-generation  : 디자인 생성 UI·상태·API 호출
├─ features/finance-calculation: 재무 계산 UI·상태·API 호출
├─ auth                        : 로그인·권한 UI
└─ shared                      : 특정 제품 기능에 속하지 않는 재사용 요소
```

이 구조에서 각 기능은 자기 화면·상태·API 호출 규칙을 소유하고, 다른 기능의 내부 상태를 직접 변경하지 않는다. `app` 셸은 메뉴·라우팅·인증 상태를 조립한다.

Micro-frontend는 기능별 프론트엔드를 별도로 빌드·배포하고 런타임에 조합하는 방식이다. 반면 frontend modular monolith는 한 웹 앱으로 함께 빌드·배포하면서 내부 경계만 모듈화한다.
