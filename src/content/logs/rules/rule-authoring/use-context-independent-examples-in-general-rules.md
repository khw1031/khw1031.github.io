**규칙:** 장기적으로 일반화해 보존할 규칙의 예시는 사라질 수 있는 실제 대상에 의존하지 말고 맥락에 독립적인 사례로 구성하라.

## 왜

규칙보다 수명이 짧은 파일, 도구, 프로젝트, 사건을 본문 예시로 고정하면 그 대상이 사라지거나 바뀐 뒤 예시의 의미를 이해하기 어려워진다. 실제 사례의 우연한 세부 사항이 규칙의 적용 범위로 오해될 수도 있다. 규칙이 보존하려는 판단 구조만 남긴 구성 사례는 원래 맥락이 없어져도 예시와 비예시의 차이를 유지한다.

## 예시

- (구성한 예) “목록 노출 판정과 목록 생성은 같은 분류 함수를 사용한다”는 사례로 공유 로직의 필요성을 설명한다. 특정 저장소의 함수명이나 파일 경로는 적지 않는다.
- (구성한 예) “필수 필드가 빠진 문서는 검사기가 종료 코드 1을 반환한다”는 사례로 차단형 lint를 설명한다. 현재 사용 중인 검사기 이름에 의존하지 않는다.
- (구성한 예) 실제 사건에서 규칙을 얻었더라도 본문에는 “정상 입력과 필드 하나만 빠진 입력을 비교한다”처럼 판단에 필요한 최소 차이만 남기고, 사건의 위치와 시점은 출처 줄에 기록한다.

## 비예시

- (구성한 예) “현재 저장소의 특정 검사 파일이 이 규칙의 모범 사례다”라고 적는다. 파일이 이동하거나 삭제되면 예시가 가리키는 행동도 함께 사라진다.
- (구성한 예) 특정 프로젝트에서 한 번 발생한 파일명과 오류 메시지를 규칙의 적용 조건처럼 나열한다. 독자가 우연한 세부 사항과 일반 조건을 구분해야 한다.
- (구성한 예) 실제 사례를 제거하면서 예시 자체도 생략한다. 구체 대상에 대한 의존은 없어졌지만 규칙을 어떻게 적용하는지 판별할 근거도 사라진다.

## 적용 범위·예외

미래의 여러 맥락에 반복 적용할 규칙 로그에 적용한다. 실제 사건의 추적 가능성은 본문 예시가 아니라 맨 아래 출처 줄로 보존한다. 감사 기록, 장애 분석, 실험 보고서처럼 특정 사건 자체가 문서의 대상인 기록은 일반화된 규칙 로그가 아니므로 실제 명칭과 증거를 유지한다.

## 확인 방법

1. 예시에 적힌 파일명, 경로, 프로젝트명, 도구명, 버전을 가린다.
2. 가린 뒤에도 규칙을 따른 행동과 어긴 행동의 차이를 판별할 수 있는지 확인한다.
3. 판별할 수 없다면 대상의 고유명 대신 입력, 행동, 결과의 구조로 사례를 다시 구성한다.
4. 실제 사건의 provenance가 필요하면 본문이 아니라 출처 줄에 남긴다.
