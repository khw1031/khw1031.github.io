## 조사 배경

이전에 정리한 [Codex·Claude Code 적응형 모델 오케스트레이션 구조](/inbox/2026-08-26-codex-claude-code-적응형-모델-오케스트레이션-구조/)에서 남겨둔 과제 — "역할별 능력 등급을 실제 모델에 대응시키는 근거"와 "라우팅 판정을 어떻게 신뢰성 있게 만들 것인가" — 를 세 가지 질문으로 좁혀 자료를 모았다.

1. 작업 유형 → 모델 티어 매핑에 실무 기준이 있는가?
2. 오케스트레이터가 라우팅을 "정확하게" 하는 방법이 연구로 뒷받침되는가?
3. "명확한 스펙 + 평가기준이 주어지면 소형 모델로 충분하다"는 주장에 근거가 있는가?

## 1. 작업 → 모델 매핑 가이드

실무 문서 기준으로 정리되는 패턴은 다음과 같다.

| 작업 유형 | 권장 티어 |
| --- | --- |
| 아키텍처 결정, 대형 리팩터, 뉘앙스 있는 요구사항 | 프리미엄(Sol/Opus/Gemini Pro급) |
| 일상적 구현, 컴포넌트 작업 | 미드티어가 속도·비용·품질 균형 최적 |
| 단순 반복, 스크립트, 검색/요약 | 소형 모델로 충분 |

- [Kilo Code의 모델 선택 가이드](https://kilo.ai/docs/code-with-ai/agents/model-selection)는 "복잡한 코딩은 프리미엄, 일상 코딩은 미드티어"를 기본으로 하고, 서브에이전트별로 모델을 다르게 오버라이드하는 패턴(예: explore 서브에이전트는 Haiku)을 권장한다: "For complex coding tasks: Premium models typically handle nuanced requirements, large refactors, and architectural decisions better. For everyday coding: Mid-tier models often provide the best balance." 작은 프로젝트는 32-64K, 대형 코드베이스는 256K+ 컨텍스트 등 컨텍스트 크기 기준도 함께 제시한다.
- [작업 난이도 기반 선택 프레임워크](https://collinwilkins.com/articles/ai-model-selection)는 어떤 벤치마크가 어떤 능력을 측정하는지 매핑한다: "SWE-bench tests coding, MMLU covers knowledge breadth... The 'best' model depends entirely on what you're asking it to do."

## 2. 오케스트레이터가 라우팅을 "정확하게" 하는 방법

LLM Routing이라는 이름으로 활발히 연구되는 분야이며, 핵심 결론은 **미리 정해둔 규칙보다 학습된 라우터가 낫다**는 것이다.

### 주요 접근법

1. **분류기 기반 — RouteLLM (ICLR 2025)**: Chatbot Arena의 인간 선호 데이터로 "이 쿼리에서 강한 모델이 이길 확률"을 예측하고, 임계값 α로 비용-품질 트레이드오프를 조절한다. "The threshold α controls the trade-off between quality and cost... our router models significantly reduce costs—by over 2x—without substantially compromising quality." ([arXiv:2406.18665](http://arxiv.org/html/2406.18665v4)) MT-Bench에서는 GPT-4 성능의 95%를 유지하며 85% 비용 절감, 강한 모델로 보낸 쿼리는 14%뿐이었다. ([NeuralTrust 정리](https://neuraltrust.ai/blog/llm-model-routing))
2. **캐스케이드 — FrugalGPT**: 싼 모델부터 시도해 신뢰도가 충분하면 통과, 아니면 다음 모델로 넘긴다. 최대 98% 비용 절감. "The cascade tries cheaper models in sequence, stops when one produces a confident-enough answer." ([NeuralTrust](https://neuraltrust.ai/blog/llm-model-routing))
3. **난이도 예측 — Hybrid LLM**: 쿼리 난이도를 예측해 라우팅하며, 쿼리의 22%만 소형 모델로 보내도 품질 저하 1% 미만. "our router assigns 22% of queries to Llama-2 (13b) with less than 1% drop in response quality." ([ICLR 2024 논문](https://proceedings.iclr.cc/paper_files/paper/2024/file/b47d93c99fa22ac0b377578af0a1f63a-Paper-Conference.pdf))
4. **멀티암 밴딧 — Meta-LLM**: 사용할수록 보상을 학습하는 적응형 라우팅. 가장 비싼 모델과 동등한 정확도(91.0 vs 90.9)를 1/16 비용으로 달성. "MAB model achieved comparable accuracy to the most expensive and high-performing LLM, while incurring significantly lower costs (0.3 versus 4.8 $ per 10,000 queries)." ([arXiv:2502.00409](https://arxiv.org/html/2502.00409v2))
5. **비용+성능 동시 예측 — CARROT**: 각 쿼리에 대해 후보 모델별 비용과 정확도를 예측해 선택하는 단순한 라우터가 미니맥스 최적이라는 이론적 결과. "a simple router that predicts both cost and accuracy for each question can be minimax optimal." ([arXiv:2502.03261](https://arxiv.org/html/2502.03261v2))

### 오케스트레이터 설계에 적용할 핵심

라우터 자체는 매우 가볍게 만들 수 있다 — RouteLLM의 행렬분해 라우터는 파라미터 46만 개, 라우팅 오버헤드는 무시 가능한 수준이다. "the MF router itself is extremely lightweight, with only ~4.6×10⁵ trainable parameters." ([arXiv:2601.07206](https://arxiv.org/html/2601.07206v1))

실전 구현 경로로는 ① 과거 작업 로그로 "어떤 작업이 어떤 모델에서 통과했는가" 데이터를 쌓고, ② 캐스케이드(소형 먼저 → 테스트 실패 시 상향)로 시작하는 것이 가장 안전하다.

## 3. "명확한 스펙 + 평가기준 → 소형 모델로 충분" 주장의 근거

이 주장은 상당한 지지를 받는다.

1. **AlphaCodium (2024, CodiumAI)** — 가장 직접적인 근거. 테스트 기반 다단계 플로우(스펙 반영 + 자동 테스트 생성 + 반복 수정)를 적용하자 소형 모델 DeepSeek-33B가 pass@5 7%→20%(약 3배)로, GPT-4도 19%→44%로 급등했다. ([arXiv:2401.08500](https://ar5iv.labs.arxiv.org/html/2401.08500)) 저자들은 "구조화된 출력이 단순 프롬프트 엔지니어링의 필요를 거의 없앤다"고까지 말한다. ([GitHub](https://github.com/codium-ai/alphacodium)) 즉 구조화된 플로우가 모델 스케일 차이를 상쇄한다.
2. **Agentless (2024)** — 고정된 정적 파이프라인(지역화→수정→검증)이 자유로운 에이전트 프레임워크를 능가했다. SWE-bench Lite에서 오픈소스 최고 성능(32%)을 문제당 $0.70에 달성했고, "Agentless has also been adopted by OpenAI as the default approach when showcasing the real-world coding performance of GPT-4o/o1." ([arXiv:2407.01489](https://arxiv.org/html/2407.01489v2)) 모델의 자유도보다 워크플로우의 구조가 성능을 결정한다는 증거다.
3. **모호성 연구 — Orchid (2026)** — 역방향 증거. 요구사항이 모호하면 모든 모델이 하락하는데, 특히 고성능 모델일수록 타격이 커서 GPT-4는 28~31%p 하락한다. "GPT-4 achieves top-tier baseline performance, its accuracy drops by more than 28 percentage points... under ambiguous requirements." ([arXiv:2604.21505](https://arxiv.org/abs/2604.21505)) 이는 스펙이 명확해지면 대형 모델의 우위가 줄어든다는 것을 시사한다. ICSE 2026 연구도 모순된 명세에서는 GPT-4가 73.8%→6.7%로 붕괴함을 보여, 큰 모델이 "모호함에 강한" 정도이지 면역은 아님을 확인했다. ([ICSE 2026 논문](https://homepages.dcc.ufmg.br/~figueiredo/disciplinas/papers/icse2026larbi.pdf))
4. **스펙 이론 (2024)** — "명세가 덜 모호할수록 정답 출력 확률이 높아지고, 검증 명세가 명확할수록 출력 검증이 쉬워진다"를 체계화한 논문. "The less ambiguous the statement specification, the more likely the LLM is to generate the correct output. Similarly, the less ambiguous the solution specification, the easier it becomes to verify the LLM's output." ([arXiv:2412.05299](https://arxiv.org/html/2412.05299v2)) 이 주장의 이론적 뼈대로 쓸 수 있다.
5. **소형 모델 + 구조화 가이드 (2025)** — 구조화된 "청사진" 제공으로 소형 모델(GPT4o-mini, Phi3-mini 등)이 GSM8K/MBPP/BBH 전반에서 향상됐다. "our framework demonstrates improved SLM performance across various tasks, including math (GSM8K), coding (MBPP), and logic reasoning (BBH)." ([arXiv:2506.08669](https://arxiv.org/html/2506.08669v1)) 단, 프롬프트 템플릿에 민감해 태스크별 최적화가 필요하다는 조건이 함께 붙는다. TDD 스타일로 테스트를 명세와 함께 주면 코드 생성 결과가 향상된다는 실증 연구도 있다. ([ACM 논문](https://dl.acm.org/doi/10.1145/3691620.3695527))

### 정직한 한계

- "소형 모델로 충분"은 **검증 가능한 작업**(테스트 통과 여부로 판정되는)에서 성립한다. 모호성 연구들은 대형 모델이 모호한 상황에서도 여전히 더 강함을 보였으므로, 스펙을 명확히 만드는 능력 자체(요구사항 정리, 아키텍처 판단)는 상위 모델 영역으로 남는다. "Larger models exhibit better robustness, but remain vulnerable to ambiguity and contradiction." ([ICSE 2026](https://homepages.dcc.ufmg.br/~figueiredo/disciplinas/papers/icse2026larbi.pdf))
- AlphaCodium 방식은 솔루션당 15~20회 LLM 호출을 소모한다. 호출당 비용이 싸도 총 토큰은 늘어날 수 있다. ([arXiv:2401.08500](https://ar5iv.labs.arxiv.org/html/2401.08500))
- 평가기준(루브릭) 자체의 품질이 결과를 좌우한다. 루브릭이 모호하면 LLM 심판의 신뢰도가 떨어지므로, 기준 문서화가 전제 조건이다. ([루브릭 기반 평가 정리](https://medium.com/%40adnanmasood/rubric-based-evals-llm-as-a-judge-methodologies-and-empirical-validation-in-domain-context-71936b989e80))

## 종합

세 질문 모두 유의미한 근거가 확보됐으며, 특히 3번 주장은 AlphaCodium·Agentless라는 구체적 벤치마크 결과로 뒷받침된다. 실전 아키텍처로 수렴하는 형태는 다음과 같다.

```text
상위 모델(오케스트레이터)
  → 스펙 작성 · 작업 분해 · 평가기준 수립을 담당

소형/미드 모델(실행자)
  → 명세 + 통과 테스트가 주어진 상태에서 실행
  → 실패 시 캐스케이드로 상위 모델에 재위임

라우팅 판단
  → 규칙이 아니라 과거 통과/실패 로그로 학습된 가벼운 분류기
    (FrugalGPT/RouteLLM 스타일)에 맡긴다
```

이는 앞서 정리한 [적응형 모델 오케스트레이션 구조](/inbox/2026-08-26-codex-claude-code-적응형-모델-오케스트레이션-구조/)의 "능력 등급 → 실제 모델 ID" 매핑과 "역할별 모델 정책" 부분을 구체화할 근거로 쓸 수 있다 — 특히 능력 등급 배정을 사람이 직관으로 정하는 대신, 실행 로그를 쌓아 학습된 라우터로 대체하는 다음 단계가 이 조사로 뒷받침된다.

## 확인 질문

- Q1: RouteLLM·Hybrid LLM류 라우터를 코딩 에이전트 맥락(대화형 챗봇이 아니라 멀티스텝 도구 사용)에 그대로 옮겼을 때도 같은 비율의 비용 절감이 재현되는가?
- Q2: 캐스케이드 방식에서 "신뢰도 충분"을 코딩 작업에 대해 무엇으로 판정할 것인가 — 테스트 통과 여부 외에 정적 분석·타입 체크 같은 보조 신호를 쓸 수 있는가?
- Q3: 스펙 명확도를 정량화하는 방법(모호성 점수)이 있다면, 이를 라우팅 임계값 α와 결합해 "이 작업은 스펙이 충분히 명확하니 소형 모델로 캐스케이드 시작"을 자동 판정할 수 있는가?
