## 배경

[LLM 라우팅: 작업 난이도 기반 모델 티어 선택의 연구 근거](/inbox/2026-08-26-llm-라우팅-작업-난이도-기반-모델-티어-선택-근거-조사/)에서 다룬 논문은 대부분 2024~25년 초 자료였다. 이번 조사는 2025 하반기~2026년 8월(오늘 arXiv 신규 등록분 포함) 최신 연구로 같은 세 질문 — 라우팅 방법론, 소형 모델 대체 가능성, 실무 적용 — 을 갱신한다.

## 1. 라우팅 연구: "쿼리"에서 "역할(role)" 단위로 진화

- **MasRouter (ACL 2025)** — 최신 라우팅 연구의 기준점. "라우팅은 작업의 도메인과 난이도뿐 아니라 에이전트의 역할에 따라 달라진다"고 정식화하며, "가장 큰 모델이 항상 이긴다"는 가정을 반박한다: "model routing depends on the task's domain and difficulty, as well as their corresponding role." ([Augment Code 가이드](https://www.augmentcode.com/guides/ai-model-routing-guide)) 핵심 통찰은 같은 세션 안에서도 역할별로 다른 모델을 배정하는 게 최적이라는 것이다.
- **UniRoute (Google, 2025)** — 테스트 시점에 새로 등장한 모델까지 포함해 30개 이상의 "본 적 없는" LLM 사이에서 라우팅하는 동적 라우팅을 제안한다: "we consider the problem of dynamic routing, where new, previously unobserved LLMs are available at test time." ([arXiv:2502.08773](https://arxiv.org/abs/2502.08773)) 새 모델이 매달 나오는 상황에서 재학습 없이 라우터를 갱신하는 문제를 다룬다.
- **Adaptive LLM Routing under Budget Constraints (2025)** — 라우팅을 컨텍스트 밴딧 문제로 정식화해, 라벨 없이 사용 피드백만으로 적응하는 라우터를 제시한다: "We propose to study LLM routing as a contextual bandit problem, enabling adaptive decision-making using bandit feedback." ([arXiv:2508.21141](https://arxiv.org/abs/2508.21141)) 오케스트레이터가 과거 로그만으로 학습하는 구조와 정확히 일치한다.
- **LLMRouterBench (2026년 1월)** — 라우터 자체를 대규모 비교하는 통일 벤치마크. RouteLLM/FrugalGPT 등 기존 라우터의 약점(안정성, 실제 배치 상황 대응)을 정량화한다.
- **AgentArch (2025년 9월)** — 18개 에이전트 아키텍처 × 여러 모델을 교차 실험. 아키텍처와 모델의 상호작용이 성능을 좌우하며, 최신 모델 중 일부만 복잡한 오케스트레이션 과제에서 유의미한 성능을 냈다: "Only three models—GPT-4.1, Sonnet 4, and o3-mini—demonstrated meaningful capability on the complex customer request routing task." ([arXiv:2509.10769](https://arxiv.org/html/2509.10769v1)) thinking tool이 단순 과제엔 도움되지만 복잡한 과제엔 효과가 거의 없었다는 발견도 있다 — 비싼 "생각"을 어디에 쓸지도 라우팅 대상이라는 근거다.

## 2. "명확한 스펙 + 검증 → 소형 모델" 가설의 최신 근거

이 방향이 2025 하반기~2026년 연구에서 가장 두드러지는 트렌드다.

- **구조화 스펙 기반 엔지니어링 SSDE (2026년 5월)** — 이 가설을 거의 그대로 다룬 논문. Gherkin 같은 검증 가능한 구조화 스펙을 LLM 입력으로 주면 리포지토리급 코드 생성 품질과 검증 가능성이 함께 향상된다: "structured specifications as LLM inputs make high-quality, repository-level code generation a tangible goal, while at the same time offering superior verifiability." ([arXiv:2605.02455](https://arxiv.org/html/2605.02455v1)) 다만 스펙 자동 생성은 아직 어렵고(사람이 스펙을 만드는 비용이 남는 과제), 주어진 스펙에서 코드를 끌어내는 능력은 뛰어나다.
- **도메인 특화 SLM이 프론티어급을 이김 (2026년 5월)** — 법률 도메인 MoE 소형 모델(Olava Extract)이 Claude Opus 4.6, Sonnet 4.6, Gemini 3.1 Pro, GPT-5.4 등 5개 프론티어 모델과 구조화 계약 추출 정확도를 겨뤄 이겼다: "evaluates whether a domain-trained Small Language Model (SLM) can outperform frontier Large Language Models on structured contract extraction." ([arXiv:2605.05532](https://arxiv.org/html/2605.05532v1))
- **소형 모델 + 제약조건 = 28배 저비용 (2026-08-26 arXiv 신규 등록)** — 제약이 주어진 소형 모델이 제약 없는 프론티어 LLM과 동등한 성능을 약 28배 낮은 비용으로 달성한다: "a small model with constraints matches a frontier LLM used without them at ~28x lower cost." ([arXiv cs.AI 신규 목록](https://arxiv.org/list/cs.AI/new)) 이 가설의 가장 최신 직접 근거다.
- **SLM 툴호출 특화 학습 (2026년 3월)** — OPT-350M(3.5억 파라미터)을 구조화된 thought-action-observation 패턴으로만 파인튜닝해 도구 호출 pass rate 77.55%를 달성했다. "Tool calling requires structured reasoning patterns rather than creative language generation" — 창의적 언어 생성이 아니라 구조화된 추론 패턴이기 때문에 소형 전문 모델이 유리하다는 결론이다. ([arXiv:2512.15943](https://arxiv.org/html/2512.15943v2))
- **Agent Lightning / 소형 코딩 에이전트 (2026)** — Qwen3.5-9B에 약 6천 예제만으로 에이전틱 RL을 적용해 SWE-bench Verified를 14.6점 향상시킨 사례가 보고됐다: "a 14.6-point SWE-bench Verified jump for Qwen3.5-9B with only ~6K examples." ([AlphaMatch 블로그](https://www.alphamatch.ai/blog/small-language-models-2026))
- **SLM 서베이 갱신 (2026년 5월, 약 160편 종설)** — 1~9B 모델이 대형 모델과 동등하거나 능가하는 사례들을 체계적으로 정리했다. Orca-2-7B가 LLaMA-2-70B와 비교 가능한 성능, Phi-1(1.3B)이 HumanEval pass@1 50.6%를 기록했다: "this survey of about 160 papers presents a family of Small Language Models... that demonstrate smaller models can perform as well, or even outperform large models." ([arXiv:2501.05465](https://arxiv.org/html/2501.05465v2))

## 3. 산업 실무: "역할별 모델 배정"이 표준으로 자리잡음

- Claude Code가 **서브에이전트별 model/effort 필드**를 정식 지원하면서 "세션당 여러 모델"이 주류가 됐다. 하나의 세션에서 프론티어 모델로 계획하고 저렴한 모델로 실행하는 패턴이다: "Per-subagent model selection went mainstream: Claude Code subagents now take their own model and effort settings." ([MightyBot 블로그](https://mightybot.ai/blog/coding-ai-agents-for-accelerating-engineering-workflows/))
- 실무 라우팅 가이드(2026년 6월)는 역할별 배정을 벤치마크 근거와 함께 제시한다 — 코디네이터는 Opus(MCP Atlas 59~62% vs Sonnet 43.8%), 구현은 Sonnet(SWE-bench 79.6%, Opus와 격차 1.2%p뿐), 파일 탐색·단순 편집은 Haiku: "Sonnet 4.6 at 79.6% closes to within 1.2 points of Opus 4.6, the smallest Sonnet-to-Opus gap in any Claude generation." ([Augment Code 가이드](https://www.augmentcode.com/guides/ai-model-routing-guide)) 구현 단계에서 대형 모델 프리미엄은 1.2%p인데 비용은 수 배라는 뜻이다.
- **OpenAI 공식 reasoning 가이드의 하이브리드 패턴** — 추론 모델이 계획을 세우고 각 단계에 맞는 실행 모델을 선택한다. 다만 오케스트레이션 단계엔 프론티어 모델이 필요하므로 "실행 비용만 절감된다"는 한계도 명시한다: "Hybrid routing requires a frontier model for the planning step, meaning it only saves cost on execution, not orchestration." ([Augment Code 가이드](https://www.augmentcode.com/guides/ai-model-routing-guide))
- **실측 사례** — Claude Code 요청을 GLM 5.2로 라우팅하는 5일 파일럿에서 요청당 비용이 $0.146 → $0.032(약 78% 절감)로 떨어졌다: "GLM 5.2 cut direct Claude Code request cost from $0.146 to $0.032 over five days." ([Faros AI 블로그](https://www.faros.ai/blog/best-ai-coding-agents-2026))

## 종합

최신 연구 흐름은 세 가지로 수렴한다.

1. **라우팅 단위가 "쿼리"에서 "역할"로** — MasRouter 이후 같은 세션 안에서도 계획자·실행자·검토자가 다른 모델을 쓰는 것이 학문적으로도 실무적으로도 정설화됐다.
2. **"제약/스펙이 주어진 소형 모델 ≒ 제약 없는 프론티어 모델"** — SSDE, 도메인 SLM, 오늘자 28배 비용 논문까지, 이전 조사의 가설이 2026년 들어 더 강해지는 추세다.
3. **검증 루프의 경제성** — AgentArch는 "비싼 thinking이 복잡한 과제에만 도움된다"를, Agent Lightning류는 "소형 모델+RL+검증 루프"의 상승 효과를 보였다. "테스트 통과 기준이 명확하면 소형 모델로 돌리고 실패 시 상향"하는 캐스케이드가 이론·실무 모두에서 최적에 가까운 구조로 확인되고 있다.

남은 미해결 영역은 SSDE 논문이 지적한 대로 **스펙 자체를 자동으로 잘 쓰는 것**(요구사항 정리·모호성 해소)이 여전히 상위 모델의 영역이라는 점이다. "오케스트레이터=최상위, 워커=소형+명세+테스트"라는 아키텍처가 2026년 현재 연구와 실무가 모두 가리키는 방향이다.

이는 [적응형 모델 오케스트레이션 구조](/inbox/2026-08-26-codex-claude-code-적응형-모델-오케스트레이션-구조/)와 [1차 라우팅 조사](/inbox/2026-08-26-llm-라우팅-작업-난이도-기반-모델-티어-선택-근거-조사/)의 "능력 등급 → 실제 모델 ID" 매핑에서, 등급 배정 자체를 역할(role) 축으로 세분화하고 소형 모델 배정 기준을 "스펙·제약의 명확도"로 구체화할 근거가 된다.

## 확인 질문

- Q1: MasRouter의 역할 기반 라우팅을 우리 오케스트레이터의 explorer/implementer/reviewer 역할 분류에 그대로 대응시킬 수 있는가, 아니면 역할 정의 자체를 재설계해야 하는가?
- Q2: SSDE가 지적한 "스펙 자동 생성의 어려움"은 사람이 계속 스펙을 써야 한다는 뜻인가, 아니면 상위 모델이 스펙 작성을 전담하면 해소되는 문제인가?
- Q3: UniRoute류의 "미관측 신규 모델 라우팅"을 로컬 환경(Codex/Claude Code + Ollama 혼합)에 적용할 때, 새 모델 출시마다 재학습 없이 라우터를 갱신하는 절차를 어떻게 설계할 것인가?
