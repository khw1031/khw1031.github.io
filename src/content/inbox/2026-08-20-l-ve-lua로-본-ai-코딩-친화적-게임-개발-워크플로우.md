## TL;DR
- GUI Editor가 없는 가벼운 프레임워크(LÖVE+Lua)에서는 AI Agent가 프로젝트 전체를 직접 수정할 수 있어, 2D 게임 개발에서 오히려 생산성이 높다는 개발자 경험담.

## 큰 그림
```
[기존 워크플로우: Unity / Unreal]
  Editor(GUI) ── Scene Hierarchy ── 클릭 설정
       │                              │
       └── AI가 직접 조작 불가 ◄──────┘  ← 병목

[새 워크플로우: LÖVE + Lua]
  코드(.lua) + 에셋(이미지·사운드)
       │
       ├── AI Agent가 전체 파일 직접 수정 가능
       │
  [실제 제작 루프]
  그림판 러프 스케치 → AI에 전달 → "이 느낌으로 그려줘" → 코드 반영
       │
  [결과물 배포]
  데모(demo.a4room.com) → 정식(토스·구글플레이)
```

## 핵심
저자는 Unity·Unreal에서 게임 Editor가 제공하는 Scene Hierarchy, Inspector 클릭 설정 등이 AI Agent에게는 **"손을 댈 수 없는 영역"** 이 된다고 주장한다. LÖVE는 Editor 자체가 없고 모든 것이 코드와 에셋 파일이므로, AI가 프로젝트 구조 전체를 읽고 쓸 수 있다는 것이 핵심 논리다. 이 주장에 따라 저자는 2D는 LÖVE, 3D는 Godot으로 개인 개발 스택을 정리했다.

## 깊이
- **[핵심-가지: Editor 부재의 효과]** 저자는 "타이틀을 제외한 게임 에셋도 전부 코드"라고 명시(주장). 즉 레벨 디자인·파라미터 설정이 별도 씬 파일이 아닌 Lua 코드로 표현되어, AI가 텍스트 수준에서 전체를 파싱·수정할 수 있었다는 설명. Unity의 .scene/.prefab 바이너리·YAML 구조와 대비되는 지점.
- **[핵심-가지: 에셋 제작 루프]** 그림판 러프 스케치 → AI 이미지 생성 → 코드에 반영이라는 3단계 파이프라인. (주장) 별도 그래픽 도구 숙련 없이 "느낌" 수준의 지시로 에셋을 뽑았다는 점.
- **[핵심-가지: 스코프]** 이 후기는 "간단한 2D 게임"에 한정(저자 본인 명시). 복잡한 물리·대규모 씬 관리에는 동일 결론이 적용되지 않을 수 있다.
- 2~15번 포스트는 사용자 댓글에 대한 감사·응답으로, 기술적 내용은 **원문에 없음**.

## 용어 풀이
- **LÖVE(러브)** — Lua 언어로 2D 게임을 만드는 오픈소스 프레임워크. 비유: "레고 블록 없이 점토로 바로 빚는 도구". 단, 점토 비유와 달리 빌드·배포 파이프라인은 개발자가 직접 짜야 한다.
- **Scene Hierarchy** — Unity에서 게임 객체를 트리 구조로 배치·설정하는 GUI 패널. 비유: "파일 탐색기". 그러나 AI 입장에선 GUI이므로 CLI·코드 편집기와 달리 자동화가 어렵다.
- **AI Agent** — 코드를 읽고 쓰고 실행까지 하는 자율 코딩 도구. 여기서는 LÖVE 프로젝트 전체 파일을 직접 수정하는 주체.

## 시각 자료
| 구분 | Unity / Unreal | LÖVE + Lua |
|---|---|---|
| Editor GUI | 있음(필수) | 없음 |
| AI 직접 수정 범위 | 코드 일부 | 프로젝트 전체(주장) |
| 에셋 설정 방식 | Inspector 클릭 | 코드 내 파라미터 |
| 적합 규모(저자 기준) | 대형·3D | 간단한 2D |

## 핵심 시사점 / 판단
- (저자 주장) 간단한 2D 게임에서는 Editor 없는 프레임워크가 AI 코딩에 더 적합하다.
- (저자 주장) 2D→LÖVE, 3D→Godot 스택이 개인 개발 최적 조합.
- (검증 필요·불확실) "AI Agent가 프로젝트 거의 모든 부분을 직접 건드릴 수 있었다"는 표현이 구체적으로 어떤 작업(레벨 디자인, 밸런싱, 버그 수정 등)을 포함하는지 원문에 상세 기술 없음.
- (검증 필요·불확실) 15개 포스트 중 1개만 기술 내용이고 나머지는 감사 응답이므로, 표본 하나로 일반화하기는 이르다.
