## TL;DR
- LLM이 SQL을 직접 작성하는 대신 분석의 **의미 구조**(Dimension·Metric·Filter 등)를 조합하게 하고, 실제 SQL은 코드에서 조립하면 정확도 100%와 유연성을 동시에 얻는다.

## 큰 그림
```
[사용자 질문]
     │
     ▼
┌─────────────────────────┐
│  LLM: 의미 구조 조합     │  ← SQL 작성 ✗
│  (Dimension / Metric /  │
│   Filter / Order / Comp)│
└────────────┬────────────┘
             │  Tool Call 인자 (JSON)
             ▼
┌─────────────────────────┐
│  Tool (Python 등)       │  ← 결정적 코드
│  Fact 테이블 + Semantic │
│  Layer → SQL 조립       │
└────────────┬────────────┘
             │  100% 정확한 Query
             ▼
        [결과 반환]
```
핵심 흐름: **자유 텍스트 → 의미 구조(제한된 조합) → 결정적 SQL**. LLM의 역할이 "코드 작성"에서 "의미 선택"으로 이동.

## 핵심
이용혁 저자는 팀에서 분석 Agent를 설계하며 한 가지 관찰에서 출발한다(저자 주장). 실제 데이터 분석 시나리오는 무한히 자유롭지 않고, **자주 쓰는 패턴이 정해져 있다**는 것이다. 이 전제가 성립하면, LLM에게 Schema를 통째로 주고 SQL을 자유롭게 쓰게 하는 2022년식 접근은 불필요한 자유도를 준다. 대신 가장 세밀한 granularity의 fact 테이블 하나를 깔고, 그 위에서 **Semantic Layer 구조를 조립**하게 하면 오히려 유연성이 살아난다. 사용자가 "최근 7일 특정 광고그룹의 CPA·ROAS"를 물으면, LLM은 SQL 문자열이 아니라 `{days, dimensions, metrics, filters, order_by}` JSON을 만들고, Tool이 이를 받아 Python 등으로 Query를 조립한다. 조립 로직이 결정적(deterministic)이므로 SQL 오류가 원천 차단된다.

## 깊이
- **[핵심-가지: LLM 역할 재배치]** 저자는 "LLM 활용도가 죽는 게 아니다"라고 강조한다. SQL 문법이라는 **구문(syntax) 자유도**를 빼는 대신, **의미(semantic) 조합 자유도**를 준다. 비유하자면, 요리사에게 "레시피를 처음부터 쓰라"는 대신 "재료·조리법·간을 메뉴판에서 고르라"는 격이다. 선택지는 제한되지만 조합은 여전히 풍부하다. 다만 이 비유는 메뉴판에 없는 재료(새로운 분석 축)가 필요할 때 깨진다—원문에는 이 확장 시나리오가 없음.
- **[핵심-가지: Semantic 5요소]** Dimension(기준), Metric(측정), Filter(조건), Order(정렬), Comparison(비교). 이 다섯이 Tool Call 스키마의 전부이며, 저자는 "가장 자세하면서도 필수적인 granularity"의 fact 테이블을 전제로 둔다.
- **[핵심-가지: 데이터 엔지니어 전문성의 복귀]** 저자는 "Human Layer가 돌아온다"고 표현한다. Semantic Layer·데이터레이크 설계 경험이 AI Agent 설계에 다시 핵심이 된다는 주장이다(저자 주장, 원문에 구체적 근거 없음).

## 용어 풀이
- **Semantic Layer** — 데이터 위에 얹는 "의미 번역층". 비유: 외국어 메뉴판을 한국어 설명으로 바꿔주는 라벨지. 라벨지만 보고 고르면 주방(Tool)이 정확히 요리한다. 비유가 깨지는 지점: 라벨지가 부실하거나 누락된 항목이 있으면 선택 자체가 불가능하다.
- **Fact 테이블** — 사건·거래 단위의 가장 세밀한 수치 기록 테이블. 비유: 영수증 원본 뭉치. 요약본이 아닌 원본이라 어떤 각도로든 재집계가 가능하다.
- **Tool Call** — LLM이 자연어 대신 구조화된 JSON 인자를 외부 함수에 넘기는 호출. 여기서는 SQL 조립 함수의 입력.

## 시각 자료
| 접근 방식 | LLM 역할 | 정확도 보장 | 유연성 |
|---|---|---|---|
| Schema → 자유 SQL (2022식) | SQL 작성 | 낮음(할루시네이션) | 높음 |
| **Semantic Layer 조립 (본문)** | **의미 구조 선택** | **높음(결정적 조립)** | **중~높음(조합)** |

## 핵심 시사점 / 판단
- (저자 주장) 분석 패턴이 정해져 있다면 자유 SQL보다 Semantic 조합이 "자율성과 통제의 균형"을 준다.
- (저자 주장) 데이터 엔지니어의 Semantic Layer 전문성이 AI 시대에 재활용된다.
- (검증 필요·불확실) "100% 정확도"는 조립 로직과 fact 테이블 스키마가 고정된 범위 내 성립. 스키마 변경·새 지표 추가 시 동작 여부는 원문에 없음.
- (원문에 없음) 다중 fact 테이블 조인, 보안·권한 필터, LLM의 의미 구조 오판 시 폴백 전략.
