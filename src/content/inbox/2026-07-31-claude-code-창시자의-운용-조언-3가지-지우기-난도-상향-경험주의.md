## TL;DR
- 새 모델이 나올 때마다 축적한 지시(시스템 프롬프트·CLAUDE.md·스킬·훅)를 **전부 지우고, 관측된 반복 실패만 되살리는 것**이 Claude Code 팀의 기본 운용이다. 나머지 두 조언은 "할 일·가드레일·종료 기준 세 가지만 주고 자기 검증 수단을 쥐어 줘라"와 "비법은 없으니 경험주의로 가라"이다.

## 큰 그림
```
[새 모델 출시]
      │
      ▼
[애블레이션] 전부 삭제 ─► 그냥 써 본다 ─► 같은 지점에서 반복 실패 관측 ─► 그것만 복원
      │                                                                      │
      │                        복원 기준 = 관측된 반복 실패 (사전 예측 아님) ◄┘
      ▼
[과제 설계] 할 일 · 넘지 말 선 · 종료 기준  (1→2→3 절차 나열은 하지 않음)
      │
      ▼
[검증 수단 부여] 테스트 스위트 · 픽셀 단위 비교 · 스크린샷
      │
      ▼
[자율 실행] dynamic workflow ─► 에이전트 수백~수천 개 · 11일~2주 연속 실행
```

## 핵심
- 앤트로픽은 Opus 5 출시에 맞춰 Claude Code 시스템 프롬프트의 **80% 이상을 삭제**했다. 이유는 그 지시 대부분이 "모델이 당연히 알았어야 하는데 몰랐던 행동"의 교정이었고, 새 모델은 그것을 그냥 알기 때문이다. 이 삭제-복원 실험을 팀은 **애블레이션(ablation)** 이라 부른다(1차 확인).
- 같은 권고가 사용자에게도 그대로 적용된다. 원문 발화는 "every 6 months delete your Claude MD. Delete your skills. Delete your hooks." — 과거 모델 때문에 필요했던 지시가 지금도 필요한지 6개월마다 의심하라는 뜻이다(1차 확인).
- **복원 기준은 예측이 아니라 관측이다.** 어떤 지시가 필요할지 맞히려 하지 말고, 제품을 실제로 돌려 보고 *같은 지점에서 반복해서 넘어질 때만* 되살린다. 모델은 그 지시를 매 호출마다 읽으므로, 불필요한 지시는 상시로 나가는 비용이다(1차 확인).
- 프롬프트를 전부 지우면 모델이 **오히려 조금 더 똑똑해진다**는 관측이 있다. `CLAUDE_CODE_SIMPLE=1` 환경변수(원문 표현으로 "undocumented feature")를 켜면 도구 프롬프트까지 포함해 시스템 프롬프트가 모두 제거되며, 팀은 이것을 프롬프트 유용성 측정용 애블레이션 장치로 쓴다(1차 확인).
- 가장 흔한 실수는 **과잉 지시**다. "1번 하고 2번 하고 3번 순서대로 해" 대신 세 가지만 말한다 — 할 일(task), 넘으면 안 되는 선(guardrails), 언제 끝난 것인지(exit criteria). 그다음은 모델에게 맡긴다(1차 확인).
- 사람들이 가장 많이 놓치는 것은 **검증(verification)** 이다. 모델이 스스로 결과를 판정할 수단을 쥐고 있으면 막히지 않는다. 그래서 지시의 핵심은 "다시 써라"가 아니라 "비교해라"에 있다(1차 확인).
- 상위 사용자가 되는 비법을 묻자 나온 답은 "비법은 없다"였다. 원문 표현으로는 "don't listen to the LinkedIn influencers", 그리고 이론적 과학이 아니라 **경험적 과학**으로 접근하라는 것 — 써 보고, 어디서 넘어지는지 보고, 그 지점만 보완한다(1차 확인).
- 인터뷰를 관통하는 단어는 **언호블링(unhobbling)** 이다. 진단은 "모델은 이미 할 수 있는데 우리 제품과 습관이 막고 있다"이며, 모델을 자동완성 상자에 가두지 않고 터미널을 통째로 열어 준 Claude Code 자체가 그 사례로 제시된다(1차 확인).

## 깊이
- **[Bun: Zig → Rust 11일 재작성]** Claude Code는 Bun(Node.js 대안 자바스크립트 런타임) 위에서 돌아가고, Bun은 시스템 언어 Zig로 작성되어 메모리를 수동 관리한다. Bun 저자는 세대마다 이 재작성을 모델에게 던지는 시험 문제로 써 왔고, Fable부터 성공하기 시작했다. 성립 조건은 **판정 수단**이었다 — Bun과 Node.js 양쪽의 방대한 테스트 스위트가 "제대로 했는지"를 자동으로 알려 준다. 프롬프트는 하나였고 dynamic workflow로 11일간 실행되어 코드베이스 전체를 재작성했다. **다만 진행자가 "one shot이었나"라고 묻자 보리스는 "one-shot은 아니었고 steering이 있었다"고 정정한다** — 요약 영상은 이 정정을 전달하지 않는다.
- **[Slack 실험 — 2주째 실행 중]** 보리스는 Claude tag 세션에서 ①GitHub의 macOS 러너를 연결해 맥 가상 머신을 띄우게 하고 ②Swift 재작성용 빈 코드베이스 접근 권한을 준 뒤 ③"Electron 앱을 Swift로 다시 써라. 원본을 가상 머신에서 실행해 스크린샷을 찍고 새 버전과 픽셀 단위로 비교해라. 끝날 때까지 멈추지 마라"라고 지시했다. 인터뷰 시점에 2주째 실행 중이며 소환된 에이전트 수는 "수천~수만"으로 추정된다(본인도 정확히 모름). Claude는 지시받지 않은 채 **슬랙 채널을 스스로 만들어 몇 분마다 진행 스크린샷을 올리는 라이브 블로깅**을 했다.
- **[실행 규모의 두 축]** *dynamic workflow* 는 한 과제를 쪼개 수십~수천 에이전트로 오케스트레이션하는 방식으로, Bun 런타임을 샌드박스 삼아 그 안에서 가상 머신을 띄운다. 발동은 "use a workflow"라고 말하는 것이 전부다. *loops / routines* 는 반복 실행 축으로, loop는 로컬에서 도는 cron, routine은 클라우드에서 도는 같은 것이다(노트북을 닫아도 계속 돈다). 앤트로픽 내부에서는 매일 20~30개 루틴이 전 코드베이스를 돌며 죽은 코드 정리, 테스트 커버리지 보강, 쓸모없는 테스트 삭제, 중복 추상화 통합을 수행한다. 마지막 것에는 **"abstraction police"** 라는 이름이 붙어 있다.
- **[eval의 수명]** eval은 하네스보다는 오래 살지만 모델 1~3세대 정도가 한계다. 모델이 빠르게 개선되면서 eval이 포화(saturate)되면 버리고 새로 만드는 것이 정상 과정이다. eval 역시 이론이 아니라 제품을 직접 써 보며 모델이 막히는 지점에서 만들어야 한다.

## 용어 풀이
- **애블레이션(ablation)** — 전부 지운 뒤 한 줄씩 되살리면서 각 줄이 실제로 어떤 영향을 주는지 재는 삭제 실험. 실제 동작: 시스템 프롬프트를 비우고(`CLAUDE_CODE_SIMPLE=1`) 같은 과제를 돌려 결과 차이를 측정한다. 한계: 모델 세대마다 성격이 달라, 지난 세대에서 잰 기여도는 다음 세대에 그대로 옮겨지지 않는다.
- **호블링 / 언호블링(hobbling / unhobbling)** — 모델의 능력을 제품 설계가 가로막고 있는 상태와, 그 족쇄를 푸는 일. 실제 동작: 모델을 자동완성 UI에 가두는 대신 터미널·파일시스템·가상 머신을 통째로 열어 준다. 한계: 족쇄를 푸는 것과 안전장치를 없애는 것은 다르다 — 인터뷰에서도 현재 하네스 코드의 대부분은 안전·권한·정적 분석이라고 말한다.
- **dynamic workflow** — 하나의 과제를 다수 에이전트로 분해·조율하는 Claude Code 기능. 실제 동작: Bun을 샌드박스로 쓰고 그 안에 가상 머신을 띄워 에이전트를 대량 생성한다. 한계: 검증 수단이 없는 과제에서는 규모가 커질수록 틀린 결과가 늘어난다(그래서 테스트 스위트·픽셀 비교가 함께 등장한다).
- **종료 기준(exit criteria)** — 모델이 "끝났다"를 스스로 판정하는 조건. 실제 동작: 테스트 통과, 픽셀 비교 일치처럼 관측 가능한 사건으로 준다. 한계: "잘 만들어라" 같은 주관적 기준은 종료 기준이 되지 못한다.

## 핵심 시사점 / 판단
- **(저자 주장)** 축적한 설정은 자산이 아니라 부채가 될 수 있다. 지시는 매 호출마다 읽히므로, 유효성이 사라진 지시는 계속 지불되는 세금이다.
- **(저자 주장)** 자율 실행의 길이를 결정하는 것은 모델 지능이 아니라 **검증 수단의 유무**다. 11일·2주짜리 사례는 모두 자동 판정 수단(테스트 스위트, 픽셀 비교)이 먼저 있었다.
- **(2차 요약과 1차의 차이)** Bun 재작성에 대해 요약 영상은 "프롬프트는 하나였습니다"에서 멈추지만, 원본에서는 진행자의 확인 질문에 보리스가 "one-shot은 아니었고 steering이 있었다"고 명시적으로 정정한다. 인용할 때 이 단서를 빠뜨리면 안 된다.
- **(검증 필요·불확실)** 요약 영상 설명란은 원본 인터뷰 제목을 "Stop Hobbling Your AI"로 적었으나, 2026-08-06 확인 시점의 실제 제목은 "Boris Cherny: We Cut 80% of Claude Code's Prompt"다. 제목이 바뀐 것인지 표기 오류인지는 확인되지 않았다.
- **(검증 필요·불확실)** `CLAUDE_CODE_SIMPLE=1`은 원문에서 비공개 기능이라고 소개된 것으로, 현재 버전에서 동일하게 동작하는지는 직접 확인하지 않았다.
- **(경계)** 조언의 전제는 Opus 5 수준 모델과 잘 갖춰진 자동 검증 수단이다. 테스트가 부실하거나 결과 판정이 주관적인 과제에는 "지우고 맡겨라"가 그대로 이식되지 않는다.
- **(캡처 노트)** 이 노트의 최초 캡처는 Jina 정적 크롤링으로 실패했고(페이지 프레임만 수집됨), `yt-dlp --write-auto-subs --write-description`으로 자막과 설명을 받아 재작성했다. YouTube는 자막을 별도 트랙 엔드포인트로 제공하므로 페이지 HTML 크롤링으로는 본문이 잡히지 않는다.

## 확인 질문
- Q1(전이): "6개월마다 전부 지워라"가 모델 제공자의 하네스(Claude Code 시스템 프롬프트)와 사용자의 프로젝트 규칙(AGENTS.md·스킬·훅)에 같은 강도로 적용되는가? 후자는 모델 결함 교정이 아니라 프로젝트 고유 지식을 담는 경우가 많다.
- Q2(왜·어떻게): 프롬프트가 없을 때 모델이 더 똑똑해진다면, 그 손실은 지시의 양에서 오는가 아니면 지시와 모델 기본 성향의 충돌에서 오는가? 둘은 대응법이 다르다(줄이기 vs 다시 쓰기).
- Q3(경계): 자동 판정 수단이 없는 작업(문서, 설계 판단, 사용자 경험)에서 종료 기준은 무엇으로 대체할 수 있는가? 원본은 이 경우를 다루지 않는다.
