## TL;DR
- OpenWorker는 대화형 답변이 아닌 **완성된 결과물**(문서·리포트·슬랙 답장)을 만들어주는 로컬 실행 오픈소스 AI 에이전트이나, 사용자가 직접 API 키와 도구를 연결해야 작동한다.

## 핵심
- OpenWorker는 기존 챗봇과 달리 **"대화 → 답변"** 구조가 아니라 **"지시 → 결과물"** 구조로 설계되었다. 사용자가 슬랙에서 멘션하면 데스크톱에서 실제 작업을 수행하고, 스레드로 완성물을 돌려보낸다. 이는 AI가 단순 정보 제공자를 넘어 **실행 주체(agent)** 역할을 한다는 뜻이다.
- 실행력은 **도구 연결**에서 나온다. GitHub·Jira·Notion 등 25개 이상의 외부 도구와 터미널·로컬 파일까지 접근하므로, 연결된 범위 내에서만 실질적 업무가 가능하다. 연결하지 않은 도구는 사용할 수 없다.
- 안전 장치로 **Human-in-the-Loop** 패턴을 채택했다. 메시지 전송이나 명령 실행 같은 영향력 있는 행동 전에 반드시 사용자 승인을 받는다. 이는 자율성과 안전성 사이의 균형 지점이다.

## 깊이
- **[결과물 지향 설계]** 대화 답변이 아닌 파일 형태의 산출물(문서·스프레드시트·리포트)을 생성한다. 이는 LLM의 출력을 사람이 직접 복사-붙여넣기하는 단계를 자동화하는 것으로, 실제 업무 자동화의 핵심 가치다.
- **[BYOM 구조]** 모델은 사용자가 자신의 API 키로 연결하거나 로컬 모델로만 돌릴 수 있다. 특정 벤더 종속 없이 모델 교체가 가능한 유연성을 제공하지만, 반대로 API 키 발급과 비용 관리 책임이 사용자에게 넘어간다(원문에 없음: 구체적 지원 모델 목록).
- **[셋업 비용]** 슬랙·지라·노션 등 실제 도구를 하나씩 연결해야 제 몫을 한다고 명시되어 있다. 연결한 만큼만 일하는 구조이므로, 초기 세팅에 드는 시간과 유지보수가 실사용의 핵심 장벽이다.

## 용어 풀이
- **AI 에이전트(AI Agent)** — 자율적으로 판단하고 도구를 사용해 작업을 수행하는 AI / 비유: "심부름꾼에게 장보기 목록을 주면 알아서 사온다" / 비유가 깨지는 지점: 심부름꾼은 상식을 갖추었지만 AI 에이전트는 도구 연결 범위와 프롬프트 지시에만 의존한다.
- **Human-in-the-Loop** — 중요한 결정 시점에 사람의 승인을 거치는 패턴 / 비유: "결재 도장" / 비유가 깨지는 지점: 결재는 사전 검토지만, 여기서는 실행 직전 승인이라 지연 비용이 더 작다.
- **로컬 모델** — 클라우드 API 없이 사용자 기기에서 직접 실행하는 LLM / 비유: "집에서 키우는 반려견 vs 외부 훈련소" / 비유가 깨지는 지점: 로컬 모델은 성능과 하드웨어 제약이 따르며, 원문에서 구체적 모델명은 언급되지 않았다.

## 시각 자료

| 구분 | 내용 |
|------|------|
| **입력** | 슬랙 멘션, 명령어, 이벤트 |
| **추론** | 사용자 API 키 모델 or 로컬 모델 |
| **출력** | 문서·스프레드시트·리포트(파일), 슬랙 스레드 답장 |
| **도구** | 25+개(Slack, GitHub, Jira, Notion, Terminal, 로컬 파일 등) |
| **안전** | 중요 행동 전 사용자 승인(Human-in-the-Loop) |
| **설치** | 오픈소스, 로컬 실행, API 키 + 도구 수동 연결 필수 |

## 핵심 시사점 / 판단
- **(저자 주장)** OpenWorker는 "채팅 대신 끝난 일을 가져다주는" AI 동료로서, 대화형 AI에서 실행형 AI로의 전환을 보여준다.
- **(저자 주장)** 연결한 만큼만 일하는 구조이므로 셋업 수고가 있지만, 그만큼 커스터마이징 자유도가 높다.
- **(검증 필요·불확실)** 25개 이상의 도구 연동 구체적 범위와 안정성, 로컬 모델 사용 시 성능 수준, 실제 업무 환경에서의 신뢰도는 원문에서 확인되지 않는다.
- **(검증 필요·불확실)** GitHub 레포(`andrewyng/openworker`)의 실제 존재 여부와 현재 상태(스타 수·활성도)는 원문만으로는 확인할 수 없다.
