## TL;DR
- AI가 "만들 수 있는가"의 문턱을 낮췄지만, "제대로 구성하는가"는 여전히 인간의 판단과 경험이 필요하며, 오히려 더 중요해진다.

## 큰 그림
```
        [ 소프트웨어 엔지니어링 ]
                 │
   ┌─────────────┴─────────────┐
 [구현 가능성]            [시스템 설계]
   "만들 수 있는가"          "제대로 구성하는가"
        │                          │
   ┌────┴────┐              ┌──────┼──────┬──────┐
 TDD/검증  코드 생성      경계/API  절충안  인지부하  안정vs유연
   ▲ LLM 잘함             ▲ LLM 한계 / 인간 판단 필요
        │
   ┌────┴───────────────┐
 도구 호출·지시 반복     구조 추론·장기 유지보수
 (LLM 강점)            (LLM 부족, 기본기 핵심)
```

## 핵심
- 에이전트 하네스와 모델은 지난 1년간 "이걸 구현할 수 있는가"라는 문턱을 크게 낮췄다. 하지만 저자는 구현 가능성이 소프트웨어 엔지니어링의 시작일 뿐이라고 본다. 용접을 배울 때 너무 무거워 작업장 문으로도 못 빼는 물건을 만들었던 경험에 빗대어, "만들 수 있다"와 "제대로 구성한다"는 다른 문제라고 강조한다.
- 이 간극이 핵심이다. TDD와 결정론적 검증 도구를 붙이면 작동하고 테스트 가능한 코드까지는 빠르게 만들 수 있다. 그러나 그 위 단계, 즉 모듈 경계를 어디에 둘지, API를 어떻게 설계할지, 다른 시스템과 어떻게 결합할지, 몇 년 뒤 변경까지 어떻게 감당할지는 하나의 객관적 정답이 없고 경험·판단·미래 추정이 필요하다.
- 그래서 저자는 LLM의 진짜 강점이 "코드를 예측해 생성"하는 것이 아니라 "도구를 호출하고 지시를 따라 작업을 반복"하는 능력에 있다고 본다. 필요한 시점에 간결한 컨텍스트를 주고, 검증 도구가 자연어 피드백을 돌려주면 스스로 결과를 수정하게 할 수 있다. 반면 장기 유지 시스템의 구조와 절충안을 신중히 판단하는 능력은 아직 충분하지 않다고 주장한다.
- 결론적으로 구현이 쉬워질수록 엔지니어의 역할은 사라지기보다, 문제에 맞는 추상화·절충안 선택, 인지 부하 관리, 어디를 안정적으로 두고 어디를 유연하게 만들지 결정하는 일에 집중된다고 본다.

## 깊이
- [구현↔설계 간극] 저자가 TDD 명령(`develop with red/green TDD`) 예시를 드는 이유는, 에이전트가 "작동 + 테스트 가능" 단계까지는 도달하지만 그 위의 구조적 결정에서는 멈추거나 틀리기 때문이다. HN 댓글들도 이를 뒷받침: 생성 코드는 디렉터리 구조·인터페이스 설계·상태 관리가 "뒤죽박죽"이고, 특히 프롬프트에 명시하지 않은 가정(어떤 오류에서 즉시 중단하고 어떤 건 감수할지)을 모델이 대신 결정해 자주 틀린다는 증언이 있다(2차, 댓글 주장).
- [LLM의 본질 관점] 저자는 LLM을 "인간 지식을 압축해 다음 결과를 예측하는 시스템"으로 본다(저자 주장). 근거로 Apple의 *The Illusion of Thinking*과 JEPA/LeWorld Model 연구를 인용하지만, 이들이 코딩 에이전트와 직접 동일 영역은 아님을 스스로 한정한다. HN에서는 "예측 과정에서 추론이 창발했다"는 반론과 "추론처럼 보이는 것만으로 충분할 수 있다"는 입장이 공존(2차, 불확실).
- [안전] 저자는 LLM이 좋은 지시와 악의적 지시를 완벽히 구별 못한다고 본다. Simon Willison의 *lethal trifecta*를 인용해 프롬프트 인젝션 완전 차단의 어려움을 강조. 단, HN 댓글 중 Anthropic 평가(간접 주입 720회 전부 실패)를 근거로 "대체로 해결됐다"는 반례도 있으나, 다른 댓글이 "시스템을 우연히 망가뜨릴 위험까지 사라진 건 아니다"로 제동(2차, 주장 충돌).
- [반례] 한 HN 댓글은 15만 줄 코드베이스를 AI가 유지보수 중이며 코드를 거의 보지 않는다는 체험을 보고하지만, 곧바로 "두 달밖에 안 쓰고 코드를 안 보면 품질·내구성 판단을 진지히 받아들이기 어렵다"는 제동이 붙는다(2차, 주장).

## 용어 풀이
- **에이전트 하네스(Agent Harness)** — 모델을 감싸 도구 호출·루프·검증을 연결해주는 뼈대 / 비유: 레이싱카 엔진(모델)을 달리게 하는 차체·조향장치 / 비유 깨짐: 하네스는 규칙 기반이라 엔진의 '판단'을 바꾸진 못한다.
- **결정론적 검증(Deterministic Verification)** — 같은 입력엔 항상 같은 결과를 내는 검사(테스트·타입검사·린트) / 비유: 디지털 주방저울, 매번 같은 무게 표시 / 비유 깨짐: 검증이 통과해도 '의도'를 맞았는지는 보장 못한다.
- **절충안(Trade-off)** — 한 속성을 키우면 다른 속성이 줄드는 관계 / 비유: 가방 용량 vs 무게 / 비유 깨짐: 소프트웨어에선 비용·시간·조직 같은 비기술 변수도 얽혀 단순 교환이 아님.
- **인지 부하(Cognitive Load)** — 코드를 이해·수정할 때 뇌가 써야 할 노력 / 비유: 방이 어지러울수록 청소할 에너지 더 듦 / 비유 깨짐: 주관적이라 한 팀에 쉬운 코드가 다른 팀엔 어려울 수 있다.
- **lethal trifecta(치명적 삼합)** — (비공개 데이터 접근)+(외부 입력)+(도구 실행)이 같은 에이전트에 공존할 때 치명 위험 / 비유: 불·산소·연료가 같은 방에 있으면 폭발 / 비유 깨짐: 실제론 세 요소를 완전히 분리하기 어려워 "부분 완화"만 가능.

## 핵심 시사점 / 판단
- (저자 주장) 구현이 쉬워질수록 추상화·절충안·인지 부하 관리·경계 설계 같은 기본기가 더 중요해진다.
- (저자 주장) LLM은 도구 호출·지시 반복에 강하지만, 장기 시스템 구조 판단엔 한계가 있다.
- (검증 필요·불확실) LLM의 "추론"이 창발했는지, 프롬프트 인젝션이 해결됐는지는 평가·관점이 갈린다.
- (사실) TDD·타입검사·테스트 같은 결정론적 검증 도구는 LLM의 자기수정 루프에 실용적으로 연결된다.
