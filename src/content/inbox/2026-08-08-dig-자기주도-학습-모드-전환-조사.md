> 캡처 맥락: dig 스킬(SKILL.md + references)·mark-board SPEC 노트·저장소 원천 소스(top-down-learning, Dan Koe)를 분석하고 학습과학 근거를 더해 종합한 **설계 조사**다. 아직 스킬·코드는 아무것도 건드리지 않았다. 6개 미결 결정을 마지막에 남긴다.

## TL;DR

- 제안은 세 개의 서로 다른 변경 묶음이고 위험도가 다르다 — **A) 구현 주체 역전**(에이전트→사용자), **B) 하강·게이트·마일스톤 의식 제거**, **C) 로그→카테고리 노트→노드 그래프 파이프라인 신설**. A·B는 dig의 심장, C는 안전한 가산 기능.
- dig의 에이전트-우선은 취향이 아니라 두 역할을 하는 불변식이다 — (1) 갭과 버그 분리, (2) 갭 강제 생성. 사용자-구현은 (2)를 약화시켜 dig이 막으려던 컴포트존 코스팅을 되부른다.
- 그러나 사용자 모드에도 근거가 있다 — 생성 효과, desirable difficulty, 특히 호기심 기반 인코딩. 저장소의 두 소스가 이미 양극(Petersson=에이전트-우선, Dan Koe=출력-우선)을 담고 있어 이건 철학 이탈이 아니라 반대 극 전환이다.
- 결론: dig을 고치지 말고 가벼운 자매 스킬로 신설한다(dig은 하드 스트레치용으로 남김). 노드 그래프의 엣지는 개념 노트의 앞/뒤 링크에 이미 있어, 그래프 요구가 그 규율 유지의 이유가 된다.

## 제안을 세 변경으로 분리

| | 변경 | dig과의 관계 | 위험도 |
| --- | --- | --- | --- |
| A | 구현 주체 역전 — 에이전트가 다 짜주는 대신 사용자가 직접 구현 | dig 불변식 제거 | 높음 |
| B | 하강·게이트·마일스톤·7산출물 의식을 걷고 "원하는 부분만 질문"을 로그로 | dig 절차 골격 제거 | 중간 |
| C | 로그 → 카테고리화된 레이어드 노트 → mark-board식 노드 그래프 | dig에 없던 신규(가산) | 낮음 |

C는 거의 순수 이득이고 A·B와 독립적으로 만들 수 있다. A·B는 학습 효과의 트레이드오프가 실재하므로 따로 판단한다.

## 변경 A·B가 건드리는 것 (근거 있는 반론)

dig SKILL.md는 "구현을 먼저 끝까지"를 전제로 못 박으며 이유를 남겼다:

- "돌아가지 않는 상태에서 내려가면 걸리는 자리가 갭인지 구현 오류인지 구분되지 않는다."
- "이해한 만큼만 코드를 받지 마라 — 이해한 범위로 구현을 제한하면 갭이 생기지 않아 배울 이유가 만들어지지 않는다."

에이전트-우선의 두 역할:

- **(1) 갭 순수성** — 코드가 돌아가니 막히는 자리는 100% 이해 갭. 버그와 안 섞인다.
- **(2) 갭 강제 생성** — 능력 밖 코드를 받으므로 반드시 모르는 곳이 나온다. 배울 이유가 자동 발생.

사용자-구현(A)은 (2)를 약화시킨다. 자기가 이해하는 만큼만 짜면 갭이 안 생기고 배울 게 없다 — dig 실패 신호 "커리큘럼 유입"으로 잡으려던 컴포트존 코스팅이다. (1)도 잃는다: 막혔을 때 버그인지 개념 갭인지 스스로 못 가른다.

변경 B의 부수 위험:
- **얕은 정지** — dig 하강은 물음표가 없어질 때까지 재귀로 바닥(선형대수·베이즈)까지 간다. "원하는 부분만 질문"은 첫 답에서 만족하고 멈추기 쉽다.
- **착각** — 마일스톤 게이트가 사라지면 이해한 느낌과 실제 이해가 기록상 구별되지 않는다(Bjork: 지금 되는 것 ≠ 나중에 남는 것).

## 사용자 모드의 과학적 근거 (균형)

- **생성 효과** — 스스로 만든 정보가 읽은 정보보다 잘 남는다(d≈.40, Bertsch 2007). 에이전트 코드를 읽는 것은 비생성적, 직접 짜는 것은 생성적. 갭만 계속 생긴다면 사용자-구현이 유지에 유리.
- **Desirable difficulty** — 구현하며 낑낑대는 것은 바람직한 어려움이고, 돌아가는 코드를 받아 읽는 편함은 dig 자신이 경계하는 "쉬운 느낌"(Bjork).
- **호기심 기반 인코딩** — "원하는 부분만 질문"은 높은 호기심 상태의 질문이고, 그 상태에선 대상뿐 아니라 곁가지 기억까지 오르며 하루 뒤에도 유지된다(Gruber 2014; Kang 2009, 둘 다 저장소 인용). 인코딩 강도 면에선 사용자 모드가 유리할 수 있다.

결정적 프레이밍: 저장소의 두 원천 소스가 이미 양극을 담고 있다.
- top-down-learning(Petersson) = 에이전트가 코드를 다 주고 하강 = 현 dig.
- 읽은-것을-기억하는-법(Dan Koe) = "배우기를 시작하지 말고 프로젝트 첫 걸음을 떼라, 가장 가까운 튜토리얼에서 딱 한 조각만 훔쳐 쓰고 반복" = 정확히 사용자 제안.

이 변경은 철학 이탈이 아니라 이미 문서화된 반대 극(출력-우선)으로의 전환이다.

## 잃는 보증을 무엇으로 대체하나 (설계)

| 잃는 것 | 대체 장치 |
| --- | --- |
| (2) 갭 강제 생성 | 진입에서 "이 프로젝트가 내 현재 능력 위인가"를 묻는다. 스트레치의 출처를 받은 코드에서 프로젝트 난이도로 옮긴다. 능력 안쪽이면 반려 |
| 질문 트리거의 질 | "궁금"이 아니라 "막힘"을 1차 트리거로. 막힘은 실제 갭을 보증. 궁금은 호기심 인코딩용으로 별도 태그해 함께 남기되 구분 |
| (1) 갭 순수성 | 막혔을 때 버그인지 갭인지 먼저 가르는 한 스텝(함께 디버깅 → 돌아가면 개념 질문). Petersson도 함께 디버깅을 학습 계기로 씀 |
| 강제 재귀 하강 | 응답 형식으로 깊이 유지 — 정의로 끝내지 말고 "왜 그렇게 되는가"까지. 바닥까지는 사용자 옵트인 |
| 마일스톤 게이트 | 레이어드 노트의 확인 질문 3개가 최소 인출 게이트. 답을 가린 채, 하나는 본문에 없던 상황으로 |

## 파이프라인 설계 (변경 C)

**1단계 — 질문 로그(append-only 스테이징).** 한 질문이 한 줄. dig `exchange` 규격에 개념/카테고리 추가:

```jsonl
{"ts":"…","q":"사용자 질문 그대로","a":"확정 요지 3~5줄","concept":"gradient","category":"LEARN","trigger":"막힘|궁금","refs":["…"]}
```

`q`는 사용자 문장 그대로(생성 효과·"무엇을 몰랐나" 기록). 이건 스테이징이고 최종 노트가 아니다 — inbox/idea-inbox처럼 승격 후 소비된다.

**2단계 — 마이그레이션 = 기존 카테고리·개념에 통합.** 새 고립 노트를 만들지 말고 이미 있는 개념 노트를 찾아 갱신한다(dig 개념 노트 원칙 "덧붙이지 말고 정리한다"를 저장소 규모로). 대상 카테고리 체계는 이미 존재한다 — notes 토픽 트리(허브+자식), noteId 접두어(LEARN/AI/ARCH/…), tags. 본문은 레이어드 포맷(입문/중급/전문가)으로. 이 단계는 core(핵심 확정) + notes-polish(통합) 성격의 결합이다.

**3단계 — 노드 그래프.** 그래프 엣지는 이미 노트 안에 있다. 개념 노트 규격의 앞(선행)·뒤(열리는) 링크가 곧 방향 엣지, 허브↔자식은 포함 엣지, 인라인 링크는 참조 엣지. 노드는 개념 노트, 그룹/색은 카테고리. 따라서 노드 그래프 요구는 역으로 개념 노트 앞/뒤 규율을 유지할 이유가 된다.

## mark-board 현실 확인 + 그래프 실현

- mark-board는 이 저장소가 아니라 별도 로컬 앱이다(NestJS 서버 + React Flow 캔버스, brew 설치). mark-board 노트는 그 앱의 SPEC. "mark-board 형식과 유사하게"는 그 캔버스 UX를 이 사이트에 재현하자는 뜻.
- 이 저장소는 순수 Astro, React 없음. mermaid(build-time SVG)만 있다. mark-board가 React Flow를 쓴 이유는 노드 편집인데, 학습 노트 그래프는 읽기 전용(팬·줌·클릭 이동)이라 그 무게가 불필요.

| 옵션 | 방식 | 장점 | 대가 |
| --- | --- | --- | --- |
| a. 정적 mermaid | 빌드시 노트 링크→mermaid SVG | 의존성 0(이미 있음) | 노드 많으면 뭉개짐, 팬·줌·클릭 약함 |
| b. 클라이언트 포스 그래프 | cytoscape.js / d3-force를 Astro client 아일랜드로 | 팬·줌·클릭 이동 | 클라이언트 JS 추가, 순수-Astro 규약 이탈 |
| c. React + @xyflow/react | mark-board와 동형 | 캔버스 UX 그대로 | React 통합 신규 — 가장 무거움 |

읽기 전용 학습 그래프엔 b(cytoscape/d3)가 균형점. 데이터는 빌드시 노트 frontmatter+링크에서 JSON 추출해 아일랜드에 주입. mark-board 코드 재사용 불필요(그쪽은 서버·편집·SQLite 전제).

## 신규 스킬 vs dig 수정 (권고)

권고: dig을 고치지 말고 가벼운 자매 스킬을 신설한다.

- 에이전트-우선은 dig의 불변식이라, 빼면 튜닝이 아니라 다른 기계다. 덮어쓰면 하드 스트레치 학습에 유용한 도구를 파괴한다.
- CLAUDE.md의 Surgical Changes / Preserve Existing Behavior와 맞는다.
- dig limits.md는 제거한 기계를 되살릴 때의 맞바꿈을 경고하며 결정을 되돌리기 비싼 것으로 취급한다.
- dig은 "배울 것의 종류로 절차를 나누지 말라"고 하지만, 이건 종류가 아니라 학습 모드(에이전트-스트레치 vs 자기주도-호기심)의 차이라 정당하게 다른 엔진이다.

분담: 하드·낯선 분야 = dig(에이전트가 끌어올림), 어느 정도 짤 수 있고 직접 만들며 배우고 싶다 = 신규 스킬. 진입에서 모드만 가르면 된다.

## 결정할 것 (착수 전 · 추천 포함)

1. 질문 트리거 — 궁금 / 막힘 / 둘 다(구분 태그)? → 추천: 둘 다, 태그로 구분.
2. 스트레치 보증 — 진입에서 "능력 위 프로젝트인가" 게이트? → 추천: 둔다.
3. 최소 게이트 — 레이어드 노트 확인 질문을 인출 게이트로 강제? → 추천: 강제.
4. 로그 위치 — skill-local staging / src/content 스테이징 컬렉션? → 추천: skill-local staging(최종 노트만 저장소에).
5. 그래프 렌더 — 정적 mermaid / cytoscape 아일랜드 / React Flow? → 추천: cytoscape 아일랜드.
6. 스킬 형태 — dig 수정 / 신규 자매 스킬? → 추천: 신규 스킬.

## 한계

- 사용자 모드가 dig보다 나은지는 프로젝트가 실제로 능력 위일 때만 성립한다 — 난이도 게이트가 없으면 갭이 안 생겨 학습이 멈춘다.
- 호기심 인코딩·생성 효과 수치는 각 실험 조건의 값이고 이 절차로의 이식은 유추다.
- 노드 그래프의 값은 마이그레이션이 앞/뒤 링크를 성실히 남기는가에 전적으로 달렸다. 링크가 비면 그래프는 고립점 무더기가 된다.
