## TL;DR

- **한 문장**: ==크래프톤은 코딩테스트의 변별력 붕괴에 대한 대응으로 산출물이 아니라 *AI와 일하는 과정*을 자동 기록해 채점하는 평가 솔루션 **Cofa-Probe**를 만들었고, CJ올리브영이 이를 도입해 라이브 코딩을 폐지한 **AI 과제 전형**으로 경력 공채를 진행 중이다(2026-07-20 ~ 08-09).==
- **Probe의 핵심 설계**: ==평가 대상이 "정답"에서 "과정"으로 이동한다.== 브라우저 웹 IDE에서 실 API·실 컴퓨트로 과제를 풀게 하고, 프롬프트·transcript·도구 설정·검증 실행 흔적을 **지원자가 서술하지 않아도 자동 수집**한 뒤 rubric으로 채점한다. 사후 Q&A로 "본인 산출물을 설명할 수 있는가"를 따로 검증한다.
- **평가축이 배포처마다 다르다**: Cofa 공식 제품 페이지는 **3축**(기술·의도·인지), 올리브영 채용 페이지는 여기에 **소통(Communication)을 더한 4축**을 제시한다. Adopt 티어에 "회사 평가 영역/가중치 정의"가 있어, 축 구성 자체가 고객사별 조정 파라미터로 보인다 (§평가축 불일치).
- **모델 환경은 플랫폼 지급 + 전원 동일**: 데모 영상 실측으로 **Claude Code 사전 설치**(`Opus 4.8 (1M context) · API Usage Billing`), 요금표상 **Claude·OpenAI·Gemini 제공**. 공정성 각주가 "모든 지원자에게 같은 모델·같은 토큰 한도, 개인 구독 여부는 평가에 영향 없음"이라고 못박는다 — "모델에 제한을 두지 않는다"는 *하향 조정하지 않는다*는 뜻이며, 유료 구독자 우위 제거가 목적이다.
- **기존 스킬·하네스 반입은 허용이 아니라 가점 항목이다**: `uploads/` 디렉터리와 드래그앤드롭 드롭존이 있고, 워크스페이스에 `AGENTS.md`·`.mcp.json`·`.claude.json`이 이미 놓여 있으며, rubric `i5`(재사용 가능한 작업 체계)가 "**반입 자산을 실제로 사용**"을 직접 채점한다. 단 같은 항목에 "도구·프롬프트 남발 없음"이 걸려 있다 — 양이 아니라 신호 대 잡음비.
- **프론트엔드 지원자에게 실질적으로 가장 중요한 사실**: 올리브영 프론트엔드는 지금 **두 공고가 동시에 열려 있고 중복 지원이 불가**하다 — AI-First Track(경력 2년+, AI 과제 전형)과 기존 커머스플랫폼유닛 공고(경력 5년+, 라이브 코딩 전형). 경력 연차와 전형 방식이 모두 달라 선택이 곧 전략이다.
- **짝을 이루는 Sourcer는 "지원하지 않은 사람"을 찾는다**: ==컨퍼런스·arXiv·GitHub·특허·커뮤니티·블로그 등 **8개 공개 소스**를 스캔해 후보 카드를 만들고, 스킬 매칭·레벨 추정·**이직 가능성**을 점수화한다.== 로그인이 필요한 폐쇄 플랫폼은 쓰지 않으므로 **열린 웹의 흔적만** 읽는다.
- **이력 전략에 대한 함의**: 평가 단위가 "무엇을 했다"는 진술에서 **링크로 가리킬 수 있는 산출물**로 바뀐다. 프론트엔드 직무에 실제로 유효한 소스는 8개 중 4개(GitHub·블로그/개인 사이트·국내 컨퍼런스·커뮤니티)뿐이며, arXiv·특허는 해당 없다 (§5).

## 1. Cofa / Cofa-Probe — 무엇인가

크래프톤이 개발한 **AI Native 인재 발굴·평가 채용 플랫폼**이다. 두 모듈로 구성된다.

| 모듈 | 역할 | 하는 일 |
| --- | --- | --- |
| **Sourcer** | 발굴 (Discovery) | 논문·오픈소스·특허·컨퍼런스 활동 등 공개 신호를 연결해 *아직 지원하지 않은* 후보의 전문성·관심사를 파악하고, 적합도 점수와 판단 근거, 아웃리치 초안을 제시(담당자 승인 후 발송) |
| **Probe** | 검증 (Assessment) | 모든 지원자에게 동일한 AI 환경을 주고, 문제 정의부터 도구 선택·검증·수정까지 실제 작업 과정을 기록·채점 |

### 문제 인식 — "채용 공식이 깨졌다"

Cofa가 스스로 내세우는 전제는 명확하다: 자기소개서는 AI가 다듬고, 코딩테스트는 AI가 풀고, 포트폴리오는 점점 빠르게 만들어진다. **사람을 가려내던 기존 신호가 변별력을 잃었다.** 그래서 "AI 도구를 똑같이 쥐여줘도 결과물은 같아지지 않는다"는 관찰에 기대어, 격차를 만드는 것은 도구가 아니라 *도구를 운용하는 역량*이라고 규정한다.

부수적으로 제품 페이지가 인정하는 현장 통증 세 가지 — 이게 왜 이 제품이 팔리는지를 설명한다:
- "AI 인재상이 없어요" — 회사·포지션마다 필요 역량이 달라 범용 정의가 합의되지 않음
- "'잘 쓴다'의 기준이 없어요" — 빠르게 코드를 뽑는 것이 잘 쓰는 것은 아님
- "평가자인데 AI를 잘 몰라요" — 현업 평가자가 AI에 익숙하지 않으면 후보 간 실제 격차를 읽지 못함

### 평가축 (Cofa 제품 기준 · 3축)

| 축 | 원어 | 무엇을 보는가 |
| --- | --- | --- |
| **기술 관리** | Technique | AI가 만든 산출물을 본인이 장악해, 실제로 돌아가게 · 유지 가능한 구조로 · 보안이 새지 않게 구성했는가 |
| **의도 관리** | Intent | AI에게 일을 맡기고 조향하며, 목표·제약을 정의하고 작업을 분해해 위임하고, 검증 루프로 결과를 통제하는가 |
| **인지 관리** | Cognition | AI의 작업과 산출물을 이해하고, 왜 이 구조인지·어떻게 동작하는지·어디서 깨지는지 **본인 산출물 기준으로** 설명할 수 있는가 |

각 축은 세부 rubric으로 채점되며, 기준마다 grey area와 충족·미충족 예시가 정의돼 **채점이 재현 가능**하도록 설계됐다고 밝힌다. 근거가 되는 프롬프트·소스코드를 함께 제시한다.

### 세부 rubric 12개 — 축별 평가 방법이 다르다

Probe 페이지의 렌더링되지 않은 응답 데이터에서 전체 rubric이 확인됐다(탭으로 가려져 화면에는 기술 관리만 노출됨). **축마다 평가 근거가 다르다는 점이 설계의 핵심**이다.

**기술 관리 — 산출물·코드로 평가**

| # | 기준 | 무엇을 보는가 | 세부 |
| --- | --- | --- | --- |
| t1 | 기능·실행성 | 실제 환경에서 깨끗하게 돌아가는가 | 부팅·실 호출 확인 · 테스트 통과율 · mock이 아닌 실 인프라 검증 |
| t2 | 격리·구조화 | 유지·확장 가능한 구조로 만들었는가 | 외부 API 격리 계층 · 에러 유형별 분류 · race-free 트랜잭션 |
| t3 | 보안 위생 | 시크릿·민감정보가 코드·로그로 새지 않는가 | 시크릿 누출 0 · `.gitignore` 시크릿 패턴 · raw key는 ENV로만 |

**의도 관리 — 행동으로 평가** (가장 항목이 많다 = 이 축이 무게중심)

| # | 기준 | 무엇을 보는가 | 세부 |
| --- | --- | --- | --- |
| i1 | Output 목표 구체화 | AI에게 맡긴 일이 어떤 상태가 되면 끝나는지를 정의하는가 | 완료 조건·수용 기준 명시 · 산출물 형태·제출 포맷 지정 · 검증 기준을 되돌려볼 수 있는 문장으로 · 작업 가능한 단위의 목표 |
| i2 | 문제 상황·제약 정의 | AI가 추측하지 않도록 맥락과 경계를 제공하는가 | 필요한 파일·로그·현재 상태 제공 · 하지 말 것·범위·제약 명시 · 증상만이 아니라 왜 문제인지 · 과잉 구현에 경계 설정 |
| i3 | 의도 갱신·맥락 유지 | 새 정보와 실패가 생겼을 때 지시와 기록을 갱신하는가 | 주요 결정의 이유 기록 · **버린 대안과 기각 근거** · AI 제안과 본인 판단 구분 · 실패가 다음 지시에 반영 |
| i4 | 작업 분해·위임 설계 | 큰 문제를 점검 가능한 실행 단위로 쪼개 맡기는가 | 실행 단위 분해 + 순서 설계 · 중간 점검 지점 확보 · AI 재량 범위 지정 · 범위 밖 변경 거절 |
| i5 | 재사용 가능한 작업 체계 | 반복 작업과 맥락 전달을 문서·도구로 고정하는가 | 의도를 인수 가능한 문서로 · **반입 자산을 실제로 사용** · 자동화가 판단을 가리지 않음 · 도구·프롬프트 남발 없음 |
| i6 | 검증 루프 설계·통제 | AI 결과를 그대로 믿지 않고 검증 → 수정 → 재검증으로 닫는가 | 테스트·실행으로 결과 검증 · **실패 후 같은 검증 재통과** · 완료 보고 독립 검증 · 사람 승인 지점 구분 |

**인지 관리 — 사후 Q&A로 평가**

| # | 기준 | 무엇을 보는가 | 세부 |
| --- | --- | --- | --- |
| c1 | AI 의사결정·근거 이해 | AI가 택한 구조와 기술이 무엇이고 왜인지 설명하는가 | 설명과 실제 구현의 일치 · 이유를 요구사항·제약에 연결 · 트레이드오프와 포기한 것 |
| c2 | AI 산출물 구조 이해 | AI가 만든 것의 실제 구성과 연결을 설명하는가 | 파일·모듈·데이터 흐름 · 구현/개선/미구현 구분 · 제3자가 검증 가능한 근거 |
| c3 | AI 산출물 동작·리스크 예측 | 정상·비정상 경로의 동작과 깨질 조건을 예측하는가 | 정상 경로 동작 설명 · 실패·timeout 등 비정상 대응 · 깨질 조건·리스크 지점 · 향후 확인·개선 지점 |

**모든 답변 공통 기준**(horizontal): 실제 제출물과 모순되지 않는가 · 일반론이 아닌 본인 산출물 기준인가 · 없는 것을 지어내지 않는가 · **권위가 아닌 증거로 추론하는가**

### 진행 방식 (4단계)

```
1. 실전 환경에서 시작
   브라우저 웹 IDE · mock이 아닌 실 API/실 컴퓨트 · 시간 + 토큰 budget 제약
2. 산출물 · 과정 기록 자동 수집
   소스코드 + transcript + 프롬프트 + 도구 설정 + 검증 실행 흔적
   → 지원자가 따로 서술하지 않음
3. 사후 Q&A
   결과물 · 의도 · 인지에 걸쳐 출제, 본인 결과물을 설명해야 함
4. 자동화된 평가 · 면접 리포트
   역량별 rubric 자동 채점 + 후보별 변별 리포트
```

**가능하며, 오히려 가점 항목이다.** 근거 세 층이 일관된다.

1. **환경**: `uploads/` 디렉터리 + 드래그앤드롭 드롭존, 워크스페이스에 `AGENTS.md`·`.mcp.json`·`.claude.json`이 이미 존재

3. **rubric 전용 항목**: 의도 관리 축의 `i5` **재사용 가능한 작업 체계** — "반복 작업과 맥락 전달을 문서·도구로 고정하는가" / 세부: 의도를 인수 가능한 문서로 · **반입 자산을 실제로 사용** · 자동화가 판단을 가리지 않음 · 도구·프롬프트 남발 없음

즉 **반입 자체가 아니라 "반입한 것을 실제로 써서 판단이 드러나는가"가 점수**다. 충족 신호에 `CLAUDE.md`가, 미충족 신호에 "도구·MCP 남발로 흐려진 신호"가 나란히 있는 이유다 — 붙인 양이 아니라 신호 대 잡음비를 본다.

**두 가지 단서**:
- **MCP 커스터마이즈는 기업측 권한**이다. "MCP 외부 도구 연동 커스터마이즈"는 **Adopt 티어 기능**으로 분류돼 있어 연동 범위는 채용사가 정하는 노브다. 지원자가 임의로 외부 MCP 서버를 붙일 수 있는지, 네트워크 egress 정책이 어떤지는 공개 자료에 없다. *(`.mcp.json`이 워크스페이스에 있으므로 로컬 stdio 서버는 가능할 것으로 추정)*
- **"하네스 업로드 가능" 문구의 출처가 채용 전형 문서가 아니다.** Cofa가 별도 운영한 공개 행사 페이지에만 있고, 올리브영 AI 과제 전형 안내에는 동일 서술이 없다. 동일 Probe 엔진이며 사전 체험 README가 "본 시험에서도 동일한 환경·도구"라고 하므로 같을 것으로 보이나 **추정**이다. 환경 쪽 근거(`uploads/` 디렉터리·드롭존·rubric `i5`)는 제품 자체에서 확인된 것이라 이 단서와 무관하게 유효하다.

### 채점 신호 — 충족 / 미충족

제품 페이지가 명시한 신호 목록이다. **에이전트 코딩을 실제로 어떻게 하는지가 그대로 점수가 된다는 점에서 실무적으로 가장 유용한 부분.**

**충족으로 보는 신호**
- 완료 조건·수용 기준이 명시된 프롬프트
- 실패 → 수정 → *같은 검증으로* 재통과한 기록
- 결정 이유와 **기각한 대안**의 기록
- 새 세션이 이어받을 수 있는 의도 문서 (`CLAUDE.md`)
- 실제 제출물과 일치하는, 본인 산출물 기준의 답변

**미충족으로 보는 신호**
- "알아서 잘 만들어줘"식의 통짜 위임
- AI의 완료 보고를 검증 없이 수용
- 교과서 일반론으로 채운 답변
- 없는 파일·API를 인용하는 설명
- 도구·MCP 남발로 흐려진 신호

> 마지막 항목이 특히 눈에 띈다 — 도구를 많이 붙이는 것이 감점 요인으로 명시돼 있다. 모델 성능·범위에는 제한을 두지 않는다("실제 업무 환경과 동일한 자유도").

### 크래프톤 자체 적용

Probe는 **크래프톤의 정규 채용 평가 테스트로 이미 운영 중**이며, 연구원·엔지니어·비개발/백오피스까지 직군별 테스트와 평가 리포트를 제공한다고 밝힌다. 사내 AI 역량 평가도 도입·확장 중이며 전 포지션 확대를 준비한다고 한다. 즉 **자사에서 돌려본 것을 외부에 판매하는 구조**다.

## 4. Cofa Sourcer — 발굴 쪽 엔진

Probe가 "지원한 사람을 검증"하는 도구라면 Sourcer는 **"지원하지 않은 사람을 찾아내는"** 도구다. 이력 구성 전략에 직접 영향을 주는 쪽은 이쪽이다.

### 4-1. 전제 — 왜 만들었나

제품 페이지가 밝힌 문제 인식 세 가지:

1. **"공고를 내고 기다리면 이미 이직 중이거나 적극 탐색 중인 후보들만 만나게 돼요. 정말 필요한 사람들은 공고를 보지 않아요."**
2. **"엔지니어·연구자의 중요한 신호는 하나의 프로필보다 발표·논문·프로젝트·커뮤니티 활동에 더 많이 남아 있어요."**
3. "컨퍼런스 발표자, 논문 저자, 오픈소스 기여자 수백 명을 매주 추적하는 건 사람 손으론 어려워요."

핵심 주장: "AI 시대의 핵심 인재는 여러 공개 소스에서 **신뢰 가능한 발자취**를 남기고 있다." 즉 평가 대상이 *자기 진술(이력서)*에서 *제3자가 검증 가능한 흔적*으로 옮겨간다.

## 5. 이력을 어떻게 다르게 구성할 것인가 *(도출 — 사실이 아니라 판단)*

여기부터는 조사한 사실에서 **내가 도출한 해석**이다. Cofa는 기업용 도구이고 가중치는 공개돼 있지 않으므로, 아래는 "이 도구에 최적화하는 법"이 아니라 **"발굴 방식이 이렇게 바뀌면 무엇이 합리적인가"**다.

### 5-1. 전제 변화 세 가지

1. **채용의 진입점이 pull에서 push로 바뀐다.** 이력서는 *지원할 때* 쓰는 문서이고, Sourcer가 읽는 것은 *지원하지 않을 때도 존재하는* 흔적이다. 두 자산은 다르며, 후자는 미리 쌓아두지 않으면 만들 수 없다.
2. **단위가 "경력 기술"에서 "특정 가능한 산출물"로 바뀐다.** 후보 카드는 "3년간 React 개발"이 아니라 `PyCon 2024`, `12 PRs merged`처럼 **링크로 가리킬 수 있는 것** 하나씩으로 구성된다.
3. **검증 가능성이 표현력을 이긴다.** 카드에 "근거"가 함께 붙고 담당자가 그 근거를 클릭한다. 잘 쓴 자기소개보다 **제3자가 확인할 수 있는 흔적**이 강하다.

### 5-2. 프론트엔드 엔지니어에게 실제로 적용되는 소스만 골라내기

8개 소스를 그대로 따라가는 건 잘못된 조언이다. **arXiv 논문·인용 그래프·특허·연구실 페이지는 프론트엔드 직무에 사실상 해당하지 않는다** — ML 리서처 기준으로 설계된 소스다. 실제로 유효한 것은 4개다.

| 소스 | FE 적용 가능성 | 구체적으로 무엇 |
| --- | --- | --- |
| **GitHub** (PR·이슈·스타) | ★★★ 가장 직접적 | 본인 저장소보다 **남의 저장소에 머지된 PR**. 이슈 논의 기록도 읽힌다 |
| **공개 포트폴리오** (블로그·개인 사이트) | ★★★ 통제 가능성 최고 | 직접 소유·운영하므로 유일하게 100% 통제되는 소스 |
| **국내 컨퍼런스** | ★★ 진입 장벽 있으나 신호 강도 큼 | FEConf · DEVIEW · IF · 사내 기술 세미나 공개 발표 |
| **Tech 커뮤니티** | ★ 통제 어려움 | 디스코드·슬랙·오픈카톡. "Top 1%" 같은 활동량 지표로 읽힌다 |
| arXiv · 특허 · 학회 | ✗ | FE 직무에서는 무리한 투자. 무시해도 된다 |

### 5-3. 이력 구성 변경점 — 무엇을 다르게 쓸 것인가

**(1) "무엇을 했다"에서 "무엇을 가리킬 수 있다"로.**
기존 이력서 한 줄이 `대규모 트래픽 환경에서 렌더링 성능 개선`이라면, 발굴 가능한 형태는 그 판단 과정이 **공개된 글이나 커밋으로 존재**하는 것이다. 같은 사실이라도 링크가 붙으면 카드에 인용되고, 없으면 자기 진술로 남는다.

**(2) 결정 기록을 공개 자산으로 승격한다.**
Probe의 `i3`(버린 대안과 기각 근거)·`i5`(의도를 인수 가능한 문서로)가 채점하는 것과, Sourcer가 블로그에서 읽는 것이 **같은 형태의 문서**다. 즉 *결정 로그를 공개적으로 쓰는 습관 하나가 양쪽에 동시에 걸린다.* 이 저장소의 `AGENTS.md`·notes·wiki 구조가 이미 그 형태다 — 다만 `notes`/`inbox`/`sources`/`idea`는 검색·사이트맵에서 제외돼 있어 **발굴 대상이 되지 않는다**. 공개 노출을 의도한 것은 `posts`/`wiki`뿐이다. 발굴 관점에서는 이 경계가 곧 "보이는 이력"의 경계다.

**(3) 기여의 방향을 바꾼다.**
개인 프로젝트 저장소를 늘리는 것보다 **외부 저장소에 머지된 PR**이 카드에 더 잘 잡힌다(`12 PRs merged`가 샘플 카드의 단위다). 스타 수보다 머지 여부와 리뷰 논의 기록이 신호다.

**(4) 활동의 연속성을 관리한다.**
Fit Analyzer가 "최근 활동 신호로 이직 가능성"을 추정한다. *(추정)* 장기 공백 뒤 갑작스러운 활동 급증은 "구직 중" 신호로 읽히기 쉽다. 반대로 **꾸준한 저빈도 활동**이 레벨 추정에는 유리할 가능성이 크다 — 다만 이건 근거 없는 내 추론이며, 실제 가중치는 공개되지 않았다.

**(5) 동일인 식별을 의식적으로 정한다.**
Shadow Sourcer가 "가명/익명 활동까지 동일인 추정"을 한다. 즉 닉네임 활동을 묶는다. **묶이길 원한다면** GitHub·블로그·발표 자료에서 이름/핸들을 일관되게 쓰는 것이 발굴 확률을 직접 올린다. **원하지 않는다면** 분리해야 하며, 그 분리는 자동 추정을 상대로 하는 일이라 완전하지 않다.

### 5-4. 무엇을 학습할 것인가 — 우선순위

Probe 4축과 Sourcer 소스를 겹쳐 보면 학습 항목이 좁혀진다. **AI 도구 숙련도는 명시적으로 평가 대상이 아니다**("특정 AI 툴의 숙련도를 의미하지 않는다")는 점이 출발점이다.

### 5-5. 한계와 주의 — 이 도출을 어디까지 믿을 것인가

- **Cofa는 벤더 하나다.** 8개 소스 구성은 Cofa의 선택이고, 가중치는 비공개다. 특정 제품에 최적화하는 것은 합리적이지 않다. 지속되는 것은 *"공개 흔적이 발굴 표면이 된다"*는 메커니즘이며, 이 메커니즘은 Cofa가 사라져도 남는다. *(의견)*
- **역방향 최적화는 rubric이 직접 벌점을 준다.** "도구·MCP 남발", "교과서 일반론으로 채운 답변", "없는 파일·API를 인용하는 설명"이 미충족 신호다. 산출물 개수를 늘리는 전략은 Probe 단계에서 역효과가 난다.
- **활동량 지표는 직무 적합성과 다르다.** "Discord Top 1%"가 카드에 들어가지만 그것이 FE 역량을 뜻하지는 않는다. 발굴되는 것과 통과하는 것은 별개다 — Sourcer는 문을 열어주고, 통과는 Probe 4축이 정한다.
- **거부 사유가 기록된다는 점은 양면적이다.** 준비되지 않은 상태로 노출을 늘리는 것이 항상 이득은 아니다. *(추정 — 거부 기록의 보존 기간·재평가 정책은 공개되지 않았다)*
- **미검증 전제**: Sourcer의 실제 도입 사례는 확인되지 않았다. 올리브영이 Sourcer도 쓰는지, Probe만 쓰는지는 어느 자료에도 없다. 올리브영 채용 페이지는 **Cofa-Probe만** 언급한다.

## 6. 관찰과 시사점

- **Sourcer와 Probe는 서로 다른 자산을 요구하고, 그 둘이 한 습관에서 나온다.** Sourcer는 *공개된 산출물*을, Probe는 *과정의 규율*을 본다. 그런데 Probe가 채점하는 `i3`(기각한 대안 기록)·`i5`(인수 가능한 의도 문서)와 Sourcer가 블로그에서 읽는 것이 **같은 형태의 문서**다. 결정 로그를 공개적으로 쓰는 습관 하나가 발굴과 통과 양쪽에 걸린다 — 이게 이 조사에서 가장 실용적인 결론이다. *(도출)*
- **크래프톤의 포지션이 게임사를 넘어선다.** Cofa는 자사 채용 문제를 해결한 내부 도구를 외부에 판매하는 형태이고, 올리브영은 그 첫 대형 외부 레퍼런스로 보인다. 크래프톤 정글(교육), Cofa(발굴·평가)로 인재 파이프라인 자체를 제품화하는 흐름으로 읽힌다. *(추정 — 사업 전략에 대한 공식 언급은 확인하지 못했다)*
- **"과정 자동 수집"이 새로운 평가 기반이면, 지원자 준비법도 바뀐다.** 충족/미충족 신호 목록이 사실상 에이전트 코딩 모범 사례 체크리스트다 — 수용 기준을 명시한 프롬프트, 실패→수정→동일 검증 재통과, 기각한 대안의 기록, 세션 인계용 `CLAUDE.md`. 이 저장소가 이미 하고 있는 방식(AGENTS.md 규칙 문서화, thread-state 체크포인트)과 놀랍도록 겹친다.
- **"도구·MCP 남발이 감점"은 반직관적이고 중요하다.** 도구를 많이 붙이는 것이 역량 신호로 읽히지 않는다는 명시적 선언이다.
- **채용 시장 신호로서**: 라이브 코딩 폐지가 대기업 공채에서 실제 집행 단계에 들어섰다. 발표가 아니라 **진행 중인 공고**라는 점이 중요하다.
- **8개 소스 구성이 ML 리서처 기준으로 설계됐다.** arXiv 인용 그래프·특허·연구실 페이지가 절반을 차지한다. 프론트엔드·백엔드 등 제품 엔지니어링 직군은 GitHub·블로그·컨퍼런스·커뮤니티 4개로 좁혀지므로, **직군에 따라 발굴 표면의 넓이가 크게 다르다.** 이 비대칭은 도구의 한계이지 지원자의 문제가 아니다. *(도출)*
- **반입 자산이 감점이 아니라 가점인 구조는 드물다.** 기존 코딩테스트는 외부 자산 반입을 부정행위로 규정하는데, Probe는 `i5`로 별도 채점한다. 다만 채점 대상은 반입 여부가 아니라 *반입한 것을 실제로 써서 판단이 드러나는지*이며, "도구·프롬프트 남발 없음"이 같은 항목의 세부 기준으로 함께 걸려 있다 — 양이 아니라 신호 대 잡음비를 본다.
- **평가 방법이 축마다 분리된 설계가 rubric의 진짜 특징이다.** 기술=산출물/코드, 의도=행동 기록, 인지=사후 Q&A. 산출물만으로는 의도를 알 수 없고 행동 기록만으로는 이해도를 알 수 없다는 전제가 깔려 있다. 의도 축에 항목이 6개(기술 3, 인지 3 대비)라는 배분이 무게중심을 드러낸다.
- **미확인 사항** — 후속 조사가 필요한 지점:
  - Cofa가 크래프톤 사내 조직인지 별도 법인인지 (getcofa.com 푸터는 "© 2026"만 표기)
  - 3축 vs 4축 vs 5축 중 어느 쪽이 현행 기본 rubric인지
  - 지원자가 임의의 외부 MCP 서버를 붙일 수 있는지, 응시 환경의 네트워크 egress 정책
  - 하네스 업로드 허용이 올리브영 채용 과제에도 동일 적용되는지 (행사 안내 문구만 확인됨)
  - 응시 시점 현재의 실제 모델 버전 (데모 영상은 `Opus 4.8` 시점 스냅샷)
  - 올리브영 "3,000만+ 회원" vs "1,600만+ 멤버십" 수치 근거
  - **Sourcer의 실제 도입 사례** — 올리브영이 Sourcer도 쓰는지는 어느 자료에도 없다 (채용 페이지는 Probe만 언급)
  - Sourcer 점수 가중치, "이직 가능성" 추정 방식, 거부 기록의 보존 기간·재평가 정책 (전부 비공개)
  - 커뮤니티 소스(디스코드·슬랙·오픈카톡)를 어떤 방식으로 수집하는지 — "스크래핑 금지 서비스는 사용하지 않는다"는 원칙과의 정합성이 설명되지 않았다
