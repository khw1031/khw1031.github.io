## TL;DR
- AI 에이전트에게 문서는 코드를 대신하는 것이 아니라, 코드베이스를 탐색하도록 돕는 **얇은 맥락 계층**이어야 한다(저자 주장).

## 큰 그림
```
          AI 에이전트의 코드베이스 이해
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
       코드(Code)            문서(Docs)
    ┌────┴────┐          ┌─────┴─────┐
    │ What    │          │ Why       │
    │ How     │          │ Context   │
    └─────────┘          └───────────┘
   Source of Truth       얇은 지식 계층
   실행·테스트 가능      실행 불가·맥락 전용
          │                     │
          └───── 불일치 시 ─────┘
              코드가 우선
```

## 핵심
- Matt Pocock의 핵심 주장은 **코드가 곧 Source of Truth**여야 한다는 것이다. AI 에이전트는 코드를 직접 읽어서 이해할 수 있으므로, 코드를 이해하기 위해 문서를 읽어야 하는 구조는 설계 자체가 좋지 않다고 본다(저자 주장).
- 그 이유는 문서는 **실행할 수도, 테스트할 수도 없기** 때문이다. 시간이 지나면 코드와 문서가 다른 이야기를 하게 되고, 두 개의 상충하는 Source of Truth가 공존하면 AI 에이전트에게는 오히려 혼란만 커진다(저자 주장).
- 그러나 문서를 완전히 없애라는 것이 아니라, **더 높은 수준의 정보**만 남기라고 한다. 남겨야 할 것은 용어집(Glossary), 아키텍처 결정 기록(ADR), 설계 배경, 코드베이스 탐색 가이드다(저자 주장).
- 이를 한 줄로 압축하면 **"What과 How는 코드에, Why와 Context는 문서에"**다(저자 주장).

## 깊이
- **[문서가 초래하는 AI 혼란]** — 원문에 따르면 코드와 문서가 다른 내용을 말하면 AI 에이전트는 두 Source of Truth 사이에서 판단 근거를 잃는다. 이는 인간 개발자가 outdated 문서를 보고 겪는 혼란과 동일한 구조지만, AI는 맥락 추론이 약해 **더 취약**할 수 있다는 점이 저자의 암묵적 전제다(저자 주장, 검증 필요).
- **[문서에 남겨야 할 'Why'의 구체적 예시]** — 원문은 UI 분야 예시를 든다: 초 단위 타임스탬프 표시 이유, 완료 버튼(초록) vs 다음 단계 버튼(파랑) 색상 결정 이유, 두 데이터를 같은 줄에 배치한 이유. 이들은 코드에는 구현돼 있지만 **왜 그렇게 했는지**는 코드만으로는 드러나지 않는 의사결정이다(저자 주장).
- **[얇은 지식 계층이라는 비유]** — 문서를 "에이전트가 코드베이스를 탐색하도록 돕는 얇은 지식 계층"으로 규정한다. 즉 문서는 코드 위에 덧씌우는 두꺼운 설명서가 아니라, 코드로 들어가는 **입구 안내판** 역할이다. 이 비유는 문서량이 적을수록 좋다는 뉘앙스를 주지만, 복잡한 도메인(금융 규제, 의료 등)에서는 얇은 계층만으로 충분한지 불확실하다(비유 한계).

## 용어 풀이
- **Source of Truth** — 단일 진실 공급원. 하나의 권위 있는 원본만 두고 나머지는 그것에 맞추라는 원칙. / 비유: "등대" — 등대가 하나여야 배가 길을 찾듯, 코드 하나가 진실이어야 AI도 길을 잃지 않는다. / 비유가 깨지는 지점: 등대는 고정돼 있지만 코드는 계속 바뀐다. 즉 Source of Truth 자체도 **지속적 관리**가 필요하다.
- **ADR (Architecture Decision Record)** — 아키텍처 결정 기록. 특정 기술·구조를 왜 선택했는지 남기는 짧은 문서. / 비유: "회의록 한 장" — 결정 결과뿐 아니라 대안과 기각 사유까지 적는다. / 비유가 깨지는 지점: 회의록은 일회성이지만 ADR은 코드 수명 동안 **참조**되므로 버전 관리가 필요하다.
- **Glossary (용어집)** — 프로젝트 내부에서만 쓰는 도메인 용어를 정의한 목록. AI 에이전트가 팀 고유의 이름을 코드에서 마주했을 때 맥락을 잃지 않도록 돕는다(저자 주장).

## 시각 자료
| 구분 | 코드(Code)에 남길 것 | 문서(Docs)에 남길 것 |
|------|----------------------|----------------------|
| 내용 | What (무엇을), How (어떻게) | Why (왜), Context (맥락) |
| 예시 | 함수 구현, 타입 정의, API 라우트 | ADR, 용어집, 설계 배경, 탐색 가이드 |
| 특성 | 실행·테스트 가능, 자동 검증 | 실행 불가, 수동 갱신 필요 |
| 노후화 위험 | 낮음 (테스트가 잡아줌) | 높음 (코드 변경 시 방치되기 쉬움) |

## 핵심 시사점 / 판단
- **(저자 주장)** 문서를 지우라는 것이 아니라, 문서의 역할을 **"구현 설명"에서 "맥락 설명"**으로 전환하라는 것이다.
- **(저자 주장)** What/How를 문서에 중복 기술하면 코드 변경 시 동기화 비용이 발생하고, 이는 AI 에이전트에게도 인간에게도 해롭다.
- **(검증 필요·불확실)** AI 에이전트가 코드만 읽고도 충분히 맥락을 추론할 수 있는지는 모델 능력, 코드베이스 크기, 도메인 복잡도에 따라 달라질 수 있다. 원문은 이 조건을 구체화하지 않는다.
- **(원문에 없음)** 문서 삭제 후 AI 에이전트 성능 변화에 대한 실험 데이터나 정량적 근거는 원문에 제시돼 있지 않다.
