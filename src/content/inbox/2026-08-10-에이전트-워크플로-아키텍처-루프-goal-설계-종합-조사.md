# TL;DR

조사 축은 세 갈래다: ① 이 저장소의 기존 노트·캡처(notes 5건, inbox 약 50건, idea·posts 약 10건 전수 훑기), ② 학술 논문(arXiv 원문 1차, 기초 패턴 7편 + 서베이 6편 + 멀티에이전트 6편 + 종료 조건 4편 + 2025–2026 최신 4편), ③ 프로바이더 공식 자료(Anthropic 6편, OpenAI 3편, Google 5편, Microsoft 3편 + 프레임워크·반대 관점 4편). 외부 자료 확인 날짜는 모두 2026-08-10.

핵심 결론 다섯:

1. **어휘는 Anthropic이 정했고 전 진영이 수용했다** — workflow(사전 정의된 코드 경로) vs agent(모델이 스스로 방향을 정하는 루프)의 구분이 OpenAI·Google·Microsoft·LangChain에서 각자의 방식(정의·클래스·추상화 수준·스펙트럼)으로 재현된다.
2. **루프는 배타적 선택지가 아니라 원시 요소의 합성이다** — 실제 오픈소스 코딩 에이전트 13개 중 11개가 ReAct·generate-test-repair·plan-execute·retry·tree search를 섞어 쓴다(소스코드 실측). 기존 노트의 루프 3부작(4분류·4+1 아키텍처·outer loop)은 이 원시 요소들의 **층위**를 가른다.
3. **종료는 프롬프트가 아니라 구조에서 보장해야 한다** — ReAct의 자기 선언식 `finish`에 종료를 맡긴 설계가 6,549개 저장소 정적 분석에서 실제 무한 루프 68건으로 확인됐고, 기존 노트의 eval gate(완료 = SHA 고정 eval 통과 이벤트)와 Anthropic의 JSON 기능 목록(`passes` 필드만 수정 가능)이 같은 답의 두 구현이다.
4. **작업한 주체가 판정하지 않는다** — 기존 노트의 규칙이 2026년 실측으로 뒷받침됐다: 검증기를 답을 생성한 모델로 교체하면 구제 효과가 대부분 사라진다(Leni 분해 연구). 그리고 검증 루프 단독 기여는 +1.5점에 그친다 — 신뢰도의 대부분은 스캐폴딩·라우팅에서 온다.
5. **멀티에이전트는 기본값이 아니라 조건부다** — 여섯 진영이 "단순하게 시작하라"에 수렴하고, 실패 분류 체계(MAST 3범주 14모드)가 문서화됐다. 단 "코딩은 멀티에이전트에 부적합"이라는 2025년 경계는 "검증기가 거의 완벽하고 독립 과업이 풍부하면 성립한다"(Anthropic C 컴파일러, 16 에이전트)로 다시 그어졌다.

## 1. 용어 — workflow vs agent

기준 문서는 Anthropic [Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)(1차, 2024-12)다. **workflow는 "LLM과 도구가 미리 정해진 코드 경로로 오케스트레이션되는 시스템"**, **agent는 "LLM이 자기 프로세스와 도구 사용을 동적으로 지시하며 통제권을 유지하는 시스템"**. 각 진영의 수용 방식:

| 진영 | 수용 방식 |
| --- | --- |
| OpenAI | agent = "독립적으로 과업을 완수하는 시스템". 경계선은 "LLM이 workflow **실행을 제어**하는가" |
| Google ADK | 클래스 선택으로 구현 — `Sequential`/`Parallel`/`Loop` workflow agent vs `LlmAgent` transfer(동적 라우팅) |
| Microsoft | 추상화 수준 차이 — workflow는 agent를 구성요소로 포함하는 사전 정의 연산 시퀀스(상위 비즈니스 프로세스 층) |
| LangChain | 구분을 채택하되 "agent는 이진이 아니라 **스펙트럼**"으로 확장. 대부분의 프로덕션 시스템은 혼합 |

기존 캡처 [에이전틱 워크플로우 그래프](/inbox/2026-07-22-아이디어에서-구현까지-에이전틱-워크플로우-그래프/)가 여기에 두 가지를 보탠다: **"워크플로우를 규정하는 것은 게이트와 역방향 엣지다 — 순방향 노드만으로는 루프/그래프가 아니다"**, 그리고 **"하네스는 단계가 아니라 런타임이다"**(normalpowers 같은 하네스는 파이프라인의 한 공정이 아니라 전체를 실행·기록하는 기반). Microsoft Azure 아키텍처 문서는 방향 양쪽의 안티패턴을 함께 경고한다 — 비결정론적 문제에 결정론적 패턴을 쓰는 것도, 결정론적 문제에 비결정론적 패턴을 쓰는 것도 함정.

## 2. 루프 — 원시 요소, 층위, 실측

### 2.1 원시 요소 (논문 계보)

- **ReAct** ([arXiv 2210.03629](https://arxiv.org/abs/2210.03629), ICLR 2023, 1차) — Thought → Action → Observation 인터리빙. 추론이 계획·예외 처리를, 행동이 외부 지식 접점을 맡는 분업. 종료는 모델이 스스로 내는 `finish` 액션 — 이 자기 선언식 종료가 4절의 2026년 연구들이 문제 삼는 지점이다.
- **Reflexion** ([arXiv 2303.11366](https://arxiv.org/abs/2303.11366), NeurIPS 2023, 1차) — 실패 피드백을 자연어 반성문으로 에피소딕 메모리에 쌓고 다음 시행 프롬프트에 주입. ReAct 에피소드 위에 외부 루프 한 겹을 더 씌우는 구조. 정책 개선의 매개체가 gradient가 아니라 텍스트.
- **Tree of Thoughts** ([arXiv 2305.10601](https://arxiv.org/abs/2305.10601), NeurIPS 2023, 1차) — 추론을 사고 단위 트리 탐색으로 재구성(lookahead·backtracking). 4 구성요소(사고 분해·후보 생성·상태 평가·탐색 알고리즘)가 그대로 설계 체크리스트.
- **Plan-and-Solve** ([arXiv 2305.04091](https://arxiv.org/abs/2305.04091), ACL 2023, 1차) — 계획을 먼저 만들고 실행. plan-execute 제어 구조 계보의 출발점.
- **LATS** ([arXiv 2310.04406](https://arxiv.org/abs/2310.04406), ICML 2024, 1차) — MCTS + ReAct 행동 + self-reflection 통합. ToT와 달리 환경 피드백을 탐색에 끌어들임.
- **Toolformer** ([arXiv 2302.04761](https://arxiv.org/abs/2302.04761), NeurIPS 2023, 1차) — 위와 층이 다르다: 도구 호출을 프롬프트 제어가 아니라 가중치에 심는 학습 방법. "호출이 뒤 토큰의 예측 손실을 낮추는가"로 유용성을 라벨 없이 정의.

### 2.2 실측 — 루프는 합성된다

**Inside the Scaffold** ([arXiv 2604.03515](https://arxiv.org/abs/2604.03515), 2026-04 프리프린트, 1차)가 이 조사에서 설계 논의에 가장 직접 쓸 수 있는 논문이다. 오픈소스 코딩 에이전트 13개의 실제 소스코드를 고정 커밋에서 읽어 3계층 12차원(제어 아키텍처·도구/환경 인터페이스·자원 관리)으로 분류했더니, 관찰된 루프 전략은 **ReAct, generate-test-repair, plan-execute, multi-attempt retry, tree search의 5개 원시 요소**로 정리되고 **13개 중 11개가 여러 원시 요소를 합성**한다. "우리는 ReAct 에이전트다"는 아키텍처 서술로 부족하다는 뜻이다.

### 2.3 층위 (기존 노트의 루프 3부작)

저장소의 캡처 셋이 같은 대상을 다른 층위에서 자른다:

- [Claude Code 팀의 루프 4분류](/inbox/2026-07-08-claude-code-팀이-정의하는-에이전트-루프의-4가지-분류와-설계-가이드/) — Turn-based / Goal-based / Time-based / Proactive. Goal-based의 핵심은 **작업 모델과 evaluator 모델의 분리**(멈추려 할 때마다 평가자가 점검, 미달이면 반려). Proactive는 단일 기능이 아니라 트리거+완료 조건+워크플로의 합성.
- [Loop Engineering의 4+1 아키텍처](/inbox/2026-07-09-loop-engineering-에이전트-루프의-네-가지-아키텍처/) — Execution / Task / Product / System Loop + Oversight Loop. "피드백 없는 루프는 그냥 `for` 문이다." fan-out은 루프가 아니라 **토폴로지**라는 구분, 그리고 "안쪽 루프는 능력이고 바깥쪽 루프는 행위 주체성"이라는 정리.
- [Outer Loop 책임 모델](/inbox/2026-07-10-outer-loop를-소유하라-에이전트-시대의-엔지니어-책임-모델/) — 그 바깥 고리의 인간 책임: Constraints / Sampling / Audit / Ownership. 품질을 "최대 자율성"이 아니라 **back pressure**로 정의. "에이전트는 당신이 리뷰할 수 있는 것보다 더 많이 출하할 수 있다" — 희소 자원은 생성이 아니라 판단.

2.1의 원시 요소는 이 층위 중 맨 안쪽(Execution/Task loop)의 어휘이고, Anthropic Agent SDK 글의 루프 재정의(컨텍스트 수집 → 행동 → 검증 → 반복)도 같은 층이다. 층위를 섞으면 논의가 어긋난다 — 예컨대 Ralph Loop(매 반복 완전히 새 컨텍스트로 재시작하는 "의도적 낭비")는 Execution loop 최적화가 아니라 Task loop 전략이다.

## 3. Goal — 목표는 어디서 오고 어떻게 형식화되는가

**목표의 출처**에 대한 가장 명시적인 학술 어휘는 Liu et al.의 [Agent Design Pattern Catalogue](https://arxiv.org/abs/2405.10467)(JSS 게재, 1차)의 **Passive Goal Creator**(사용자 프롬프트 분석) vs **Proactive Goal Creator**(맥락에서 의도를 선제 예측) 쌍이다. Google [Agents 백서](https://www.kaggle.com/whitepaper-agents)(1차; 본문은 제3자 미러 PDF로 확인했으므로 인용 시 Kaggle 원본 대조 권장)는 goal을 아예 agent 정의에 넣는다 — "적절한 목표 또는 목적이 제공되었을 때" 사람 개입 없이 행동하며, orchestration layer가 profile·goals·instructions를 보유한다.

**목표의 형식화**에서 기존 노트와 외부 사례가 정확히 같은 자리에 도달해 있다:

- 기존 노트 [event-log-gateway-and-eval-gate](/notes/event-log-gateway-and-eval-gate/)는 `goal / task / eval` 삼항이 모든 스케일에서 재귀하고, epic·plan에는 상태 필드가 없으며(상위 완료 = 하위 전부 eval-green), **완료는 특정 git SHA에서 eval이 통과했다는 로그 이벤트**이지 선언이 아니라고 규정한다.
- Anthropic [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)(1차, 2025-11)는 완료 조건을 **200개 이상 항목의 JSON 기능 목록**으로 형식화한다. 각 항목이 상세 단계와 `passes: false`를 갖고, 에이전트는 실제 테스트를 거쳐 **`passes` 필드만** 수정할 수 있으며 기능 삭제·편집은 금지된다. 실패 모드 4개(과욕, **조기 완료 선언**, 진행 기록 부재, 검증 없는 완료 표시)를 initializer/coding agent 2단 구조와 컨텍스트 밖 지속 상태(git 이력 + 진행 파일 + 기능 목록)로 막는다.
- Microsoft의 Magentic 패턴([Azure AI agent design patterns](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns), 1차)은 관리자 에이전트가 목표·하위 목표를 담은 **task ledger**를 만들어 정제하며 "원래 요청이 충족되었는지 아니면 정체되었는지 정기적으로 확인"한다.

**분해(decomposition)** 의 최신 형태는 선형 계획(Plan-and-Solve)에서 **DAG + 맥락 격리**로 옮겨갔다 — Task-Decoupled Planning([arXiv 2601.07577](https://arxiv.org/abs/2601.07577), 2026-01 프리프린트, 1차)은 Supervisor가 하위 목표 DAG를 만들되 핵심은 분해 자체가 아니라 각 하위 태스크의 추론을 scoped context에 가둬 오류 전파를 막는 것이고, 토큰을 최대 82% 줄였다. 기존 캡처 [마일스톤 분해·종료 판정·자율 루프](/inbox/2026-08-06-마일스톤-분해-종료-판정-자율-루프-오케스트레이션/)의 정리가 이 주제의 지도다: **"분해가 루프의 단위를, 종료 판정이 루프의 탈출 조건을, 세션 관리가 루프의 지속 가능성을 정한다. 하나만 갖추면 나머지가 무너진다."**

## 4. 종료 판정 — 2026년에 독립 주제가 됐다

2023–2024년 문헌에서 종료는 대부분 고정 반복 상한으로 처리되고 별도 논의가 없었다. 2026년에 상황이 바뀌었다.

**각 진영의 종료 조건 목록** (공식 문서 기준):

| 출처 | 종료 조건 |
| --- | --- |
| OpenAI Agents SDK | final-output 도구 호출 / 도구 호출 없는 응답 / 핸드오프 / `max_turns` |
| Anthropic | 체크포인트의 사람 피드백 / 막힘 / 최대 반복 횟수 |
| Google ADK `LoopAgent` | `max_iterations` 또는 에이전트가 `escalate=True` 설정(품질 임계값 충족 시 조기 종료) |
| Microsoft | 단일 에이전트에도 반복 한도 필수. 패턴별 대표 실패: Handoff는 무한 핸드오프 루프, Magentic은 정체(stall) |

**2026년 연구 셋**이 이 목록의 한계를 짚는다:

- **IAL-Scan** ([arXiv 2607.01641](https://arxiv.org/abs/2607.01641), 2026-07, 1차; stopping 주제 중 근거 강도 최고) — Infinite Agentic Loop를 "피드백 경로가 유계(bounded)가 아닐 때"로 정의하고 정적 분석(Agent IR + 루프 의존 그래프)으로 검출. 에이전트 저장소 6,549개를 스캔해 47개 프로젝트에서 68건의 실제 무한 루프 확인(정밀도 91.9%). 두 가지 시사: 종료는 프롬프트 수준 `finish` 액션이 아니라 **제어 그래프 수준 유계성**으로 보장해야 하고, 위험한 피드백 경로 일부는 개발자 코드가 아니라 **프레임워크가 암묵적으로 만든다**.
- **Semantic Early-Stopping** ([arXiv 2606.27009](https://arxiv.org/abs/2606.27009), 2026-06, 1차; 단독 저자·60문항 소표본이라 아이디어만 인용 가치) — 연속 초안의 임베딩이 의미상 정체하고 품질 개선도 정체할 때 멈추는 결합 신호. judge 없이 토큰 38% 절감, 품질 동등.
- **LoopTrap** ([arXiv 2605.05846](https://arxiv.org/abs/2605.05846), 원문 미조회 — 인용 전 확인 필요) — 종료 판단 자체가 프롬프트 인젝션의 공격 대상이라는 문제의식(termination poisoning). 우발적 무한 루프(IAL)의 의도적 판본.

OpenAI [GPT-5 prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide)(1차)는 종료를 프롬프트 파라미터로 다루는 반대편 극단이다 — 조기 종료 기준("상위 결과가 한 영역으로 약 70% 수렴"), 고정 도구 호출 예산, persistence 지시("완전히 해결될 때까지 계속하라"), 그리고 **도구별로 다른 정지 임계값**(결제는 쉽게 사람에게 확인, 검색은 거의 묻지 않음, 파일 삭제는 훨씬 낮게). 기존 노트의 답은 구조 쪽이다: [event-log-gateway-and-eval-gate](/notes/event-log-gateway-and-eval-gate/)의 명시적 종료 조건 7개(`eval-green`, `all-evals-green`, `visual-approved`, `spec-complete`, `budget-exhausted`, `user-stop`, `change-request-created`)와 [오답공간 없음 캡처](/inbox/2026-07-10-llm-오답공간-없음-환각의-필연성과-실패-명세-설계/)의 규정 — "성공 경로만 있는 스킬은 미완성"이며 기권·에스컬레이션의 관찰 가능한 조건이 함께 선언돼야 한다.

가장 급진적인 사례는 Anthropic [C 컴파일러 실험](https://www.anthropic.com/engineering/building-c-compiler)(1차, 2026-02)이다 — 종료 조건 없이 `while true`로 2주 넘게 약 2,000 세션을 돌렸고, **테스트 스위트가 목표 명세이자 종료 판정기** 역할을 했다("과업 검증기가 거의 완벽한 것이 중요하다"). 종료 조건이 없어도 되는 게 아니라, 종료 판정이 외부 검증기로 완전히 외화된 경우다.

## 5. 검증 — 작업한 주체가 판정하지 않는다

기존 노트·캡처의 일관된 규칙이 2026년 외부 실측으로 뒷받침됐다.

- 기존 규칙: [마일스톤 분해 캡처](/inbox/2026-08-06-마일스톤-분해-종료-판정-자율-루프-오케스트레이션/)의 공통 결론 "작업한 주체가 판정하지 않는다", [goal-oriented-task-harness-redesign](/notes/goal-oriented-task-harness-redesign/)의 "실패를 확인하지 않은 판정기는 무엇을 판정하는지 알 수 없다"(판정 프로그램은 구현보다 먼저 실패해야 한다), pi-subagents 규약의 "자식이 보고한 성공은 불인정".
- 외부 실측: **Where Does Agent Reliability Come From?** ([arXiv 2607.17044](https://arxiv.org/abs/2607.17044), 2026-07 프리프린트, 1차)이 프로덕션 에이전트의 신뢰도를 분해했다 — 전체 +11.0%p 향상 중 **검증 루프 단독 기여는 +1.5점**이고 대부분은 스캐폴딩·라우팅·전문가 모델에서 왔다. 결정적 ablation: **작은 전용 검증기를 답을 생성한 프론티어 모델로 교체하면 구제 효과가 대부분 사라진다.** Liu 카탈로그가 Self-Reflection과 Cross-Reflection을 굳이 갈라놓은 것이 실측으로 사후 정당화된 셈이다.
- 보조 근거: [환각 눈덩이 캡처](/inbox/2026-07-11-llm-자기회귀-생성의-사전-계획과-환각-눈덩이-효과/) — 같은 문맥 내 intrinsic self-correction은 대체로 실패하고, self-consistency·multiagent debate는 외부 검증자 없으면 25배 비용에도 단일 샘플 대비 개선이 없다. HAL([arXiv 2510.11977](https://arxiv.org/abs/2510.11977), 다기관 21,730 롤아웃, 1차)은 최종 정답률만 보는 평가로는 루프 설계 품질을 알 수 없음을 보였다(로그 검사에서 벤치마크 검색·신용카드 오사용 같은 문제 행동 발견; reasoning effort 증가가 다수 실행에서 정확도를 떨어뜨림).

검증의 **수단** 쪽 어휘는 Anthropic이 정리했다: 규칙 기반(린트·검증 체크) / 시각적 피드백(스크린샷) / LLM-as-judge(견고성 낮고 지연 대가). 그리고 진행 판정의 근거는 일관되게 **환경으로부터의 ground truth**(도구 호출 결과, 코드 실행)다. 기존 캡처 [Boris Cherny 운용 조언](/inbox/2026-07-31-claude-code-창시자의-운용-조언-3가지-지우기-난도-상향-경험주의/)의 정리가 이 축의 요약이다 — **"자율 실행의 길이를 결정하는 것은 모델 지능이 아니라 검증 수단의 유무다."** 과제 설계 3요소(할 일 / 넘지 말 선 / 종료 기준)에 가장 흔히 빠지는 네 번째가 "검증 수단을 모델 손에 쥐어 주기"라는 지적까지 포함해서.

남는 한계는 기존 노트가 스스로 지목한 것이 가장 정직하다 — [goal-oriented-task-harness-redesign](/notes/goal-oriented-task-harness-redesign/)의 닫지 못한 자리 첫째: **"판정이 목표를 실제로 증명하는지는 프로그램으로 검증되지 않는다."** 먼저 실패를 확인하는 규율은 아무것도 판정하지 않는 검사를 잡지만, 엉뚱한 것을 정확히 판정하는 검사는 잡지 못한다.

## 6. 패턴 카탈로그 — 네 카탈로그의 겹침

패턴 이름은 진영마다 다르지만 실체는 크게 겹친다. 대응표:

| 실체 | Anthropic 5패턴 | Google ADK 7패턴 | Microsoft 5패턴 | Liu 18패턴 (학술) |
| --- | --- | --- | --- | --- |
| 순차 연결 | Prompt chaining | Sequential Pipeline | Sequential | Incremental Model Querying |
| 분류 후 분기 | Routing | Coordinator and Dispatcher | — | — |
| 병렬 실행·집계 | Parallelization | Parallel Fan-Out and Gather | Concurrent | Voting-based Cooperation |
| 동적 분해·위임 | Orchestrator-workers | Hierarchical Task Decomposition | Magentic | Role-based Cooperation |
| 생성-평가 루프 | Evaluator-optimizer | Generate and Review / Iterative Refinement | Group Chat (maker-checker) | Self/Cross-Reflection |
| 제어권 이전 | — | (LlmAgent transfer) | Handoff | — |

- Anthropic 5패턴의 원전은 Building Effective Agents. routing과 orchestrator-workers의 차이가 중요하다 — 전자는 분기가 사전에 열거되고, 후자는 분해가 입력에 따라 런타임에 결정된다.
- Liu et al. 카탈로그(1차, 학술지 게재)는 여기에 다른 진영에 없는 범주를 갖고 있다: 목표 생성(Passive/Proactive Goal Creator), 안전·통합·평가(Guardrails, Tool/Agent Registry, Agent Adapter, Agent Evaluator).
- LangGraph 문서(2차)는 Anthropic 5패턴을 실행 가능한 코드로 옮긴 카탈로그다.
- 멀티에이전트의 조율 방식 자체는 논문 계보로: 대화 프로그래밍(AutoGen, [arXiv 2308.08155](https://arxiv.org/abs/2308.08155)), SOP 조립 라인(MetaGPT, [arXiv 2308.00352](https://arxiv.org/abs/2308.00352) — 문제 규정이 "환각의 연쇄"), 역할 대화(CAMEL, [arXiv 2303.17760](https://arxiv.org/abs/2303.17760)), 논쟁 합의(Debate, [arXiv 2305.14325](https://arxiv.org/abs/2305.14325)).

기존 캡처의 실무 패턴이 이 표에 두 개를 보탠다: [advisor 패턴](/inbox/2026-07-08-anthropic-advisor-tool-저비용-executor와-고지능-advisor의/)(저비용 executor + 고지능 advisor 2단 추론)과 [coordinator 패턴](/inbox/2026-07-08-claude-managed-agents-plan-big-execute-small-노트북/)(도구 없는 프론티어 코디네이터 + 값싼 worker). 선택 기준은 [비용 최적화 캡처](/inbox/2026-07-24-anthropic-비용-최적화-패턴과-ai-오케스트레이션-도구-정리/)의 한 줄로 요약된다 — **"작업이 쪼개지지 않으면 advisor, 쪼개지면 orchestrator."** 운영 규율은 "오케스트레이터에 툴을 주지 않는 것", 그리고 두 패턴보다 prompt caching이 먼저라는 기본기 우선 원칙.

## 7. 멀티에이전트 — 논쟁의 현재 위치

**여섯 진영이 시작점에서 같은 말을 한다**: Anthropic("더 단순한 해법이 부족할 때에만"), OpenAI("먼저 단일 agent의 능력을 최대화하라"), Google("단일 agent로 시작"), Microsoft("요구사항을 신뢰성 있게 충족하는 가장 낮은 복잡도"), LangChain(스펙트럼), Cognition(단일 스레드 기본). 멀티에이전트로 넘어갈 근거도 겹친다: 프롬프트 분기 폭발, 도구의 **유사·중복**(OpenAI: 개수가 아니라 유사성이 문제), 컨텍스트 윈도우 초과, 보안 경계, 실제 병렬 이득.

논쟁의 축은 **컨텍스트 공유**다:

- **Cognition** [Don't Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)(1차, 2025-06) — 병렬 서브에이전트가 실패하는 이유는 과업 텍스트를 복사해줘도 그 과업 이해를 형성한 대화 이력과 결정을 복제할 수 없기 때문("행동은 암묵적 결정을 담고 있으며, 상충하는 결정은 나쁜 결과를 낳는다"). 단일 스레드 + 필요시 압축 전용 LLM.
- **Anthropic** [multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)(1차, 2025-06) — orchestrator-workers 프로덕션 사례. 단일 Opus 4 대비 90.2% 우수, 성능 분산의 80%가 토큰 사용량으로 설명. 대가는 일반 챗의 약 15배 토큰. **부적합 영역을 스스로 명시**: 컨텍스트 공유가 필요한 도메인, 의존성 촘촘한 과업, 대부분의 코딩.
- **재반전** — Anthropic C 컴파일러(1차, 2026-02): 중앙 오케스트레이터 없이 파일 락만으로 조정되는 16개 에이전트가 10만 줄 Rust 컴파일러를 완성. 성립 조건이 명시돼 있다: 독립적으로 실패하는 테스트 수백 개(병렬 과업 풍부), 즉각적 성공/실패 신호, 머지 자가 해결. **경계는 "코딩이냐"가 아니라 "검증기가 거의 완벽하고 과업이 독립적이냐"로 다시 그어졌다.**
- **실패의 분류** — MAST([arXiv 2503.13657](https://arxiv.org/abs/2503.13657), 버클리, 1차): 7개 프레임워크 1,600+ 궤적에서 3범주 14 실패 모드(시스템 설계 결함 / 에이전트 간 정합 실패 / 태스크 검증 실패). 멀티에이전트를 채택하기 전에 읽을 문서.

기존 캡처가 이 논쟁에 실무 층을 보탠다: [모노레포 에이전트 팀 캡처](/inbox/2026-07-22-모노레포-에이전트-팀의-서비스-격리와-공통-코드-전략/)의 **"worktree 격리는 파일 충돌만 막는다 — 의미 충돌은 태스크 스코핑과 공통 패키지 직렬화로만 막을 수 있다"**는 Cognition의 "상충하는 암묵적 결정" 문제를 저장소 운영 언어로 옮긴 것이고, coordinator 캡처의 "worker가 읽은 원문 전체가 코디네이터 컨텍스트에 절대 들어가지 않는다는 점이 비용 절감의 전부다"는 Anthropic의 서브에이전트 압축 요약(1,000–2,000 토큰) 원칙과 같은 자리다.

## 8. 기존 노트와 외부 근거가 충돌하는 지점

저장소가 양쪽 근거를 다 갖고 있는 모순 셋 — 결함이 아니라 이 주제의 실제 미결 지점이다.

1. **하네스는 효과가 있나.** [The Harness Effect 캡처](/inbox/2026-07-23-the-harness-effect-에이전트-ai의-토큰-경제학을-결정하는-오케스트레이션-설/)는 모델 고정·하네스 교체만으로 비용 −41%를 실측했다 하고(단 저자 전원이 해당 벤더 직원, 표본 22개), [마일스톤 분해 캡처](/inbox/2026-08-06-마일스톤-분해-종료-판정-자율-루프-오케스트레이션/)의 METR 통제 비교는 전용 하네스가 시간 지평을 크게 늘리지 못했다고 적는다. 화해 지점: **하네스의 이득은 "더 긴 과제 완주"가 아니라 관측 가능성·재개·조기 종결 방지·비용 통제다.** Leni 분해 연구(+11.0%p 중 검증 +1.5점, 나머지가 스캐폴딩·라우팅)는 이 화해를 지지하는 쪽이다.
2. **규칙 파일을 쓰라 vs 다 지우라.** AGENTS.md를 권하는 캡처와 Boris Cherny의 "6개월마다 다 지우고 관측된 반복 실패만 복원"이 맞선다. 실증 판정은 [ai-capability-scoring-axes 노트](/notes/ai-capability-scoring-axes/)에 있다 — 컨텍스트 파일은 평균적으로 과제 성공률을 낮추고 추론 비용을 20% 넘게 올리며, **사람이 쓴 파일만 +4%p**. 판별 질문은 지시 템플릿 캡처의 것: "이 줄을 지우면 모델이 실수하게 되는가?"
3. **사람을 루프에 남길 것인가.** Outer Loop 책임 모델은 인간이 4개 바깥 고리를 소유해야 한다고 하고, 같은 노트의 실증은 사람-AI 조합이 평균적으로 더 나은 단독보다 못했으며(메타분석 g = −0.23) AI가 우위인 결정 과제에서 사람 잔류가 최대 손실이라고 적는다. 기존 노트 [goal-oriented-task-harness-redesign](/notes/goal-oriented-task-harness-redesign/)이 이 긴장의 실제 설계 답이다 — 게이트를 없애지도 강제하지도 않고, **승인 대상을 결과에서 판정기로 옮기고**(마일스톤당 1회, 착수 직전) 시점 선택권을 사용자에게 준다. OpenAI(고위험·비가역 행동만 사람 트리거)와 Microsoft(HITL 게이트를 출력 전체가 아니라 특정 도구 호출로 좁혀라)의 지침도 같은 방향 — 사람 게이트의 **개수를 줄이고 위치를 옮기는** 쪽으로 수렴 중이다.
