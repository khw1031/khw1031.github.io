## TL;DR
- Claude Code에서 한글이 깨지는 원인은 인프라가 아닌 모델이 `\uXXXX` hex 번호를 받아쓰다 한 자리를 틀리는 습관이며, 지시문 한 줄로 해결 가능하다.

## 큰 그림

```
Claude Code 한글 손상 문제
│
├─ 증상 ───────── "로그인"→"로까잉", "잘못"→"잡모" (에러 없이 유효 글자)
│
├─ 진짜 원인 ──── 모델이 tool call JSON 한글을 \uXXXX escape로 표기
│                 → hex 한 자리 오기 → 한글 연속 배치라 옆 글자로 치환
│
├─ 기각된 가설 ── (1) 컨텍스트 길이(0~80%) 무관
│                 (2) Bedrock 전용 아님 (1P/3P 동일)
│
├─ 재현 실험 ──── 번호 표기 유도군: 45/45(100%) 손상
│                 글자 그대로 유도군: 1/60(1.7%) 손상
│                 AWS 계정 2개 × Claude Enterprise / Bedrock 동일 재현
│
└─ 해결 ───────── CLAUDE.md에 "비ASCII는 UTF-8 리터럴, \uXXXX 금지" 추가
                  → 번호 받아쓰기 차단 → 증상 완전 소실
```

## 핵심
- **증상의 이례성**: 깨진 기호(``)나 에러가 아니라 "잡모", "완릷"처럼 *유효한 다른 한글*로 출력된다. 이는 단순 인코딩 문제가 아니라 모델 내부 표기 방식에서 기인한다는 단서다. 이 단서를 따라가면 원인은 인프라가 아니라 **모델의 출력 습관**으로 좁혀진다.
- **메커니즘 연결**: 모델이 tool call JSON의 한글을 글자 그대로가 아닌 `\uXXXX` 유니코드 escape로 "받아쓰기"할 때가 있다. 한글 11,172자는 Unicode 상에 빈틈없이 연속 배치되어 있으므로, hex 번호 한 자리만 틀려도 JSON 파서는 에러를 내지 않고 **인접한 유효 글자**로 해석한다. 즉 `\uc798\ubabb`("잘못")을 쓰려다 `\uc7a1\ubaa8`로 오기하면 그대로 "잡모"가 되는 구조다. 에러가 없는 것이 오히려 발견을 늦추는 함정이다.
- **가설 검증 → 해결**: 초기 두 가설(컨텍스트 길이, Bedrock 전용)은 통제 실험에서 모두 기각됐다. 재현 시험에서 번호 표기를 유도한 그룹은 100% 손상, 글자 그대로 쓰게 한 그룹은 1.7% 손상에 그쳐 **escape 표기 자체**가 원인임을 확증했다. 따라서 해결은 자연스럽게 "escape로 쓰지 않게 막기"—즉 `CLAUDE.md`에 UTF-8 리터럴 지시문 한 줄을 추가하는 것으로 귀결된다.

## 깊이
- **[메커니즘-연속 배치]** 한글은 Unicode U+AC00~U+D7A3에 11,172자가 *빈칸 없이* 나열돼 있다. 이는 비유하면 "번지수가 틀리면 옆집으로 배달되는 아파트"와 같다. 알파벳은 번지 사이가 띄엄띄엄이라 잘못된 hex가 대체로 invalid character 에러를 내지만, 한글·CJK는 옆 유효 글자로 조용히 치환된다. **비유가 깨지는 지점**: 실제 메모리 주소와 달리 Unicode는 논리 매핑이므로 "물리적 인접"의 의미는 없다. 다만 코드포인트 순서가 연속이라는 점이 기능적으로 동일 효과를 낸다.
- **[실험-통제군 설계]** 저자는 동일 과제를 두 그룹으로 나눠 한쪽은 번호 표기를 유도, 다른 쪽은 글자 그대로 쓰도록 유도했다. 45건 vs 60건 표본에 100% vs 1.7%라는 극단적 차이는 escape 표기가 *충분조건*에 가까움을 시사한다. AWS 계정 두 개, 1P/3P 인프라에서 동일 재현되어 특정 환경 종속성이 아님도 확인. **원문에 없는 사항**: 실험 프롬프트 구체 내용, 온도(temperature) 설정, 모델 버전별 상세 비교 표.
- **[해결-지시문의 원리]** "비ASCII는 UTF-8 리터럴로, `\uXXXX` 금지" 지시는 모델의 출력 *공간 자체*를 제한한다. 번호 받아쓰기 경로를 차단하면 오기 기회도 사라진다. 적용 후 증상이 "완전히 사라졌다"고 저자 주장. CJK 전반(일본어·중국어)에도 동일 패턴이 적용된다고 본다.

## 용어 풀이
- **`\uXXXX` 유니코드 이스케이프** — JSON 등에서 문자를 16진수 코드포인트로 표기하는 방식. / 비유: 글자를 "이름" 대신 "주민번호"로 부르는 것. / 비유가 깨지는 지점: 실제 주민번호와 달리 Unicode는 체계적 규칙(한글은 조합형 공식)으로 생성된다.
- **Tool call (function calling)** — LLM이 외부 도구를 호출할 때 구조화된 JSON 파라미터를 반환하는 행위. / 비유: AI가 "전화 걸기" 버튼 대신 전화번호(JSON)를 직접 다이얼에 입력하는 것. / 비유가 깨지는 지점: 사람과 달리 모델은 이 번호를 hex로 "받아쓰기"할 수 있다.
- **CJK 출력 무결성** — 중국어·일본어·한국어 출력이 원문 그대로 보존되는 성질. / 비유: 우편물이 주소 그대로 도착하는 것. / 비유가 깨지는 지점: CJK는 코드포인트 밀도가 높아 손상 시 "유효한 오배달"이 되어 감지가 더 어렵다.

## 시각 자료

| 구분 | 손상률 | 표본 | 비고 |
|------|--------|------|------|
| `\uXXXX` 번호 표기 유도 | 100% (45/45) | 45건 | escape가 직접 원인 |
| 글자 그대로(리터럴) 유도 | 1.7% (1/60) | 60건 | 통제군 |
| 인프라 비교 | 차이 없음 | — | 1P/3P, AWS 계정 2개 |
| 컨텍스트 사용률 | 차이 없음 | — | 0~80% 구간 |

| 오기 예시 | 의도 | 실제 출력 | Hex 변화 |
|-----------|------|-----------|----------|
| 잘못 | `uc798 ubabb` | 잡모 (`uc7a1 ubaa8`) | 각 자리 1~2칸 이동 |
| 로그인 | 원문 | 로까잉 | — (원문에 hex 미상세) |

## 핵심 시사점 / 판단
- **(저자 주장)** CJK 출력 무결성은 "nice-to-have"가 아닌 **릴리스 게이트(release QA gate)** 항목이어야 한다. 한국은 Claude Code 최상위권 유료 시장임에도 Sonnet 5 → Opus 5 출시 동안 이 문제가 걸러지지 않았다.
- **(저자 주장)** 영어 벤치마크는 소수점까지 경쟁하면서 CJK 문자 체계 손상 테스트가 출시 QA에 없었다는 뜻이다.
- **(검증 필요·불확실)** "Opus 5에서도 종종 등장"의 빈도·재현률은 원문에 수치 미상. Sonnet 5 대비 정량 비교 없음.
- **(검증 필요·불확실)** 적용 지시문이 모든 워크플로우·모델 버전에서 안정적으로 유효한지, 장기적 회귀 가능성은 원문에 미상.
- **(사실)** 저자는 Anthropic Claude Code 저장소에 Issue #83033으로 공식 등록 완료.
