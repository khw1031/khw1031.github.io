## TL;DR
- "확인 → 실행"을 분리하면 동시 요청이 같은 상태를 동시에 읽어 제한을 초과 발급하는 **TOCTOU** 버그가 발생하며, 확인과 실행을 하나의 원자 연산으로 묶어야 해결된다.

## 큰 그림

```
[쿠폰 이벤트 장애 시나리오]

  요청A ─┐                    ┌─ "99장" 읽기 ─→ 통과 ─→ 발급(100번째)
  요청B ─┼─ 동시에 도착 ──────┼─ "99장" 읽기 ─→ 통과 ─→ 발급(101번째) ← 초과!
  요청C ─┘                    └─ "99장" 읽기 ─→ 통과 ─→ 발급(102번째) ← 초과!

  원인: TOCTOU (Time-of-Check ≠ Time-of-Use)
        ┌──────────┐   gap   ┌──────────┐
        │  Check   │ ──────→ │   Use    │
        │(count=99)│  ←틈→  │(issue()) │  ← 이 틈에 다른 요청이 끼어듦
        └──────────┘         └──────────┘

  해결: 원자 연산으로 통합
        ┌─────────────────────────────────┐
        │ UPDATE ... WHERE remaining > 0  │
        │  → 성공 여부로 발급 결정         │
        └─────────────────────────────────┘
```

## 핵심
- 저자 주장에 따르면, 선착순 100장 쿠폰 이벤트에서 103장이 발급된 사고가 발생했다. 로그와 코드는 모두 정상이었고, `countIssued() < 100` 검사 뒤 `issue()`를 호출하는 로직도 규칙대로 동작했다. 문제는 **코드가 아니라 동시성**에 있었다.
- 밀리초 단위로 분석하면 마지막 순간 여러 요청이 동시에 "현재 99장"을 읽었고, 모두가 조건을 통과했다. 확인하는 순간에는 실제로 99장이었기 때문이다. 이것이 **TOCTOU**(Time-of-Check to Time-of-Use) 패턴의 전형적 발현이다.
- 확인(check)과 실행(use) 사이에 상태 변경이 끼어들 수 있는 틈이 존재하며, 동시성이 있는 환경이라면 이 틈은 언제든 열릴 수 있다.

## 깊이
- **왜 일반 테스트는 못 잡았나** — (저자 주장) 일반적인 테스트는 요청을 순차적으로 실행하므로 TOCTOU가 드러나지 않는다. 이 버그는 트래픽이 순간적으로 몰리는 상황(쿠폰 이벤트, 티켓팅)에서만 모습을 드러낸다. 200개 요청을 동시에 발생시키고 정확히 100장만 발급되는지 검증하는 **동시성 테스트**가 필요하다.
- **해결책: 원자 연산** — (저자 주장) `SELECT` 후 `INSERT`하는 대신, `UPDATE coupon_stock SET remaining = remaining - 1 WHERE event_id = ? AND remaining > 0`처럼 DB의 행 잠금(row-level lock)을 활용한 조건부 차감 하나로 확인과 실행을 합친다. UPDATE 성공 여부가 곧 발급 자격이다.
- **TOCTOU의 다른 출현처** — (저자 주장) 파일(존재 확인 → 열기 사이 삭제), 권한(확인 → 실행 사이 회수), 외부 API(잔액 확인 → 결제 사이 차감), 캐시(미스 확인 → 생성 사이 중복 생성) 등 "확인 → 신뢰 → 실행" 패턴이 존재하는 모든 곳에서 발생할 수 있다.

## 용어 풀이
- **TOCTOU** — "검사 시점과 사용 시점 사이의 괴리". 비유: 냉장고에 우유가 있는 것을 확인하고 돌아오는 사이에 가족이 마셔버리는 상황. 비유가 깨지는 지점: 실제 시스템에서는 이 "사이"가 나노초~밀리초 단위이며, 의도적 동시 접근이 반복적으로 발생한다.
- **원자적 연산 (atomic operation)** — "더 이상 쪼개지지 않는 하나의 작업 단위". 비유: 은행 창구에서 입금과 출금을 한 번의 호출로 처리하는 것. 비유가 깨지는 지점: DB에서는 `UPDATE ... WHERE`가 원자적이지만, 애플리케이션 레벨의 여러 단계를 묶는 것은 별도 메커니즘(트랜잭션, 분산 락 등)이 필요하다.
- **동시성 (concurrency)** — "여러 작업이 겹쳐 실행되는 상태". 비유: 여러 사람이 동시에 같은 화장실 문을 두드리는 상황. 비유가 깨지는 지점: 병렬성(parallelism)과 혼동되기 쉬우나, 동시성은 구조적 겹침이고 병렬성은 물리적 동시 실행이다.

## 시각 자료

| 영역 | Check (확인) | Use (실행) | 틈의 위험 |
|---|---|---|---|
| DB 재고 | `count < 100` | `issue()` | 동시 통과 → 초과 발급 |
| 파일 시스템 | 파일 존재 확인 | 파일 열기 | 확인 후 삭제됨 |
| 권한 검사 | 권한 있음 확인 | 리소스 접근 | 사이에 권한 회수 |
| 외부 API | 잔액 확인 | 결제 요청 | 사이에 잔액 소진 |
| 캐시 | 캐시 미스 확인 | 캐시 생성 | 동시 미스 → 중복 생성 |

## 핵심 시사점 / 판단
- (저자 주장) 코드 리뷰 시 "확인 → 신뢰 → 실행" 패턴이 보이면 경고등을 켜야 한다. 동시성이 있는 환경에서는 이 구조 자체가 잠재적 버그다.
- (저자 주장) 순차 테스트만으로는 동시성 버그를 잡을 수 없으므로, 이벤트·티케팅 등 트래픽 급증이 예상되는 기능에는 반드시 동시성 부하 테스트를 설계해야 한다.
- (검증 필요·불확실) 원자 연산으로 `UPDATE ... WHERE`를 사용하면 모든 시나리오에서 해결되는지, 혹은 분산 환경(여러 DB 인스턴스, 마이크로서비스)에서는 추가 메커니즘이 필요한지에 대한 논의는 원문에 없다.
