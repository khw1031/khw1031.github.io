**최상위:** LLM은 한 번의 호출만으로 필요한 정보를 모두 알거나 행동하고 자신을 검증할 수 없다. 에이전트는 탐색·도구 실행·검증을 반복하고, 시스템은 컨텍스트와 정책을 관리해 이 반복을 통제한다.

## 먼저 보는 흐름

```text
LLM을 한 번 호출
→ 필요한 정보가 부족하고, 텍스트 밖의 행동을 할 수 없으며, 결과를 스스로 믿기 어려움
→ 필요한 정보를 찾고 도구를 실행하는 에이전트 루프로 확장
→ 대화와 도구 결과가 쌓이므로 컨텍스트를 정리
→ 테스트·권한 정책·훅으로 결과와 행동을 검사
```

이 문서에서 자주 쓰는 용어는 다음 뜻이다.

- **워크플로우(`workflow`):** 코드가 실행 순서와 분기를 미리 정한 구조
- **에이전트(`agent`):** 모델이 현재 상태를 보고 다음 행동·도구·종료 시점을 고르는 구조
- **하네스(`harness`):** 모델 밖에서 도구, 컨텍스트, 권한, 실행 순서를 연결하고 관리하는 시스템
- **검증기(`verifier`):** 테스트나 정답 비교처럼 결과의 통과 여부를 기계적으로 판정하는 장치
- **RLVR:** 검증기가 맞다고 판정한 결과에 보상을 주어 모델을 학습시키는 방법

## 전체 피라미드

*(현재 수록분 기반 — 강의 자료가 추가될 때 갱신)*

- **핵심:** LLM의 한계를 에이전트 루프로 보완하고, 그 루프가 헤매거나 위험하게 행동하지 않도록 컨텍스트와 검증 절차를 함께 설계해야 한다.
  - **근거 ① 왜 한 번의 호출로 부족한가:** 모델은 학습한 지식과 주어진 컨텍스트만 알며, 필요한 정보를 스스로 추가하거나 파일 수정 같은 행동을 할 수 없다. 프롬프트만으로 오류와 보안 문제를 항상 막기도 어렵다.
  - **근거 ② 에이전트는 어떻게 이 한계를 보완하는가:** 모델이 필요한 정보를 찾고 도구를 실행한 뒤 결과를 보고 다음 행동을 정하는 과정을 반복한다. 턴·이터레이션·세션은 이 반복과 컨텍스트의 수명을 구분하고, 도구·대기열·훅은 모델이 할 수 있는 행동과 시스템의 개입 지점을 정한다.
  - **근거 ③ 코딩 에이전트는 무엇을 모델과 코드에 맡기는가:** 탐색과 수정처럼 미리 모든 경우를 정하기 어려운 일은 모델에 맡긴다. 빌드·테스트·권한처럼 같은 기준이 매번 적용되어야 하는 일은 코드에 고정한다. 이 문서의 적용 해석이다.
  - **근거 ④ 왜 긴 대화에서 에이전트가 헤매는가:** 컨텍스트에 모순, 중복, 비슷하지만 다른 정보가 쌓이면 중요한 내용을 고르기 어려워진다. 오래된 내용 일부를 자르는 것만으로는 부족하며, 필요한 내용만 다시 정리하거나 깨끗한 컨텍스트에서 재시작해야 한다.
  - **근거 ⑤ 같은 검증 원리가 학습에는 어떻게 쓰이는가:** RLVR은 검증기를 통과한 풀이에 보상을 주고, 통과한 풀이를 다음 학습 데이터로도 사용한다. 다만 검증기가 틀린 답을 통과시키거나 비슷한 풀이만 남기면 학습이 오염될 수 있고, 정답이지만 사람이 읽기 어려운 추론이 늘어날 수도 있다.

## 장별 기록

### 0. 에이전틱 코딩 에이전트와의 연결 ‹2026-08-11›

**핵심:** 코딩 에이전트는 LLM에게 모든 제어권을 넘긴 시스템이 아니다. 모델은 탐색과 수정을 선택하고, 코드는 권한과 검증 절차를 강제하며, 하네스는 컨텍스트를 관리한다.

이 절은 강의 슬라이드 자체가 아니라, 슬라이드 1~9를 코딩 에이전트 설계에 적용한 해석이다.

1. **단일 호출의 네 가지 한계가 에이전트의 네 부품으로 바뀐다.**

   - 지식이 부족함 → 코드베이스를 탐색한다.
   - 한 프롬프트에 모든 정보를 담을 수 없음 → 필요한 정보를 반복해서 가져온다.
   - 텍스트 밖에서 행동할 수 없음 → 파일 편집·명령 실행 도구를 사용한다.
   - 결과를 믿기 어려움 → 테스트와 권한 정책으로 검사한다.

   한마디로 정리하면 다음과 같다.

   ```text
   탐색 → 판단 → 행동 → 검증 → 필요하면 다시 탐색
   ```

2. **모델과 코드가 서로 다른 종류의 제어를 맡는다.**

   | 맡는 주체 | 적합한 일 |
   | --- | --- |
   | 모델 | 무엇을 읽을지, 어떤 원인부터 조사할지, 어떤 수정을 시도할지 |
   | 코드 | 권한 검사, `typecheck`, 빌드, 테스트, 배포 조건 |
   | 사람 | 요구사항의 뜻, 설계 적절성, 보안처럼 자동 판정하기 어려운 판단 |

   **“가능한 분기를 미리 열거할 수 있는가?”**는 유용한 출발점이지만, 경우의 수만으로 둘을 구분하기에는 부족하다. 더 본질적인 질문은 **“이 결정을 사전에 명확하고 안정적인 규칙으로 고정할 수 있는가?”**이다.

   - 판단 기준이 명확하고 매번 같은 결과가 필요하다 → 코드에 고정
   - 상황의 의미를 해석해야 하고 판단 기준을 미리 완전히 쓰기 어렵다 → 모델이 실행 중 판단

   실무에서는 이를 **“일관성이 중요한 규칙은 코드에 맡기고, 상황 해석이 필요한 판단은 모델에 맡긴다”**로 기억할 수 있다. 다만 모델이 판단하는 영역에서도 허용되는 행동의 범위와 결과 검증은 코드가 맡아야 한다.

   따라서 현실적인 코딩 에이전트는 `agent`와 `workflow`의 혼합이다.

3. **에이전트의 시간과 컨텍스트는 서로 다른 세 단위로 나뉜다.**

   ```text
   세션
   ├─ 턴: 요청 하나부터 최종 응답까지
   │  ├─ 이터레이션: 읽기 → 결과 확인 → 판단
   │  └─ 이터레이션: 수정 → 테스트 → 판단
   └─ 다음 턴
   ```

   중요한 차이는 **턴 종료가 작업 완료를 뜻하지 않는다는 것**이다. 모델이 최종 응답을 만들면 턴은 끝나지만, 작업 완료는 테스트 같은 외부 검증기가 판정해야 한다.

4. **하네스의 중요한 역할은 컨텍스트 관리다.**

   코딩 에이전트에서는 파일 전문, 빌드 출력, 테스트 로그가 컨텍스트를 빠르게 채운다. 그래서 성능은 무엇을 읽느냐뿐 아니라 **무엇을 남기고 무엇을 버리느냐**에도 달려 있다.

   - 필요한 범위만 읽기
   - 검색으로 후보를 좁힌 뒤 읽기
   - 큰 출력은 파일에 두고 요약만 남기기
   - 별도 작업은 서브에이전트의 분리된 컨텍스트에서 처리하기
   - 다음 세션에 필요한 상태는 대화가 아니라 파일로 남기기

   이 관점에서 서브에이전트는 단순한 능력 확장보다 **컨텍스트 격리 장치**에 가깝다.

5. **가드레일은 지시문이 아니라 실행되는 정책이어야 한다.**

   “비밀 파일을 수정하지 마”라고 프롬프트에 쓰는 것만으로는 매번 적용된다고 보장할 수 없다. 실제 권한 검사나 훅이 해당 작업을 차단해야 한다.

   마찬가지로 Goal의 자가평가는 작업을 계속할지 판단하는 트리거로는 쓸 수 있지만, 완료의 증거가 될 수는 없다. 모델이 자신에게 점수를 주는 구조이기 때문이다.

전체 구조를 한 줄로 압축하면 다음과 같다.

```text
코딩 에이전트
= 모델이 선택하는 탐색·수정
+ 코드가 강제하는 권한·검증
+ 하네스가 관리하는 컨텍스트
```
