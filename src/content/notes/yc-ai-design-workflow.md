**최상위:** 생성이 쉬워진 AI 디자인의 병목은 좋은 후보를 고르고, 그 판단을 다음 생성이 실행할 조건으로 바꾸는 평가 능력이다.

## 전체 피라미드

- **핵심:** 생성이 쉬워진 AI 디자인의 병목은 좋은 후보를 고르고, 그 판단을 다음 생성이 실행할 조건으로 바꾸는 평가 능력이다.
  - **방향과 비교 조건:** 무드보드와 `soul.md`로 방향을 고정하고, 같은 목표·규칙·화면 상태에서 만든 후보를 비교한다.
  - **이유 확인:** 선택과 이유의 명료함을 구분한다. 이유가 바로 나오지 않으면 질답과 가설 확인을 거치고, 확인되지 않은 에이전트 분석은 사람의 이유와 분리한다.
  - **판단 전달:** 확인된 선택 이유를 **유지·수정·회피**로 나눠 다음 후보가 실행할 생성 조건으로 바꾼다.
  - **수렴 판별:** 이전 장점과 비교 조건을 유지하면서 문제 목록이 줄어들어야 개선이다. 그렇지 않으면 정체·후퇴·표류로 구분한다.
  - **규범화 경계:** 후보를 선택하는 것과 그 특징을 디자인 원칙으로 채택하는 것은 다르다. 원칙과 적용 범위는 사람이 별도로 승인한다.
  - **자동화의 경계:** 쌍대 비교 자료로 선호 예측을 도울 수는 있지만, 기계적으로 확인할 정답이 부족해 좋은 디자인의 최종 평가는 사람에게 남는다.

## 장별 기록

### 1. 핵심 ‹2026-08-12›

- **핵심:** AI 디자인 워크플로우는 AI에게 한 번 잘 만들어 달라고 요청하는 방법이 아니라, 방향을 고정하고 여러 후보를 만든 뒤 사람이 선별한 결과로 탐색 범위를 좁혀 가는 반복 절차다.
  - **방향 고정:** 무드보드와 효과는 원하는 시각적 분위기를 정하고, `soul.md`는 사용자·제품 철학·주고 싶은 경험을 문서로 고정한다. 생성할 때마다 목적이 흔들리지 않게 만드는 기준이다.
  - **후보 비교:** AI에게 시안 여러 개를 만들게 하고, 모델 이름을 가린 채 A·B·C로 비교한다. 첫 결과에 만족하거나 모델의 명성에 끌리지 않고 결과 자체를 선별하기 위한 장치다.
  - **반복 개선:** 선택한 후보의 유지·수정·회피 요소를 다음 라운드에 넣는다. 이 과정은 좋은 요소를 한 번에 찾아내기보다 좋지 않은 요소를 하나씩 제거하는 방식으로 수렴한다.

절차를 한 줄로 줄이면 다음과 같다.

```text
방향 고정 → 후보 여러 개 생성 → 블라인드 비교 → 판단 전달 → 다시 생성
```

여기서 역할은 다음과 같이 구분된다.

- AI: 후보를 싸고 빠르게 많이 생성
- 사람: 후보를 비교하고 다음 라운드의 방향을 결정
- 랭킹 시스템: 선택과 판단 근거를 모아 다음 라운드로 연결

따라서 원문의 “선별이 능력이다”는 단순히 안목이 좋다는 말보다 넓다. **좋은 것을 알아보고, 왜 좋은지 구분하고, 그 판단을 다음 생성 조건으로 바꾸는 능력**을 뜻한다.

### 2. 깊이 ‹2026-08-12›

- **핵심:** AI는 디자인 후보를 만들 수 있지만, 무엇이 더 좋은지 평가하는 일은 아직 사람에게 남아 있다.
  - 코딩·수학과 달리 디자인에는 기계적으로 확인할 정답이 부족해 평가 자동화가 어렵다.
  - A/B 선택 자료가 쌓이면 선호를 예측할 수는 있지만, 이것이 좋은 디자인의 객관적 판정인지는 미해결이다.
  - 현재 워크플로우의 병목은 사람이 선택 이유를 말로 표현해 다음 라운드에 전달하는 능력이다.
  - 시안이 인터랙티브 페이지로 바뀌면서 디자이너의 역할은 구현까지 넓어졌다.
  - 다만 화자 한 명의 단기 실험이므로 결과를 일반화하기는 어렵다.

### 3. 핵심 시사점 / 판단 ‹2026-08-12›

- **핵심:** 이 워크플로우의 가치는 AI가 디자인하는 데 있지 않고, 사람의 비교와 판단을 반복 가능한 평가 과정으로 만든 데 있다.
  - 공개 도구만으로 `후보 생성 → 비교 → 재생성` 루프를 구성할 수 있다.
  - 랭킹 UI는 사람의 선택과 이유를 모아 다음 라운드 입력으로 바꾸는 장치다.
  - 생성이 쉬워질수록 병목은 후보 제작에서 선별과 평가로 이동한다.
  - 평가 코멘트는 모델을 실제로 재학습시키는 자료라기보다 다음 생성에 넣는 피드백 문맥이다.
  - 평가 자동화 가능성과 다른 작업으로의 일반화 여부는 아직 확인되지 않았다.

한 사람이 한 번 재현했다는 사실만으로 일반적인 재현 가능성이 입증되지는 않는다. 또한 “랭킹 UI가 가장 저평가됐다”는 표현은 사실이라기보다 화자의 판단으로 봐야 한다.

## 응용 — 선별 결과가 디자인 규범이 되는 과정

사람의 판단을 다음 라운드에 전달하려면 평가 코멘트를 다시 넣는 것만으로는 부족하다. 후보를 살펴본 기록과 앞으로 따라야 할 디자인 원칙을 구분해야 한다.

```text
후보 비교와 근거 기록 → 사람이 기준 후보를 채택 → 승인된 디자인 원칙에 반영
```

- **탐색 기록:** 만들어 본 후보, 후보끼리 비교한 결과, 선택 이유를 보관하는 영역이다. 아직 프로젝트가 따라야 할 공식 기준은 아니다.
- **사람의 채택:** 점수나 모델의 추천은 후보를 좁히는 참고 자료일 뿐이다. 어떤 후보를 다음 기준으로 삼을지는 사람이 이유와 함께 결정한다.
- **디자인 원칙 반영:** 후보를 골랐다고 그 특징이 곧바로 영구 규칙이 되지는 않는다. 앞으로 유지할 원칙을 사람이 따로 검토하고 승인해야 한다.
- **다음 라운드 연결:** 승인된 결정이 기록된 뒤에만 채택한 후보와 원칙을 다음 라운드의 출발점으로 사용한다.

따라서 평가를 보존하는 일과 평가를 규칙으로 채택하는 일은 다르다. 한 번 선호한 후보나 반복된 코멘트도 사람이 적용 범위를 승인하기 전에는 현재 프로젝트의 원칙이나 여러 프로젝트에 적용할 기본 취향이 되지 않는다.

### 비교가 성립하는 조건

후보를 공정하게 비교하려면 모델 이름을 가리는 것뿐 아니라 생성 조건도 같아야 한다.

- 해결하려는 사용자 문제와 목표
- 평가에 사용할 기준
- 출발점으로 삼은 기존 디자인
- 색상·간격·컴포넌트처럼 지켜야 할 디자인 규칙
- 화면 크기, 실제 콘텐츠, 오류·빈 화면 같은 비교 상태

조건이 다르면 어느 후보가 더 나은지 바로 순위를 매기지 않고, 조건을 맞추거나 별도 라운드로 나눠야 한다.

비교 결과도 반드시 승자와 패자로 나눌 필요는 없다. 두 후보가 비슷하거나, 둘 다 기준에 못 미치거나, 판단할 정보가 부족하다는 결과를 그대로 남겨야 한다.

따라서 좋은 비교 과정은 순위만 저장하는 것이 아니라 **어떤 공통 조건에서 무엇을 비교했는지 함께 보존하는 과정**이다.

## 응용 — 선택 이유가 바로 나오지 않을 때

- **핵심:** 무엇을 선택할지는 분명하지만 그 이유를 바로 설명하지 못할 수 있다. 따라서 선택 결과와 이유의 확인 상태를 따로 다뤄야 한다.
  - 먼저 선택한 후보가 나은 점과 다른 후보를 선택하지 않은 이유를 묻는다.
  - 답하기 어렵다면 에이전트의 해석을 먼저 주입하지 않고, 눈에 먼저 들어온 부분이나 불편했던 요소처럼 답을 유도하지 않는 질문으로 이유를 함께 찾는다.
  - 그래도 설명되지 않으면 에이전트가 후보 사이의 차이를 몇 가지 가설로 제안하고 사용자가 맞는지 확인한다.
  - 사용자가 확인한 가설만 선택 이유로 기록한다. 확인되지 않은 분석은 사람의 이유와 분리해 남긴다.
  - 이유가 끝내 불명확해도 선택 자체를 무효로 만들지는 않는다. 다만 그 선택에서 디자인 원칙이나 장기적인 취향을 자동으로 추출하지 않는다.

한 줄로 줄이면 다음과 같다.

```text
선택 → 이유 질문 → 함께 탐색 → 가설 확인 → 확인된 이유와 미확인 분석 분리
```

## 응용 — 선택 이유를 다음 생성 조건으로 바꾸기

- **핵심:** 선택 이유는 과거 후보에 대한 감상이므로, 그대로 반복하기보다 다음 후보가 실행할 수 있는 조건으로 바꿔야 한다.
  - **유지:** 선택한 후보에서 효과가 있었으며 다음 후보에서도 잃지 말아야 할 요소
  - **수정:** 선택한 후보에도 남아 있어 다음 라운드에서 개선해야 할 문제
  - **회피:** 선택하지 않은 후보에서 드러났으며 다시 만들지 말아야 할 요소

예를 들어 “B가 더 한눈에 들어오고 A는 부가 기능이 너무 튄다”는 이유는 다음처럼 바뀐다.

```text
유지: 주요 상태와 부가 기능 사이의 시각적 계층
수정: 주요 상태를 더 빠르게 구분할 수 있도록 차이를 강화
회피: 부가 기능이 주요 상태와 같은 강도로 보이는 구성
```

여기서 중요한 것은 색상이나 위치를 그대로 복제하는 것이 아니라, **그 표현이 해결했던 관계와 사용자 작업을 조건으로 남기는 것**이다. 그래야 다음 후보가 다른 형태를 시도하면서도 선택의 핵심은 이어갈 수 있다.

이유의 확인 상태도 변환 범위를 제한한다.

- 사람이 직접 말했거나 확인한 이유: 유지·수정·회피 조건의 근거로 사용
- 확인되지 않은 에이전트 분석: 다음 후보에서 시험할 가설로만 사용
- 끝내 이유를 찾지 못한 선택: 기준 후보는 바꿀 수 있지만 새로운 디자인 원칙은 만들지 않음

한 줄로 줄이면 다음과 같다.

```text
확인된 선택 이유 → 유지·수정·회피로 분해 → 다음 후보의 생성 조건
```

## 응용 — 반복 생성이 수렴하는지 판별하기

- **핵심:** 라운드 수가 늘었다고 디자인이 개선된 것은 아니다. 이전 판단이 보존되고 해결할 문제가 줄어들 때만 수렴하고 있다고 볼 수 있다.
  - **유지 성공:** 이전 라운드에서 유지하기로 한 장점이 새 후보에도 남아 있다.
  - **수정 진전:** 고치기로 한 문제가 해결되거나 영향이 작아졌다.
  - **회피 성공:** 다시 만들지 않기로 한 문제가 반복되지 않는다.
  - **새 문제 통제:** 하나를 고치면서 더 큰 문제가 생기지 않았다.

라운드 결과는 다음 네 상태로 구분할 수 있다.

- **수렴:** 장점은 유지되고 문제 목록은 줄어든다.
- **정체:** 같은 문제가 표현만 바뀐 채 반복된다.
- **후퇴:** 새 문제를 고치면서 이전에 확보한 장점을 잃는다.
- **표류:** 목표나 비교 조건이 달라져 이전 라운드와 개선 여부를 비교할 수 없다.

```text
이전 조건
  ↓
새 후보 생성
  ↓
유지됐는가 · 수정됐는가 · 회피됐는가
  ├─ 모두 진전 → 탐색 범위를 더 좁힘
  ├─ 같은 문제 반복 → 조건을 더 구체화
  ├─ 기존 장점 손실 → 이전 기준으로 되돌림
  └─ 비교 조건 변화 → 별도 라운드로 분리
```

멈출 시점도 “마음에 드는 결과가 나왔다”보다 구체적으로 판단할 수 있다.

- 반드시 지켜야 할 조건을 모두 충족한다.
- 남은 차이가 핵심 사용자 작업에 큰 영향을 주지 않는다.
- 추가 라운드에서 얻을 개선보다 새 문제나 표류 위험이 커졌다.
- 채택한 방향과 앞으로 유지할 원칙이 구분되어 기록됐다.

한 줄로 줄이면 다음과 같다.

```text
수렴 = 이전 장점의 보존 + 문제의 감소 + 비교 조건의 유지
```

## 용어 참조

- **RLVR (Reinforcement Learning with Verifiable Rewards):** 정답을 기계적으로 확인할 수 있는 과제에서 자동으로 보상을 주어 학습시키는 방식. 디자인은 무엇이 정답인지 자동으로 확인하기 어려워 적용하기 까다롭다.
