### 1. Designing with ML and LLM Thinking ‹2026-08-10~2026-08-11›

- **핵심:** attention의 수학 내부는 몰라도 된다 — LLM을 "입력 벡터 → 벡터 변환 → 변환된 벡터의 활용"이라는 한 흐름으로만 이해하면, 세상의 어떤 문제든 "어떻게 벡터화하고 어떤 모델을 쓸까"라는 AI 문제로 바꿀 수 있다.
  - **근거 ①** LLM·임베딩의 실제 동작은 결국 하나의 흐름이다 (모달 → 토큰화 → 벡터화 → 변환연산 → 출력벡터). ✅ 이번에 정리
  - **근거 ②** 벡터화 대상은 텍스트·이미지에 그치지 않는다 (DNA·조직도·매출 등). ✅ 이번에 정리
  - **근거 ③** 문제를 AI 문제로 바꾸는 건 "2단 질문(어떻게 벡터화 / 어떤 모델) + 3용도(Retriever·Decision·Generation)"다. ✅ 이번에 정리
  - **근거 ④** LLM이 기존 ML의 여러 작업을 수행할 수 있어도, 기존 ML의 실무 가치까지 사라지는 것은 아니다. ✅ 이번에 정리

#### 근거 ① — 모델은 벡터를 바꾸고, 서비스는 결과를 사용한다

LLM과 임베딩 모델은 겉으로는 다른 일을 하지만 기본 흐름은 같다.

```text
텍스트·이미지 같은 입력
→ 모델이 처리할 수 있는 숫자 배열(벡터)로 변환
→ 모델이 문맥과 의미를 반영한 새로운 벡터로 변환
→ 서비스가 결과 벡터를 목적에 맞게 활용
```

복잡한 수학보다 먼저 알아야 할 것은 **무엇을 벡터로 만들고, 변환된 벡터를 어디에 사용할지**다.

**"모델이 변환한다"는 뜻**

모델은 입력 벡터를 학습된 연산에 통과시켜 **문맥과 관계가 반영된 새로운 내부 표현**으로 계속 갱신한다. 이렇게 모델의 각 층을 지나며 만들어지는 벡터를 `hidden state`라고 한다.

예를 들어 "나는 은행에서 돈을 찾았다"라는 문장에서 처음의 `은행` 벡터는 토큰 자체의 기본 표현이다. Transformer 층에서는 다음 과정이 일어난다.

1. **Self-Attention**이 `은행`과 `돈`, `찾았다` 사이의 관련성을 계산한다.
2. `은행` 벡터에 주변 단어의 문맥 정보가 섞인다.
3. **Feed-Forward Network(FFN)**가 섞인 정보를 다시 가공한다.
4. 여러 층에서 이 과정을 반복한다.

그 결과 `은행`의 hidden state는 단순히 "은행이라는 단어"가 아니라 **이 문장에서는 금융기관을 뜻한다**는 문맥을 담게 된다.

```text
처음 벡터 = 토큰 자체의 기본 표현
변환된 벡터 = 주변 단어와의 관계·문맥이 반영된 hidden state
```

- **LLM**은 변환 결과로 다음 토큰의 확률을 계산하고 하나를 선택한다. 이 과정을 반복해 문장이나 코드를 생성한다.
- **임베딩 모델**은 입력의 의미나 특징을 대표하는 벡터를 출력한다. 두 벡터가 가까운지 비교하면 비슷한 문서·상품·이미지를 찾을 수 있다.

세부적으로 어떤 토큰의 벡터를 모아 최종 벡터를 만드는지는 모델마다 다르다. 중요한 공통점은 **입력을 벡터로 바꾸고 → 모델이 변환하고 → 결과를 활용한다**는 구조다.

같은 구조도 결과를 활용하는 방법에 따라 다른 서비스가 된다.

1. **반품 사유 자동 처리 — 검색·분류 + 판정**  
   반품 사유를 벡터로 바꾸고 대표 카테고리와 비교해 분류한다. 이후 규칙이나 결정트리가 자동 환불과 상담원 연결 중 하나를 선택한다.
2. **사내 문서 검색과 답변(RAG) — 검색 + 생성**  
   질문과 문서를 각각 벡터로 바꾸고 관련 문서를 먼저 찾는다. 찾은 문서를 LLM에 전달해 답변을 생성한다.
3. **상품 추천 — 검색**  
   고객이 구매한 상품들의 벡터를 모아 취향을 나타내는 평균 벡터를 만든다. 이 벡터와 가까운 상품을 추천한다.

#### 근거 ② — 벡터화 대상은 자연 모달을 넘어선다

근거 ①의 "입력 벡터 → 변환 → 활용" 흐름에서 **입구(입력 벡터)가 사실상 무제한**이라는 게 요지. "AI로 풀 수 있나?"가 곧 "이걸 어떻게 숫자 배열로 바꿀 수 있나?"로 환원된다. 두 층으로 갈림:

- **자연 모달(텍스트·이미지·음성):** 사전학습 임베딩 모델이 그대로 벡터화 — 고민 적음.
- **비정형·추상 대상(DNA·조직도·매출·구매이력):** **"어떻게 벡터화할지"가 설계자의 몫.** 강의 쇼핑몰 예시가 전형 — 구매이력을 상품 속성 문장화→임베딩→평균이라는 벡터화 *설계*를 사람이 함.

진짜 메시지는 "무엇이든 벡터화할 수 있다"는 낙관이 아니라, **비자연 모달에서는 무엇을 어떤 숫자로 표현할지가 설계 결정이며 그 선택이 서비스 품질을 좌우한다**는 것이다.

다만 데이터를 숫자로 바꿀 수 있다고 해서 그 벡터가 곧바로 유용한 것은 아니다. 예를 들어 매출액과 방문 횟수를 그대로 한 벡터에 넣으면, 숫자 크기가 훨씬 큰 매출액이 유사도 계산을 거의 결정할 수 있다. 따라서 어떤 정보를 벡터에 넣을지 정하는 **특징 설계**와 값의 크기를 비교 가능한 범위로 맞추는 **정규화**도 벡터화 과정에 포함된다.

##### 응용 — 디자인 시스템 컴포넌트의 벡터화

같은 컴포넌트라도 무엇을 찾고 싶은지에 따라 비교 기준이 달라진다. 예를 들어 `ConfirmDialog`를 찾을 때 다음 세 질문은 서로 다른 정보를 요구한다.

| 찾고 싶은 것 | 벡터로 만들 정보 | 찾을 수 있는 것 |
| --- | --- | --- |
| "삭제 전에 사용자에게 한 번 더 확인받고 싶다" | 컴포넌트의 사용 목적, 적용 사례, 사용 시나리오 같은 텍스트 | 같은 **의도**로 쓰는 컴포넌트 |
| "이 화면과 비슷하게 생긴 컴포넌트가 필요하다" | 렌더링한 스크린샷이나 색·간격·모서리 둥글기 같은 style token | **모양과 분위기**가 비슷한 컴포넌트 |
| "`open`, `onClose`를 받는 컴포넌트가 필요하다" | prop의 이름·타입·설명으로 이루어진 API 스키마 | **사용 방법과 코드 구조**가 비슷한 컴포넌트 |

즉, 컴포넌트 하나에 정답 벡터 하나가 있는 것이 아니다. **의도·시각·API 중 무엇을 기준으로 비슷하다고 판단할지에 따라 서로 다른 벡터를 만든다.** 코드만 분석해서는 "왜, 언제 쓰는가"를 알기 어렵고, 설명만 분석해서는 실제 모양이나 사용할 수 있는 prop을 정확히 알기 어렵기 때문이다.

실무에서는 이 세 종류의 벡터를 별도의 검색 목록인 **멀티 인덱스**에 저장한 뒤, 사용자의 질문에 맞는 목록을 검색한다. 여러 기준이 함께 필요하면 각 검색 결과의 점수를 합치는 **융합(fusion)** 방식을 쓴다.

```text
사용자의 요청
→ 의도·시각·API 중 필요한 기준 선택
→ 기준별로 비슷한 컴포넌트 검색
→ 검색 결과를 합쳐 최종 후보 제시
```

#### 근거 ③ — 실무 문제를 LLM 관점으로 재구성하는 순서

##### 강의 요지

강의는 현실의 문제를 AI가 처리할 수 있는 문제로 바꾸려면 "어떻게 벡터화할 것인가?"와 "어떤 모델로 벡터를 변환할 것인가?"를 결정해야 한다고 설명한다. 이 두 질문을 실무의 언어로 풀면 다음 네 단계가 된다.

1. **서비스가 최종적으로 무엇을 해야 하는가?** 비슷한 항목을 찾을지, 종류를 판정할지, 새로운 답을 만들지 정한다.
2. **그 일을 판단하려면 어떤 정보가 필요한가?** 사용자의 문장, 상품 속성, 컴포넌트 설명, 이미지처럼 모델에 넣을 입력을 고른다.
3. **입력에서 어떤 결과를 만들어야 하는가?** 검색에는 의미를 나타내는 임베딩, 판정에는 범주별 점수, 생성에는 다음 토큰의 확률분포가 필요하다.
4. **그 결과를 어떻게 서비스에 사용할 것인가?** 유사도를 계산해 후보를 찾거나, 점수에 따라 행동을 결정하거나, 토큰을 이어 붙여 답을 만든다.

강의에서 말하는 **벡터화**는 현실의 대상에서 어떤 정보를 골라 모델이 처리할 수 있게 표현하는 **입력 설계**다. **모델을 통한 변환**은 그 입력에서 필요한 관계를 찾아 목적에 맞는 결과를 만드는 과정이다. 예를 들어 임베딩 모델은 문장 속 단어의 관계를 반영해 문장 전체의 의미 벡터를 만들고, 생성 모델은 앞의 문맥을 반영해 다음에 올 토큰의 확률분포를 만든다.

1강의 보충 영상은 이 과정을 다음 세 질문으로 다시 압축한다.

| 강의의 질문 | 쉽게 풀어 쓴 설계 질문 |
| --- | --- |
| 어떻게 벡터화할 것인가? | 판단에 필요한 어떤 정보를 모델에 넣을까? |
| 어떻게 변환할 것인가? | 입력에서 무엇을 알아내야 하며, 어떤 모델이 그 일을 잘할까? |
| 어떻게 활용할 것인가? | 결과로 검색할까, 행동을 정할까, 새로운 내용을 만들까? |

모델이 만든 결과는 주로 세 방식으로 활용한다.

- **Retriever:** 의미가 비슷한 문서·상품·컴포넌트를 검색한다.
- **Decision:** 범주별 점수나 규칙을 이용해 분류하고 다음 행동을 정한다.
- **Generation:** 다음 토큰을 차례로 선택해 텍스트·코드 같은 새로운 결과를 만든다.

세 용도는 하나만 고르는 배타적인 선택지가 아니다. 하나의 서비스 안에서 앞 단계의 결과를 다음 단계가 받아 순서대로 연결할 수도 있다.

```text
컴포넌트 후보 검색(Retriever)
→ 호환성과 조합 가능성 판정(Decision)
→ 여러 조합과 예제 코드 생성(Generation)
```

따라서 전체 사고 순서는 다음과 같다.

```text
서비스의 목적 결정
→ 판단에 필요한 입력 선택
→ 목적에 맞는 모델로 입력 처리
→ 나온 결과를 검색·판정·생성에 활용
```

##### 강의 예시 — 상품 추천

쇼핑몰의 상품 추천 문제는 다음과 같이 바뀐다.

```text
구매 상품의 속성
→ LLM으로 속성을 문장화
→ 상품별 임베딩 생성
→ 고객별 평균 구매 벡터 계산
→ 유사한 상품 검색
```

이 예시에서 서비스의 최종 용도는 Retriever이고, 벡터화 대상과 방법을 정하는 일이 설계자의 핵심 판단이다.

##### 보완 — 모델의 활용과 서비스 실행은 다른 층이다

강의의 세 용도는 **모델이 만든 결과를 활용하는 방식**을 분류한 것이다. 규칙 평가, 데이터베이스 조회, 외부 시스템 실행은 벡터 표현이나 네 번째 모델 용도가 아니라 모델 밖의 서비스 처리다. 그래프·시계열·정형 데이터도 그대로 벡터인 것은 아니며, 모델에 넣으려면 목적에 맞는 특징이나 임베딩으로 표현해야 한다.

또한 임베딩은 학습 목표와 데이터가 해당 목적에 맞을 때 관련 패턴을 표현할 뿐, 주문 번호·날짜·금액 같은 정확한 값의 보존을 보장하지 않는다. 이런 값은 원본 데이터나 데이터베이스에서 다뤄야 한다. "decoder 하나로 기존 ML이 불필요하다"는 강의의 다음 주장은 근거 ④에서 별도로 검토한다.

#### 근거 ④ — LLM이 할 수 있다는 것과 LLM을 써야 한다는 것은 다르다

- **핵심:** LLM이 기존 ML의 여러 작업을 수행할 수 있다는 사실과, 기존 ML이 쓸모없다는 결론은 다르다.
  - **근거 1:** 하나의 LLM 구조로 검색·분류·회귀·생성 등 여러 작업을 처리할 수 있다.
  - **근거 2:** 그래서 겉으로는 OCR이나 번호판 인식 같은 작업에도 기존 ML이 필요 없어 보인다.
  - **근거 3:** 그러나 강의는 "배울 필요가 없다"와 "쓸모가 없다"를 구분하고, 실제 선택 기준은 다음 강의로 넘긴다.

여기서는 **"할 수 있는가?"와 "쓰는 편이 좋은가?"를 구분해야 한다.** 스마트폰 카메라가 사진과 동영상을 모두 찍을 수 있다고 해서 전문 카메라가 곧바로 쓸모없어지는 것은 아니다. 중요한 것은 기능의 존재보다 상황에 맞는 선택이다.

```text
LLM도 이 작업을 할 수 있다
→ 그러면 기존 ML은 필요 없나?
→ 학습 우선순위와 실무 활용 가치는 다른 문제다
→ 언제 무엇을 쓸지는 다음 강의에서 판단
```

LLM도 OCR이나 분류를 수행할 수 있지만, 이것만으로 기존 ML보다 정확한지, 더 빠르고 저렴한지, 결과를 예측하고 통제하기 쉬운지, 작은 데이터나 제한된 장비에서도 적합한지는 확인되지 않는다. 이 기준들은 1강의 결론이 아니라 다음 강의에서 검토해야 할 질문이다.

따라서 1강이 확정한 범위는 다음과 같다. **LLM은 기존 ML이 맡던 여러 작업을 하나의 구조로 처리할 수 있다. 기존 ML을 처음부터 깊이 학습해야 할 필요성은 줄었지만, 그렇다고 기존 ML의 실무 가치까지 사라진 것은 아니다.**

### 2. AI Service Design — Part 2: When to Use ML vs LLM ‹2026-08-11›

- **핵심:** 모델의 신구보다, 문제를 얼마나 좁고 명확하게 정의할 수 있는지가 선택을 가른다.
  - **근거 ① 기존 ML:** 입력과 출력이 정해진 문제에서는 빠르고 저렴하며 결과를 통제하기 쉽다. ✅ 이번에 정리
  - **근거 ② LLM:** 입력이 다양하고 무엇을 의미하는지 해석해야 하는 문제에 유리하다. ✅ 이번에 정리
  - **근거 ③ 설계자의 역할:** 같은 현실 문제도 범위를 어떻게 정하느냐에 따라 ML 문제나 LLM 문제로 바뀐다. ✅ 이번에 정리
  - **보완:** 강의의 `ML = 결정적`, `LLM = 해석적` 구분은 유용한 설계 기준이지만 엄밀한 기술 분류는 아니다.

#### 먼저 이해할 개념 — 해석 엔트로피

강의는 모델 선택의 중심 기준으로 **해석 엔트로피**라는 표현을 사용한다. 여기서 엔트로피는 엄밀한 정보이론 수식이라기보다 **입력이 무엇을 뜻하는지 알아내고, 출력이 무엇을 뜻하는지 판단하는 데 드는 불확실성과 해석 비용**이라는 뜻에 가깝다.

예를 들어 번호판 인식을 좁게 정의하면 해석 엔트로피가 낮다.

```text
입력: 정해진 위치에서 촬영한 국내 번호판 사진
출력: 번호판에 적힌 문자
```

입력 형식과 원하는 답이 정해져 있으므로 작은 전용 모델이 빠르게 처리할 수 있다. 반대로 문제를 넓게 정의하면 해석 엔트로피가 높아진다.

```text
입력: 국가·연도·촬영 각도가 제각각인 차량 사진
출력: 번호판을 찾아 문자를 읽고 어떤 형식인지 설명
```

먼저 사진에서 번호판이 어디인지, 어느 나라 형식인지, 흐릿한 문자를 어떻게 해석할지 판단해야 한다. 강의는 이런 문제에 LLM이나 멀티모달 모델이 더 잘 맞는다고 본다.

#### 강의의 선택 기준

| 판단 기준 | 기존 ML이 어울리는 경우 | LLM이 어울리는 경우 |
| --- | --- | --- |
| 문제 범위 | 한 가지 작업으로 좁게 정의됨 | 문제 자체를 해석해야 함 |
| 입력 | 형식과 범위가 정규화됨 | 자연어처럼 표현과 조건이 다양함 |
| 출력 | 클래스·점수·숫자처럼 고정됨 | 설명·요약·계획처럼 열려 있음 |
| 실행 조건 | 매우 빠르거나 자주 실행해야 함 | 어느 정도 비용과 지연을 허용할 수 있음 |
| 변화 대응 | 도메인과 규칙이 안정적임 | 새로운 표현과 상황이 자주 등장함 |
| 설명 | 단순 모델의 변수 영향을 확인해야 함 | 통합적인 해석과 생성이 중요함 |

#### 근거 ① — 기존 ML은 닫힌 문제에 강하다

여기서 강의가 말하는 `기존 ML`은 로지스틱 회귀·결정트리 같은 고전 알고리즘뿐 아니라, 특정 작업만 수행하도록 학습한 작은 CNN·RNN 등의 전용 모델까지 포함한다. 핵심은 모델의 연식이 아니라 **입력과 출력 사이의 계약이 얼마나 명확한가**다.

```text
허용할 입력을 미리 정할 수 있고
→ 출력의 종류도 고정할 수 있고
→ 같은 판단을 빠르게 반복해야 한다면
→ 전용 ML 모델이 유리할 수 있다
```

1. **빠르게 실행해야 한다.** 작은 전용 모델은 일반적으로 LLM보다 계산량이 적고 고정된 출력을 한 번에 계산한다. 긴 답을 토큰 단위로 생성하지 않으므로 CPU나 작은 장비에서도 빠르게 실행할 수 있다. 다만 모든 기존 ML이 항상 빠른 것은 아니며, 실제 속도는 모델 크기·하드웨어·입력 크기·생성 단계의 유무에 달려 있다.
2. **입력과 출력이 정규화돼 있다.** 정해진 위치의 카메라, 일정한 이미지 크기, 허용된 번호판 형식처럼 입력의 형태와 범위를 통제하고 출력도 문자열 하나나 `인식 실패`처럼 고정할 수 있다면, 모델이 문제 자체부터 해석할 필요가 없다.
3. **제한된 데이터에서 좁은 패턴을 학습한다.** 문제의 범위와 특징이 잘 정의돼 있다면 비교적 적은 학습 데이터로도 전용 모델을 만들 수 있다. 그러나 데이터가 작으면 무조건 기존 ML이 낫다는 뜻은 아니다. 입력의 구조화 정도, 예측 범위, 적합한 사전학습 모델의 존재, 새로 학습할지 그대로 사용할지를 함께 판단해야 한다.
4. **판단 근거를 추적해야 한다.** 로지스틱 회귀나 얕은 결정트리처럼 단순한 모델은 어떤 변수가 결과에 영향을 줬는지 비교적 쉽게 확인할 수 있다. 기존 ML 전체가 설명 가능한 것은 아니며, 복잡한 CNN이나 대규모 신경망은 내부 판단을 설명하기 어렵다.

```text
기존 ML이라서 설명 가능하다 ✗

계수·분기·특징 영향을 추적할 수 있는
단순한 모델을 선택했기 때문에 설명 가능하다 ✓
```

##### 보완 — 규칙, ML, LLM을 먼저 구분한다

강의는 주로 ML과 LLM을 비교하지만, 정확한 규칙을 코드로 작성할 수 있다면 ML조차 필요하지 않을 수 있다.

```text
판단 규칙을 사람이 정확히 작성할 수 있음
→ 규칙·일반 코드

규칙은 작성하기 어렵지만 고정된 데이터에서 패턴을 학습할 수 있음
→ 기존 ML

입력의 의미와 문제 범위부터 해석해야 함
→ LLM
```

컴포넌트 추천 서비스에 적용하면 다음처럼 나뉜다.

| 문제 | 적합한 수단 |
| --- | --- |
| React 버전 범위가 맞는가? | package metadata와 버전 규칙 |
| 필수 prop이 전달됐는가? | TypeScript·정적 분석 |
| 화면과 시각적으로 비슷한가? | 이미지 임베딩이나 전용 ML |
| 사용 의도에 적절한가? | 텍스트 임베딩·LLM |
| 여러 후보 중 어떤 구성이 자연스러운가? | 호환성 규칙 + 실제 사용례 + LLM |

따라서 근거 ①의 핵심은 다음과 같다. **입력과 출력의 계약이 좁고 반복 실행 조건이 명확할수록 작은 전용 모델이 유리하다. 판단 규칙까지 정확히 작성할 수 있다면 모델보다 일반 코드가 먼저다.**

#### 근거 ② — LLM은 열린 해석 문제에 강하다

기존 ML이 정해진 입력에서 정해진 출력을 만드는 전용 창구라면, LLM은 여러 형태의 요청을 받아 무엇을 원하는지 먼저 해석하는 종합 안내 창구에 가깝다.

```text
기존 ML
정해진 입력 → 정해진 작업 → 정해진 출력

LLM
다양한 입력 → 의도와 맥락 해석 → 상황에 맞는 출력
```

##### 정규화되지 않은 입력의 해석

현실의 사용자는 같은 의도를 여러 방식으로 표현한다. "삭제 전에 확인받고 싶어", "위험한 작업을 바로 실행하지 않게 해줘", "사용자가 실수하지 않도록 한 번 더 물어봐"는 표면의 단어가 다르지만 모두 `파괴적 작업 전 확인`이라는 비슷한 의도를 가진다.

LLM과 임베딩 모델은 넓은 데이터에서 학습한 언어 패턴을 이용해 사용자가 명시하지 않은 목적, 문장 전체의 맥락, 여러 요구사항의 관계, 처음 보는 표현의 변형을 해석할 수 있다. 강의가 말하는 **높은 입력 해석 엔트로피를 감당한다**는 것이 이 뜻에 가깝다.

##### 통합적인 결과의 생성

LLM은 입력을 하나의 범주로 분류하는 데서 끝나지 않고 여러 정보를 엮어 설명·요약·계획·코드를 만들 수 있다.

```text
사용자 요청
+ 검색한 컴포넌트 문서
+ 실제 프로젝트 사용례
+ 호환성 검사 결과
→ LLM
→ 후보 조합 + 선택 이유 + 예제 코드
```

강의는 이를 **통합적 위임 업무**라고 표현한다. 사용자가 중간 절차를 모두 지정하지 않아도 여러 정보를 해석해 하나의 결과로 구성할 수 있다는 뜻이다. 다만 검색 결과나 호환성처럼 사실 확인이 필요한 정보는 도구와 규칙이 제공하고, LLM은 확인된 정보를 해석하고 구성하는 역할을 맡는 편이 안전하다.

##### 문제를 다시 정의하는 능력

강의는 LLM이 주어진 문제를 해결할 뿐 아니라 다른 문제 정의를 제안할 수 있다고 본다. 예를 들어 사용자가 "컴포넌트 검색 결과가 부족하다"고 말했을 때, LLM은 맥락을 검토해 "검색 개수보다 사용 의도와 API 호환성을 함께 평가하지 않는 것이 문제일 수 있다"는 대안을 제시할 수 있다.

그러나 이것을 `진짜 문제를 스스로 발견한다`고 단정하면 과장이다. **LLM은 대안적인 문제 정의를 제안할 수 있지만, 그것이 실제 문제인지는 사용자와 프로젝트 증거가 검증해야 한다.**

##### 확률적 출력의 의미

LLM은 현재 문맥에서 다음 토큰별 확률을 계산하고, decoding 전략에 따라 토큰을 선택한 뒤 이 과정을 반복한다. `temperature`, `top-k`, `top-p`는 어떤 후보에서 토큰을 선택할지 조절한다.

강의는 이 과정을 두고 결과가 항상 무작위라고 설명하지만, 더 정확하게는 샘플링을 사용하면 같은 입력에서도 결과가 달라질 수 있고 greedy decoding을 사용하면 결과를 더 고정할 수 있다. 출력을 고정해도 판단 근거의 설명이나 내용의 정확성이 보장되는 것은 아니다. **결과의 반복 가능성, 판단 근거의 설명 가능성, 내용의 정확성은 서로 다른 문제다.**

##### 해석 엔트로피는 양쪽에서 생긴다

LLM은 복잡한 입력을 대신 해석해 사용자의 부담을 줄이지만, 자유 형식의 출력을 만들기 때문에 새로운 해석 비용을 만들 수도 있다.

```text
다양하고 모호한 입력
→ LLM이 의미를 해석해 부담을 줄임
→ 자유 형식의 결과 생성
→ 서비스가 결과를 다시 검증해야 함
```

따라서 좋은 LLM 서비스는 JSON Schema로 출력 형식을 제한하고, 검색한 출처를 함께 제공하고, 호환성 규칙으로 결과를 검증하고, 필요한 실행에는 사람의 승인을 두는 식으로 출력의 자유도를 통제한다.

##### 응용 — 컴포넌트 추천 서비스

LLM은 자연어 요청에서 사용 목적과 상황을 추출하고, 서로 다른 표현을 같은 의도로 연결하고, 후보들의 차이를 설명하고, 성격이 다른 여러 조합과 기존 조합을 바탕으로 한 대안을 제안할 수 있다.

반면 컴포넌트의 실제 존재 여부, prop과 버전의 정확한 호환성, 실제 프로젝트 사용례의 존재, 패키지 설치나 코드 변경의 성공 여부는 LLM에 맡기지 않는다.

```text
LLM
무엇을 원하는지 해석
        ↓
검색·API·File Search
실제 후보와 근거 확보
        ↓
규칙과 정적 분석
호환 가능한 조합 판정
        ↓
LLM
여러 조합의 성격·장단점·예제 설명
```

따라서 근거 ②의 핵심은 다음과 같다. **LLM은 미리 열거하기 어려운 입력의 변형과 맥락을 해석하고 여러 정보를 하나의 결과로 구성하는 데 유리하다. 그러나 사실 확인과 실행 판정까지 LLM의 해석에 맡겨서는 안 된다.**

강의의 결론은 다음처럼 압축된다.

```text
경계가 좁고 입출력이 명확한 문제
→ 기존 ML

경계가 넓고 입력의 의미를 해석해야 하는 문제
→ LLM
```

#### 근거 ③ — 모델보다 먼저 문제의 경계를 설계한다

강의는 번호판 인식을 두 방식으로 비교한다.

```text
"국내에서 사용하는 다섯 가지 번호판 형식만 인식한다"
→ 범위가 닫힌 결정 문제
→ 기존 ML로 설계 가능
```

```text
"어느 나라, 어느 시대의 번호판이든 알아서 찾아 읽어라"
→ 범위가 열린 해석 문제
→ 멀티모달 LLM에 가까운 문제
```

즉, 번호판 인식이라는 이름만 보고 모델을 고르는 것이 아니다. **허용할 입력의 범위와 필요한 출력의 수준을 정한 뒤 모델을 고른다.** 현실의 문제가 처음부터 ML 문제나 LLM 문제로 정해져 있는 것이 아니라, 설계자가 문제의 경계를 어디에 긋느냐에 따라 적합한 수단이 달라진다.

```text
현실의 문제 이름
→ 허용할 입력과 필요한 출력 정의
→ 닫힌 전용 문제 또는 열린 해석 문제
→ 규칙·ML·LLM 선택
```

문제를 좁게 닫으면 지원하지 못하는 사례는 늘지만 빠르고 저렴하며 테스트하기 쉬워진다. 문제를 넓게 열면 다양한 현실 상황을 처리할 수 있지만 비용·지연·오류·검증 부담이 커진다.

| 설계 방향 | 장점 | 대가 |
| --- | --- | --- |
| 문제를 좁게 닫음 | 빠르고 저렴하며 테스트하기 쉬움 | 지원하지 못하는 사례가 늘어남 |
| 문제를 넓게 열어 둠 | 다양한 현실 상황을 처리할 수 있음 | 비용·지연·오류·검증 부담이 커짐 |

따라서 좋은 설계는 LLM이 처리할 수 있는 최대 범위를 목표로 하지 않는다. **사용자가 실제로 필요로 하는 범위까지만 열고, 정확히 닫을 수 있는 부분은 닫는다.**

#### 강의 표현에서 주의할 점

강의의 구분은 이해하기 쉽지만 그대로 기술적 사실로 받아들이면 몇 가지 오해가 생긴다.

- 기존 ML도 항상 결정론적이거나 설명 가능한 것은 아니다. 복잡한 신경망은 내부 판단을 설명하기 어렵다.
- LLM도 설정에 따라 같은 출력을 만들 수 있지만, 이것이 판단 근거까지 설명된다는 뜻은 아니다.
- LLM이 느린 이유는 단순히 attention 때문만은 아니다. 모델 크기가 크고, 생성할 때 토큰을 순차적으로 만들기 때문이다.
- 미션 크리티컬한 문제라고 해서 기존 ML만 쓰면 안전해지는 것은 아니다. 검증·규칙·사람의 검토 같은 별도 안전장치가 필요하다.

따라서 실무에서는 양자택일보다 여러 축으로 판단하는 편이 정확하다.

#### 응용 — 컴포넌트 추천 서비스

전체 서비스를 ML 또는 LLM 하나로 분류할 필요는 없다. 서비스 안의 각 판단을 별도 문제로 나누고, 각 단계에 가장 작은 적합 수단을 배치한다.

| 하위 문제 | 문제의 성격 | 적합한 수단 |
| --- | --- | --- |
| 사용자가 원하는 UI 의도 파악 | 표현이 다양하고 모호함 | LLM·임베딩 |
| 실제 컴포넌트 목록 확인 | 정확한 목록이 필요함 | API·CLI·File Search |
| 버전과 prop 호환성 검사 | 규칙이 명확함 | package metadata·정적 분석 |
| 실제 함께 사용된 조합 찾기 | 프로젝트 증거를 검색해야 함 | 코드 검색·사용례 인덱스 |
| 후보 순위 계산 | 기준과 점수로 비교 가능 | 규칙·랭커·전용 ML |
| 성격이 다른 여러 조합 설명 | 열린 생성 문제 | LLM |
| 예제 코드가 동작하는지 확인 | 정확한 실행 결과가 필요함 | 타입 검사·테스트·빌드 |

그래서 실제 구조는 다음과 같은 혼합형에 가깝다.

```text
LLM·임베딩
사용자의 의도를 해석해 후보 검색
        ↓
API·CLI·File Search
실제 존재하는 컴포넌트와 사용례 확인
        ↓
규칙·호환성 검사
함께 사용할 수 있는 조합만 남김
        ↓
LLM
성격이 다른 조합과 예제 코드 제안
```

사용자의 요구와 비슷한 실제 조합이 있다면 새 조합을 처음부터 생성하기보다 그것을 Base로 삼는다.

```text
실제 프로젝트에서 사용된 조합 검색
→ 현재 요구사항과 호환성 비교
→ 그대로 쓸 수 있는 부분 확정
→ 달라진 요구사항만 LLM이 변형
→ 타입 검사와 테스트로 검증
```

실제 조합이 없다면 LLM이 가장 보수적인 조합, 구현이 단순한 조합, 확장성이 높은 조합, 시각적 일관성을 우선한 조합처럼 성격이 다른 대안을 만들 수 있다. 다만 이는 **생성된 제안**이며 실제 사용례와 같은 수준의 근거는 아니다. 응답에서 둘을 구분해야 한다.

따라서 근거 ③의 핵심은 다음과 같다. **모델은 문제 이름으로 선택하지 않는다. 허용할 입력, 필요한 출력, 속도·비용·정확성 조건을 정하고 문제를 하위 단계로 분해한 뒤, 각 단계에 규칙·검색·기존 ML·LLM 중 가장 작은 적합 수단을 배치한다.**

### 3. What Defines an AI Service? ‹2026-08-11›

- **핵심:** AI 서비스 여부는 자체 모델을 학습했는지가 아니라, AI가 사용자 가치와 사업 구조에서 얼마나 중심적인 역할을 하는지로 판단해야 한다.
  - **근거 ① 구축 방식:** 모델을 직접 학습·튜닝할 수도 있고, 기존 모델에 Context·RAG·Agent를 붙여 실행 시점에 증강할 수도 있다.
  - **근거 ② 서비스 중심성:** AI는 기존 서비스의 작은 보조 기능일 수도 있고, 사용자가 원하는 핵심 결과를 만드는 중심 기능일 수도 있다.
  - **근거 ③ AI 특화 사업:** AI가 기존 방식의 비용·속도·규모 한계를 바꿀 때 AI는 기능을 넘어 사업을 성립시키는 기반이 된다.

#### 먼저 이해할 개념 — AI 서비스는 정도의 차이다

강의는 AI 서비스의 범위에 객관적인 한 줄 경계가 있다고 말하지 않는다. 업계에서는 전용 모델을 만들거나 튜닝했는지, 서비스에서 AI 기능을 얼마나 사용하는지, 핵심 사용자 가치가 AI에서 나오는지, AI가 없을 때도 같은 비용과 규모로 운영할 수 있는지처럼 서로 다른 기준을 사용한다.

이를 이해하기 쉽게 세 단계로 나눌 수 있다.

| 단계 | AI의 역할 | AI가 없어지면 |
| --- | --- | --- |
| AI 보조 기능 | 기존 서비스의 일부 기능을 편리하게 함 | 불편하지만 서비스는 계속 작동함 |
| AI 중심 제품 | 사용자가 원하는 핵심 결과를 AI가 만듦 | 제품의 핵심 가치가 사라짐 |
| AI 특화 사업 | AI가 비용·속도·규모의 한계를 바꿔 사업을 성립시킴 | 같은 방식의 사업 운영이 어려움 |

가장 간단한 판별 질문은 **"AI가 하루 동안 사라진다면 무엇이 남는가?"**다. 작은 편의 기능만 사라지면 AI 보조 기능, 사용자가 원하는 핵심 결과가 사라지면 AI 중심 제품, 서비스의 비용·속도·규모가 성립하지 않으면 AI 특화 사업에 가깝다. 이는 공식 표준이 아니라 강의 내용을 이해하기 위한 판별 도구이며, 실제 서비스는 세 단계 사이의 회색 지대에 놓일 수 있다.

#### 근거 ① — 모델 튜닝과 실행 시점 증강은 서로 다른 구축 전략이다

강의는 신경망을 직접 만들거나 기존 모델을 튜닝한 서비스만 AI 서비스로 보는 관점을 먼저 소개한다. 그러나 OpenAI·Gemini 같은 외부 모델을 사용하고 Context·RAG·Agent로 기능을 구성해도 AI가 핵심 가치를 만든다면 AI 서비스다. 모델 소유 여부와 제품의 성격은 별개의 질문이다.

##### Fine-tuning — 반복할 행동을 파라미터에 반영

**Fine-tuning**은 학습 예시를 이용해 모델의 행동·출력 형식·전문 패턴을 파라미터에 반영하는 방법이다. 강의는 장기간 많은 사용자에게 같은 행동을 빠르게 제공해야 할 때 튜닝을 고려할 수 있다고 설명한다. 매 요청마다 긴 지시와 예시를 Context에 넣지 않아도 되므로 입력 토큰과 반복 설명을 줄일 가능성이 있다.

다만 Fine-tuning했다고 모델 자체가 작아지거나 항상 빨라지는 것은 아니다. 속도는 모델 크기, 입력·출력 토큰 수, 제공 인프라, 캐시와 배치 처리에도 좌우된다. 또한 튜닝은 정확한 사실 저장보다 반복되는 행동과 형식을 맞추는 데 적합하며, 최신 정보·사내 정보·출처가 필요한 문제를 대신 해결하지 않는다.

##### 실행 시점 증강 — 필요한 정보를 그때 제공

**Context augmentation**은 실행할 때 필요한 지시·문서·도구 결과를 모델에 제공하는 방식이다.

- **RAG:** 관련 문서를 검색해 Context에 추가한다.
- **Agent:** API·검색·코드 실행 같은 도구를 호출하고 그 결과를 다시 모델에 전달한다.
- **피드백 루프:** 앞 단계의 결과와 검증 실패를 다음 요청에 반영한다.

지식이 자주 바뀌거나, 사내 자료와 최신 정보를 사용하거나, 답의 출처를 확인해야 하는 경우에 적합하다. 대신 매 요청에서 검색·도구 호출·긴 Context를 처리하므로 지연 시간과 실행 비용이 늘고, 여러 단계의 실패를 관리해야 한다.

| 판단 기준 | Fine-tuning 쪽 | 실행 시점 증강 쪽 |
| --- | --- | --- |
| 바꾸려는 것 | 반복되는 행동·문체·출력 형식 | 요청마다 필요한 지식·근거·도구 결과 |
| 정보 변화 | 비교적 안정적 | 자주 바뀜 |
| 출처 확인 | 파라미터에 섞여 확인하기 어려움 | 검색 문서와 도구 결과로 확인 가능 |
| 초기 비용 | 학습 데이터·튜닝·평가 필요 | 검색과 도구 연결 필요 |
| 실행 비용 | 입력 Context를 줄일 가능성 | 검색·도구 호출·Context 비용 발생 |

두 방식은 경쟁 관계가 아니다. 안정적인 행동은 Fine-tuning으로 맞추고, 최신 정보와 프로젝트 사실은 RAG·도구로 제공하는 식으로 함께 사용할 수 있다.

#### 근거 ② — 제품에서 AI가 차지하는 중심성이 다르다

AI 기능의 개수보다 **사용자가 제품을 선택한 이유와 AI 기능이 겹치는가**가 중요하다.

##### AI 보조 기능

기존 서비스에 제목 생성, 환영 문구 작성, 도움말 생성, 간단한 요약을 붙이는 경우다.

```text
기존 서비스 + 작은 AI 기능
→ AI 기능이 없어도 본래 목적은 수행 가능
```

Docker나 Postman에 대화형 도우미가 붙어도 제품 전체를 AI 서비스로 인식하지 않는 이유다. AI가 편의성을 높이지만 핵심 사용자 가치를 대신하지는 않는다.

##### AI 중심 제품

ChatGPT 같은 생성 서비스, AI 튜터, 자연어 검색과 질의응답, AI 추천, 이미지·만화·소설 생성처럼 사용자가 원하는 핵심 결과를 AI가 만드는 경우다.

```text
AI 기능 제거
→ 사용자가 기대한 핵심 결과를 만들 수 없음
```

직접 모델을 학습하지 않고 외부 API를 사용해도 AI 중심 제품이 될 수 있다. 반대로 AI 기능을 여러 개 붙였어도 제품의 본래 가치가 그대로 남는다면 AI 보조 기능에 가깝다.

서비스의 중심성을 판단할 때는 다음을 묻는다.

1. 사용자는 AI 결과 때문에 이 제품을 선택하는가?
2. AI가 실패하면 핵심 사용자 과업도 실패하는가?
3. AI를 제거해도 같은 가치 제안을 유지할 수 있는가?

#### 근거 ③ — AI가 사업의 비용과 가능한 범위를 바꾼다

강의가 말하는 **AI 특화 사업**은 AI가 없으면 절대 불가능한 문제만 뜻하지 않는다. 사람이 할 수는 있지만 막대한 인력·시간·비용이 필요해 규모를 키우기 어려운 문제도 포함한다.

##### 기존에는 만들기 어렵던 결과

코딩 에이전트, 생성 콘텐츠, 복잡한 인식과 판단처럼 기존 방식으로 원하는 품질을 만들기 어려웠던 결과를 AI가 가능하게 한다. 다만 "AI가 아니면 구현할 수 없다"는 강의 표현은 방향을 강조한 말이다. 실제로는 기존 알고리즘이나 사람의 작업으로 일부 구현할 수 있는 경우도 있으므로, **요구 품질과 비용 안에서 대체 가능한가**를 판단해야 한다.

##### 사람이 할 수 있지만 규모화하기 어려운 업무

- 많은 법령·판례·의학 자료를 반복 검토하는 업무
- CCTV와 설비 상태를 계속 감시하는 업무
- 농작물 상태를 확인해 작업 시점을 판단하는 업무
- 복잡하고 변하는 차량·창고·자원 배치 업무

```text
사람이 직접 처리
→ 많은 인력·시간·비용 필요
→ 규모 확장이 어려움

AI가 해석과 반복 판단을 지원
→ 단위 처리 비용 감소 가능
→ 더 많은 사례를 처리
→ 새로운 사업 구조 가능
```

의료·법률·안전처럼 위험이 큰 분야에서는 처리량이 늘어나는 것만으로 사업이 성립하지 않는다. 정확성 평가, 근거 추적, 사람의 검토, 책임 경계를 함께 설계해야 한다.

##### 기존 도메인의 AI 기반 재정의

과거의 스타트업이 금융·배달·영상 서비스를 IT 기반으로 다시 정의했다면, 강의는 앞으로 기존의 IT 서비스와 비IT 업무를 AI 기반으로 다시 정의할 수 있다고 본다.

```text
기존 업무의 높은 해석 비용·반복 노동·복잡한 탐색
→ AI가 맡을 수 있는 판단과 생성 분리
→ 사람은 목표·검증·예외 처리 담당
→ 비용 구조와 사용자 경험 재설계
```

AI를 붙였다는 사실만으로 재정의가 일어나는 것은 아니다. 사용자 가치, 품질, 운영 비용, 실패 위험이 실제로 개선됐다는 증거가 필요하다.

#### 응용 — 컴포넌트 추천 서비스의 위치

같은 컴포넌트 검색 기능도 AI가 맡는 역할에 따라 성격이 달라진다.

##### AI 보조 기능

기존 디자인 시스템 문서 사이트에 자연어 검색창만 추가한다. AI가 없어도 사용자는 목록과 문서를 직접 탐색할 수 있다.

##### AI 중심 제품

```text
사용자의 의도 해석
→ 정확한 컴포넌트 후보 검색
→ 호환 가능한 조합 판정
→ 성격이 다른 조합과 근거 제안
```

사용자는 단순 목록이 아니라 자신의 상황에 맞는 선택과 조합을 얻기 위해 제품을 사용한다. 이 결과가 사라지면 제품의 핵심 가치도 사라진다.

##### AI 특화 사업으로의 확장

```text
여러 조직의 디자인 시스템과 실제 프로젝트 분석
→ 반복되는 UI 의도와 조합 패턴 발견
→ 조직별 호환성과 사용 규칙 적용
→ 설계·구현·검증 흐름 전체 지원
```

사람이 여러 저장소와 문서를 매번 검토하던 비용을 줄이고, 기존에는 어려웠던 규모로 의사결정을 지원한다면 AI가 사업 구조를 바꾸는 단계에 가까워진다.

따라서 3강의 결론은 다음과 같다. **AI 서비스는 자체 모델 보유 여부로 정의되지 않는다. AI가 제품의 핵심 가치와 사업의 비용·속도·규모를 얼마나 바꾸는지가 더 중요한 기준이다.**

### 4. Profitability and Design Capability ‹2026-08-11›

- **핵심:** AI가 구현 비용을 낮추는 만큼 복제도 쉽게 만들기 때문에, 수익성은 AI 기능 자체가 아니라 검증 가능한 사업 효과와 결과물을 오래 바꿔 갈 수 있는 설계 역량에서 나온다.
  - **근거 ① 매출:** AI가 새로운 구매 이유나 사용량을 만들어 실제 매출에 기여해야 한다.
  - **근거 ② 비용:** 현재 많은 기업은 새 매출보다 기존 사람·운영 비용을 AI 실행 비용으로 전환하는 단계에 있다.
  - **근거 ③ 경쟁력:** 구현과 복제가 쉬워지므로 아이디어와 코드만으로는 경쟁 우위를 오래 유지하기 어렵다.
  - **근거 ④ 설계 역량:** 사람이 바뀔 지식의 경계와 성공 조건을 정하고 문제를 독립적으로 검증할 수 있게 나눌수록 AI 결과의 유지보수성이 높아진다.

#### 근거 ① — AI 기능이 아니라 새로 만든 매출을 본다

강의는 비즈니스 관점에서 AI 사업을 판단하려면 AI를 얼마나 많이 썼는지가 아니라 **AI 때문에 실제 매출이 어떻게 달라졌는지**를 봐야 한다고 설명한다.

```text
기존 제품
→ AI로 새로운 사용자 가치 추가
→ 구매·구독·사용량 증가
→ 매출 증가
```

강의의 가전·스마트폰 사례에서 중요한 것은 AI 기능의 기술적 난도가 아니다. 사용자가 그 기능 때문에 제품을 선택하거나 더 자주 사용해 매출에 기여했는지가 핵심이다. 따라서 `AI 기능 출시`와 `AI 사업 성과`를 같은 것으로 취급하면 안 된다.

확인해야 할 지표도 기능 수가 아니라 전환율, 유료 전환, 유지율, 사용 빈도, 사용자당 매출처럼 사업 효과와 연결돼야 한다. 토큰 사용량 역시 그 자체로 사용자 가치가 아니다. 사용량 증가가 매출과 유지율을 높이는지, 늘어난 모델 비용보다 큰 가치를 만드는지를 함께 봐야 한다.

#### 근거 ② — 비용 전환이 실제 절감인지는 총비용으로 판단한다

강의는 현재 많은 기업이 기존 매출 구조는 유지하면서 사람이 수행하던 일부 운영을 AI로 옮기는 **비용 전환** 단계에 있다고 본다. 고객 문의 초안, 내부 Q&A, 인프라 운영 보조, 반복 분류와 문서 처리, 개발 업무 일부가 여기에 해당한다.

```text
기존 운영
사람이 반복해서 처리
→ AI가 초안·검색·분류를 지원
→ 사람은 검증·예외 처리·최종 책임 담당
```

그러나 인건비 일부가 모델 사용료로 바뀌었다고 바로 비용 절감이 되는 것은 아니다.

```text
AI의 사업 효과
= 새로 만든 매출
+ 실제로 줄인 비용
- 모델·데이터·검증·운영·실패 비용
```

총비용에는 모델 호출, 검색·저장 인프라, 평가 데이터, 품질 검사, 잘못된 결과의 수정, 사람에게 넘기는 예외 처리, 보안·감사·모니터링, 모델과 제공자 변경 비용이 포함된다. 처리 시간과 인력이 줄어도 오류와 재작업이 늘면 비용 전환은 절감으로 이어지지 않는다.

#### 근거 ③ — 구현이 쉬워지면 복제도 쉬워진다

강의는 바이브 코딩이 서비스 생성 비용을 낮추는 동시에 경쟁 서비스의 복제 비용도 낮춘다고 지적한다.

```text
내가 AI로 빠르게 구현할 수 있음
= 경쟁자도 비슷한 기능을 빠르게 구현할 수 있음
```

아이디어 하나, 일반적인 LLM 연결, 쉽게 복제할 수 있는 UI, 공개 모델이 생성한 코드만으로는 경쟁력이 오래가기 어렵다. 상대적으로 오래 축적할 수 있는 자산은 실제 사용 데이터, 정확한 평가 기준과 실패 사례, 기존 업무 흐름과의 깊은 통합, 신뢰할 수 있는 출처와 호환성 정보, 사용자 관계와 유통 경로, 지속적인 운영 체계다.

따라서 빠르게 만든 첫 구현은 시장 가설을 확인하는 수단일 수는 있어도 그 자체가 방어력은 아니다. 수익성은 `얼마나 빨리 만들었는가`보다 `사용하며 무엇이 축적되고 다음 개선을 더 어렵게 복제하게 만드는가`에 달려 있다.

#### ==근거 ④ — 설계 역량은 AI의 결정을 좁히고 검증 가능하게 만든다==

강의는 사람이 AI에 맡기기 전에 제품과 기술을 얼마나 구체적으로 정의했는지에 따라 결과의 유지보수성이 달라진다고 설명한다.

| 사람이 정하는 범위 | AI에 맡기는 범위 | 예상 결과 |
| --- | --- | --- |
| 큰 윤곽만 정함 | 제품 정의부터 구현까지 | 빠르지만 방향과 구조의 변동이 큼 |
| 제품을 상세히 정의 | 기술 선택과 구현 | 제품 의도는 선명하지만 기술 일관성은 불확실함 |
| 제품과 기술 스택을 정의 | 구조 설계와 구현 | 기술 선택의 범위가 좁아짐 |
| 구조·경계·검증 기준을 정의 | 정해진 단위의 코드 작성 | 결과를 따로 검사하고 교체하기 쉬움 |

핵심은 사람이 코드를 더 많이 작성해야 한다는 뜻이 아니다. **AI가 결정해도 되는 범위와 사람이 고정해야 하는 계약을 구분할 수 있어야 한다**는 뜻이다.

##### 보강 ① — 작은 단계가 아니라 바뀌는 결정을 기준으로 나눈다

강의는 설계 역량을 `큰 문제를 의존성 없는 작은 문제로 분할하는 능력`이라고 압축한다. 이 방향은 유용하지만 단순히 처리 순서나 작은 함수로 쪼개는 것만으로는 부족하다.

Parnas의 모듈 분해 원칙은 **어렵거나 바뀔 가능성이 큰 설계 결정을 먼저 찾고, 각 결정을 하나의 모듈 안에 숨기라**는 것이다. 모듈의 인터페이스는 내부 구현을 가능한 적게 드러내야 한다. 그래야 저장 방식이나 알고리즘이 바뀌어도 다른 모듈을 함께 수정하지 않는다.

```text
처리 순서대로 분할
입력 → 검색 → 정렬 → 출력

변경 지식으로 분할
저장 방식 | 검색 제공자 | 순위 정책 | 출력 형식
```

AI 코딩에서도 중요한 것은 작업 조각의 크기보다 **한 구현이 바뀔 때 함께 알아야 하는 지식의 범위**다. 모델 제공자, 벡터 저장소, 호환성 규칙처럼 자주 바뀌는 지식을 경계 안에 가두면 AI가 한 부분을 다시 만들어도 변경이 퍼지지 않는다.

##### 보강 ② — 독립된 작업에는 명확한 계약과 판정 기준이 필요하다

작업을 나눴더라도 입력·출력과 성공 조건이 없으면 AI는 빈틈을 매번 다르게 채운다. 각 단위에는 다음 계약이 필요하다.

- 받아야 할 입력과 반환할 출력
- 알아도 되는 지식과 몰라도 되는 구현 세부사항
- 실패를 표현하는 방식
- 성능·보안·호환성 같은 제약
- 결과를 통과시키는 자동 평가

최근 에이전트 평가 실무는 에이전트의 마지막 설명보다 **환경에 실제로 남은 결과**를 확인하라고 강조한다. 코딩 작업이라면 `완료했습니다`라는 응답이 아니라 타입 검사, 단위 테스트, 정적 분석, 빌드 결과가 판정 근거가 된다. 열린 품질은 기준표를 사용한 모델 평가와 사람 검토로 보완하고, 기존에 되던 동작이 깨지지 않았는지는 회귀 평가로 확인한다.

```text
명확한 계약
→ AI가 작은 단위 구현
→ 코드 기반 검사
→ 열린 품질 평가
→ 통과한 결과만 통합
```

##### 보강 ③ — AI는 기존 개발 체계를 증폭한다

DORA의 2025년 연구는 AI를 조직의 강점과 약점을 확대하는 증폭기로 설명한다. 모듈 경계·테스트·문서·피드백 체계가 좋으면 AI가 그 흐름을 가속하지만, 경계가 흐리고 검증이 약하면 더 많은 불일치와 재작업을 빠르게 만든다는 뜻이다.

LLM이 실제 프로젝트의 유지보수 문제를 고치는 능력을 조사한 2025년 연구에서도 일부 개선 가능성과 함께 많은 결과가 오류나 새로운 유지보수 문제를 만들었다. 또 CodeChain 연구는 복잡한 코딩 벤치마크에서 재사용 가능한 하위 모듈을 활용한 생성 방식이 모듈성과 정답률을 높일 수 있음을 보였다. 다만 이는 제한된 벤치마크 결과이므로 모든 실무 시스템의 장기 유지보수성을 보장하는 증거는 아니다.

이를 종합하면 설계 역량은 다음 순서로 구체화된다.

1. 사용자 가치와 성공 조건을 정의한다.
2. 바뀔 가능성이 큰 지식을 찾는다.
3. 그 지식을 경계 객체 안에 숨긴다.
4. 소비자가 알아야 할 계약만 노출한다.
5. 계약별 자동 평가와 회귀 검사를 둔다.
6. AI에는 이 경계 안의 구현을 맡긴다.

#### 응용 — 컴포넌트 추천 프로젝트

이 프로젝트의 사업 가치는 `AI로 추천한다`가 아니라 적절한 컴포넌트를 찾는 시간, 잘못된 조합의 재작업, 접근성·호환성 위반, 신규 개발자의 학습 시간이 실제로 줄어드는지로 검증해야 한다.

서비스 경계는 변하기 쉬운 지식을 기준으로 나눈다.

| 경계 | 안정적인 계약 | 안에 숨길 변동 지식 |
| --- | --- | --- |
| 의도 검색 | `retrieve(intent)` | 임베딩 모델·벡터 저장소·검색 옵션 |
| 목록 확인 | `resolve(componentId)` | API·CLI·파일 구조·문서 형식 |
| 사용례 검색 | `findUsages(componentIds)` | 코드 인덱스·프로젝트별 탐색 방법 |
| 호환성 판정 | `checkCombination(candidates)` | 버전·prop·접근성 규칙 |
| 조합 생성 | `propose(evidence)` | LLM 제공자·프롬프트·조합 전략 |
| 결과 검증 | `validate(example)` | 타입 검사·테스트·빌드 도구 |

현재의 근거 우선순위는 다음처럼 적용한다.

```text
호환성으로 불가능한 후보 제거
→ 실제 조합 사용례를 Base로 우선 제시
→ 프로젝트 조건에 맞춰 순위 조정
→ 근거가 겹치지 않는 성격의 대안도 생성
→ 타입 검사·테스트로 검증
```

평가도 경계별로 나눈다.

- **검색:** 정답 컴포넌트가 상위 후보에 포함되는가?
- **목록:** 존재하지 않는 컴포넌트를 제시하지 않는가?
- **사용례:** 실제 코드 위치와 조합을 정확히 연결하는가?
- **호환성:** 버전·prop·접근성 규칙을 모두 통과하는가?
- **다양성:** 이름만 다른 조합이 아니라 장단점이 다른 대안을 제안하는가?
- **실행:** 생성된 예제가 타입 검사·테스트·빌드를 통과하는가?

이렇게 하면 특정 LLM이나 벡터 저장소를 바꿔도 소비자 흐름은 유지되고, 각 단계의 성능과 비용을 따로 측정할 수 있다. 설계 역량은 AI보다 더 좋은 코드를 직접 쓰는 능력이 아니라 **AI가 만든 결과를 국소적으로 바꾸고 객관적으로 판정할 수 있는 구조를 만드는 능력**에 가깝다.

따라서 4강의 결론은 다음과 같다. **AI는 구현 비용을 낮추지만 경쟁자의 복제 비용도 낮춘다. 지속 가능한 가치는 검증 가능한 사업 효과, 사용하며 축적되는 고유 자산, 바뀌는 지식을 경계 안에 가두고 결과를 평가할 수 있게 만드는 설계 역량에서 나온다.**
