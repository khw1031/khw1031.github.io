## 프로젝트 아이디어

소상공인·1인 기업·소규모 스타트업이 범용 LLM이나 자동화 도구를 직접 조립하지 않고, `문의에서 예약까지`, `상담에서 견적 후속까지`처럼 검증된 업무 파이프라인을 자기 사업에 설치하도록 돕는 제품이다. 제작자는 앱의 작은 동작이 아니라 `서비스 정책 질문에 답변`, `예약 조건 수집`, `가능 시간 계산`, `예약 확정`처럼 사업 결과가 드러나는 업무 노드를 조합한다.

파이프라인은 고객에게 보여주기 위한 그림이 아니라 실제 실행 정의다. 시각화 화면은 실행 정의를 편집하거나 현재 상태를 보여주는 투영이다. 고객은 노드 캔버스를 직접 다루기보다 템플릿을 고르고, 템플릿이 요구하는 사업 데이터와 계정 연결을 제공하고, 시험 결과를 승인한 뒤 운영에 배포한다.

이 제품이 쉽게 만들어야 하는 것은 특정 RAG 제품 연결이 아니라 **고객 지식의 제공·정리·시험·배포 과정**이다. 하부 검색 기술과 벡터 저장소는 교체할 수 있어야 한다.

## 첫 사례: 상담에서 예약까지

```text
템플릿 선택
→ 서비스·가격·영업시간·예약·취소 정책 제공
→ 문서 추출과 누락·충돌 확인
→ 대표 상담 질문으로 시험
→ 고객 승인
→ 채팅 상담에 운영 지식 배포
→ 실제 예약 현황 조회
→ 시간 제안·예약 확정 또는 사람에게 전달
```

고객이 제공해야 하는 정보는 다음과 같다.

- 서비스 목록, 설명, 가격과 예상 소요 시간
- 영업시간, 휴무일, 담당자와 자원 제약
- 예약·변경·취소·환불 정책
- 자주 묻는 질문과 기존 안내 문서
- 자동으로 답하면 안 되는 항목과 사람 확인 기준
- 채팅 채널, 캘린더 또는 기존 예약 시스템 연결

모든 정보를 RAG에 넣지는 않는다.

| 정보 성격 | 처리 방식 | 예시 |
| --- | --- | --- |
| 설명형 지식 | 검색과 근거 인용 | 시술 설명, 준비 사항, 자주 묻는 질문 |
| 안정적인 사실 | 구조화된 데이터 | 가격, 소요 시간, 영업시간 |
| 의사결정 규칙 | 명시적인 Policy | 취소 가능 조건, 자동 확정 조건 |
| 계속 바뀌는 상태 | 원본 시스템 실시간 조회 | 빈 시간, 예약 상태, 재고 |
| 불확실하거나 위험한 항목 | 사람에게 전달 | 문서 충돌, 예외 할인, 의료·법률 판단 |

## 사용자와 제작자

| 역할 | 책임 |
| --- | --- |
| 플랫폼 제작자 | 실행 엔진, 데이터 수집, 지식 검색, 승인, 관측, 보안과 공통 Adapter를 만든다. |
| 업무 템플릿 제작자 | 업종 사례를 업무 노드, 필요한 데이터 명세, 기본 Policy, 시험 시나리오로 만든다. 초기에는 내부 운영자가 맡는다. |
| 고객 관리자 | 자기 사업의 문서·정책·서비스 연결을 제공하고 추출 결과와 운영 배포를 승인한다. |
| 현장 사용자 | 별도 설계 없이 채팅·예약·업무 화면에서 결과와 확인 요청을 처리한다. |

장기적으로 외부 전문가나 도입 파트너가 템플릿 제작자가 될 수 있다. 그러나 고객 데이터와 자격 증명을 포함하지 않은 `WorkflowTemplate`만 배포할 수 있어야 한다. 고객에게 설치할 때 템플릿 버전, 고객 데이터, 연결 계정과 Policy가 `SolutionInstance`로 묶인다.

## 기능 요구사항

### 1. 템플릿 발견과 설치

- 고객은 업종보다 해결하려는 업무 결과로 템플릿을 찾아야 한다.
- 템플릿은 필요한 데이터, 지원하는 서비스 연결, 사람 승인 지점, 예상 결과와 제한을 설치 전에 보여줘야 한다.
- 설치 전 현재 도구 조합을 `바로 설치 가능 / 다른 연결로 가능 / 현재 지원하지 않음`으로 판정해야 한다.

### 2. 고객 데이터 받기

- 첫 MVP는 Markdown을 유일한 문서 입력 형식으로 지원한다. 고객에게 `.md` 파일 작성을 요구하지 않고 웹 편집기, 복사·붙여넣기와 Markdown 파일 업로드를 제공하며 결과는 Markdown으로 저장한다.
- PDF·DOCX·스프레드시트·웹페이지·외부 저장소는 수요가 확인된 뒤 각각의 Source Adapter로 추가한다.
- 캘린더·예약·CRM처럼 계속 바뀌는 데이터는 파일로 복사하지 않고 원본 시스템을 연결해야 한다.
- 템플릿이 요구하는 항목과 고객이 제공한 항목을 비교해 누락과 충돌을 알려야 한다.
- 추출 결과를 고객이 직접 수정하고 승인할 수 있어야 한다.

### 3. 지식 시험과 배포

- 새 자료는 바로 운영에 반영하지 않고 초안 버전을 만들어야 한다.
- 템플릿이 포함한 대표 질문과 고객이 추가한 질문으로 검색 결과, 답변, 출처와 사람 전환 여부를 시험해야 한다.
- 시험 결과를 고객이 승인하면 운영 버전으로 배포해야 한다.
- 운영 버전은 이전 버전으로 되돌릴 수 있어야 하며, 어느 실행이 어떤 버전을 사용했는지 남겨야 한다.

### 4. 파이프라인 실행

- 업무 노드는 입력, 출력, 선행 조건, Policy, 성공 기준, 실패 처리와 사람 승인 조건을 가져야 한다.
- 장시간 대기, 재시도, 중복 이벤트와 외부 서비스 오류를 처리해야 한다.
- 한 실행이 현재 어느 단계인지, 왜 멈췄는지, 다음에 무엇이 필요한지 보여줘야 한다.
- 사람 승인이 필요한 건은 한 화면에 모으고 승인 이후 같은 실행을 이어가야 한다.

### 5. 운영과 개선

- 실행 성공률, 사람 전환률, 응답 시간, 예약 완료율, 오류 유형과 사용 비용을 기록해야 한다.
- 반복되는 고객별 수정은 템플릿의 공통 개선과 고객 전용 설정으로 구분해야 한다.
- 템플릿을 새 버전으로 올릴 때 고객별 차이와 영향 범위를 먼저 보여줘야 한다.

## 고객 UI 요구사항

초기 고객 UI는 캔버스보다 설치와 운영에 집중한다.

1. `템플릿 선택` — 해결할 업무, 필요한 데이터와 연결, 사람 승인 지점을 확인한다.
2. `정보 제공` — 웹 편집기에 직접 작성하거나 기존 내용을 붙여넣고, 필요한 경우 Markdown 파일을 올린다. 실시간 운영 계정을 연결하며 누락 항목은 폼으로 채운다.
3. `추출 결과 확인` — 서비스·가격·정책과 충돌 항목을 수정한다.
4. `시험` — 대표 질문과 예약 시나리오의 답변·출처·실행 결과를 확인한다.
5. `활성화` — 승인한 지식 버전과 파이프라인 버전을 운영에 배포한다.
6. `운영 현황` — 처리 중·완료·실패·확인 대기 건과 성과 지표를 본다.

노드 캔버스는 내부 제작자와 고급 파트너용으로 둔다. 고객에게는 업무 단계와 상태를 단순한 단계 목록이나 타임라인으로 보여준다.

## 기술적 요구사항

### 실행 정의와 배포 단위

- `WorkflowTemplate`: 버전이 있는 업무 단계와 전이 정의
- `NodeDefinition`: 업무 노드의 입력·출력·Policy·승인·성공·실패 계약
- `KnowledgeRequirement`: 템플릿이 요구하는 지식과 필수 필드
- `SolutionInstance`: 템플릿과 고객 설정을 결합한 배포 단위
- `KnowledgeBinding`: 특정 노드가 사용할 고객 지식과 운영 버전 연결
- `AdapterConnection`: 채팅·캘린더·예약·CRM 연결과 권한 범위
- `WorkflowRun`, `NodeRun`, `ApprovalTask`: 실행 기록과 사람 개입 상태

실행 정의는 버전이 있는 JSON 또는 YAML로 저장하고 런타임이 직접 해석해야 한다. 화면의 노드 위치나 모양은 실행 의미와 분리한다.

### 문서 입력 경계와 정규화

문서 형식과 내부 지식 모델을 같은 것으로 고정하지 않는다. 애플리케이션이 소유하는 `KnowledgeSourcePort`를 먼저 정의하되, 첫 MVP에서는 `MarkdownSourceAdapter` 하나만 구현한다. ==지원 형식은 Markdown으로 좁히고, 다른 형식을 추가할 확장 경계는 처음부터 둔다.==

```text
웹 편집기·붙여넣기·Markdown 파일
→ MarkdownSourceAdapter
→ NormalizedDocumentV1
→ 검증
→ 초안 버전 생성
→ 분할·임베딩·색인
→ 대표 질문 시험
→ 고객 승인·운영 배포
```

```ts
interface KnowledgeSourcePort {
  ingest(input: SourceInput): Promise<NormalizedDocumentV1[]>;
}

interface NormalizedDocumentV1 {
  sourceId: string;
  tenantId: string;
  version: number;
  title: string;
  bodyMarkdown: string;
  metadata: {
    sourceType: string;
    checksum: string;
    effectiveAt?: string;
    expiresAt?: string;
  };
}
```

Markdown은 첫 버전의 본문 표현일 뿐 고객·원본·권한·시행일·만료일·체크섬과 수집 상태는 별도 메타데이터로 관리한다. 파일 경로나 파일 이름을 자료의 영구 식별자로 사용하지 않는다. 나중에 PDF 페이지, 스프레드시트 셀, 웹 문단처럼 세밀한 출처 위치가 필요해지면 `NormalizedDocumentV2`를 블록 구조로 확장한다.

추가 형식은 기존 파이프라인을 바꾸지 않고 같은 Port를 구현하는 Adapter로 연결한다.

```text
PdfSourceAdapter ─────────┐
DocxSourceAdapter ────────┼→ NormalizedDocument → 공통 지식 처리 파이프라인
WebPageSourceAdapter ─────┤
ExternalStoreAdapter ─────┘
```

이 Adapter들은 수요가 생기기 전에는 구현하지 않는다. 첫 MVP의 기술 범위에는 `MarkdownSourceAdapter`만 포함한다.

문서 지식과 실시간 운영 데이터도 같은 Port에 넣지 않는다.

| 데이터 종류 | Port | 처리 방식 |
| --- | --- | --- |
| 설명·FAQ·안내 문서 | `KnowledgeSourcePort` | 정규화한 뒤 검색·RAG에 사용 |
| 가격·서비스·영업시간 | `StructuredDataPort` | 필드와 규칙으로 검증·조회 |
| 빈 시간·예약·재고 상태 | `OperationalDataPort` | 원본 시스템에서 실시간 조회 |

### 지식 수집과 검색

- 문서 입력 방식은 `KnowledgeSourcePort`로, 검색 엔진은 별도의 `RetrievalPort`로 추상화한다. 입력 형식 Adapter와 검색 구현 Adapter를 섞지 않는다.
- 파싱·분할·임베딩·색인은 비동기로 실행하며 상태, 실패 원인과 재시도를 제공한다.
- 검색 엔진은 Adapter 뒤에 두어 벡터 검색, 키워드 검색과 하이브리드 검색 구현을 바꿀 수 있게 한다.
- 검색 결과는 출처, 원문 위치, 점수, 적용 필터와 사용한 지식 버전을 반환해야 한다.
- 고객, 지점, 문서 유형, 시행일과 권한에 따른 강제 필터를 지원해야 한다.
- 문서 삭제와 운영 중단 시 파생된 조각과 색인도 추적해 제거할 수 있어야 한다.

### 실행 안정성과 보안

- 고객 데이터, 실행 기록, 연결 자격 증명과 검색 범위를 Tenant 단위로 격리한다.
- 자격 증명은 암호화 저장하고 실행 시 필요한 최소 권한만 제공한다.
- 외부 쓰기 작업은 중복 실행을 막는 식별자와 감사 기록을 가져야 한다.
- 노드별 시간 제한, 재시도, 보상 처리, 중단과 재개를 지원해야 한다.
- 모델 입력·출력과 외부 쓰기 작업은 민감정보 정책과 보존 기간을 따로 설정할 수 있어야 한다.

### 구현 경계

- React Flow 같은 도구는 제작자용 캔버스를 구현하는 후보일 뿐, 실행 엔진이 아니다.
- n8n 같은 도구는 하위 앱 동작 실행기나 초기 Adapter 구현으로 사용할 수 있지만 업무 템플릿과 고객별 배포 단위의 원본이 되어서는 안 된다.
- AI SDK는 채팅 스트리밍, 구조화된 출력과 도구 호출 UI에 사용할 수 있지만 워크플로우 상태, 지식 색인과 승인 생애주기는 별도 애플리케이션 계층이 소유한다.
- 특정 클라우드의 Knowledge Base 제품은 교체 가능한 지식 처리 구현 후보이며 제품 요구사항 자체가 아니다.

## 첫 MVP 범위

- 고객 유형: 상담 문의와 시간 예약이 반복되는 한 업종
- 입력 채널: 웹 채팅 한 개
- 운영 연결: 캘린더 또는 단순 예약 원장 한 개
- 고객 데이터: 서비스·가격표, 운영 정책, 자주 묻는 질문, 영업시간
- 문서 입력: 웹 편집기, 복사·붙여넣기, Markdown 파일 업로드. 세 방식은 모두 `MarkdownSourceAdapter`를 통과한다.
- 업무 흐름: 문의 분류 → 정책 답변 → 예약 조건 수집 → 빈 시간 조회 → 제안 → 승인 또는 확정
- 지식 관리: Markdown 정규화, 초안, 대표 질문 시험, 고객 승인, 운영 버전 한 개와 되돌리기
- 운영 화면: 실행 목록, 단계별 상태, 근거, 확인 요청과 기본 성과 지표
- 제작 방식: 내부 제작자가 코드 또는 제한된 편집 화면으로 템플릿을 만든다.

MVP에서는 PDF·DOCX·스프레드시트·웹페이지 자동 변환, 외부 문서 저장소 동기화, 공개 템플릿 장터, 모든 업종 지원, 고객 자유 캔버스, 자체 벡터 데이터베이스 개발과 복수 예약 채널 동시 지원을 제외한다.

## 초기 성공 기준 초안

- 신규 고객이 도움 없이 30분 안에 필수 자료와 연결을 제공할 수 있는가
- 대표 질문 20개에서 근거 출처와 사람 전환이 의도대로 작동하는가
- 문서에 없는 내용이 예약 확정이나 외부 쓰기로 이어지지 않는가
- 고객이 실행 실패 이유와 필요한 다음 행동을 운영 화면에서 이해할 수 있는가
- 두 번째 고객 설치에서 새 코드보다 설정으로 해결되는 비율이 높아지는가
- 템플릿 또는 지식 버전을 바꾼 뒤 이전 버전으로 안전하게 되돌릴 수 있는가

## 더 해볼 질문

- 첫 업종은 상담량, 예약 규칙의 복잡도, 기존 시스템 연결 가능성 중 무엇을 기준으로 고를 것인가?
- 고객에게 문서 업로드와 구조화된 폼 입력을 어느 순서로 제시해야 가장 적은 수정으로 정확한 지식을 얻는가?
- 대표 질문 시험의 합격 기준과 자동 처리 중단 기준을 누가 어떻게 정할 것인가?
- 고객별 지식 색인을 완전히 분리할지, 공유 색인에 강제 Tenant 필터를 적용할지 어떤 조건으로 결정할 것인가?
- 템플릿 제작자가 지원해야 하는 최소 도구와 시험 규약은 무엇인가?
- 고객이 실제로 돈을 내는 단위는 템플릿 설치, 월간 실행·운영, 새 버전 업데이트 중 무엇인가?
