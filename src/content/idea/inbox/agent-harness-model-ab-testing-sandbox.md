## 아이디어

사용자가 자기 에이전트 하네스(시스템 프롬프트, 규칙 파일, 스킬·툴 정의, 권한 설정, 서브에이전트 구성 일체)를
통째로 업로드하면, 도구가 그것을 Docker 같은 격리 환경에 심고 **컨텍스트가 완전히 초기화된 상태**에서
같은 과제를 여러 모델로 돌린다. 하네스는 상수로 고정하고 모델만 바꾸는 A/B(혹은 N-way) 실험이다.
결과로는 최종 산출물뿐 아니라 궤적 — 툴 호출 순서, 재시도, 규칙을 어디서 어긴 뒤 언제 회복했는지,
토큰·시간·비용 — 을 나란히 놓은 비교 리포트를 낸다.

지금 공개 리더보드는 "어느 모델이 좋은가"를 답하지만 실무에서 알고 싶은 건 "**내** 하네스에서 어느 모델이
좋은가"다. 같은 모델이 하네스만 바꿔도 순위가 뒤집히는 사례가 이미 관측되고 있어서
(Terminal-Bench 2.1은 이 혼동을 막으려고 Agent Org와 Model Org 열을 분리해 놓았다), 하네스를 실험 단위로
고정한 채 모델을 스왑하는 자리는 비어 있는 편이다. 컨텍스트 초기화와 컨테이너 격리는 여기서 부가 기능이
아니라 실험 타당성의 전제다 — 이전 세션의 잔여 상태나 로컬 환경 차이가 남으면 측정한 차이가 모델 차이라고
말할 수 없다.

## 더 해볼 질문

- "하네스"의 경계를 어디까지로 정의할 것인가. 프롬프트·규칙 파일까지인가, MCP 서버·툴 바이너리·저장소
  스냅샷까지인가. 경계를 넓힐수록 재현성은 올라가고 업로드 마찰은 커진다.
- 판정 기준을 무엇으로 삼는가. 최종 산출물 정답(테스트 통과 등)만 볼지, 궤적 품질(불필요한 툴 호출,
  규칙 위반 횟수)까지 점수화할지. 후자는 LLM-judge가 필요해지고 judge 모델 편향 문제가 따라온다.
- 비결정성을 몇 회 반복으로 눌러야 유의미한 차이라고 말할 수 있는가. pass@1 × 3회가 관행인데,
  개인 사용자가 감당할 비용 안에서 그 반복이 가능한가.
- 사용자 하네스에는 내부 저장소·API 키·비공개 프롬프트가 섞이기 쉽다. 업로드 시 비밀값 처리와 실행
  네트워크 정책을 어떻게 잡을 것인가. 로컬 전용 CLI로 시작하고 호스팅은 나중에 두는 선택지도 있다.
- 이미 있는 것으로 충분한가. Inspect는 외부 에이전트를 Docker 샌드박스에서 돌릴 수 있고, promptfoo는
  모델 매트릭스 비교를 하고, Terminal-Bench는 하네스별 리더보드를 낸다. 이 도구의 차별점이
  "조립 비용 제거(UX)"인지 "새로운 측정(하네스 고정 N-way)"인지 정해야 한다.
- 과제 셋은 누가 주는가. 사용자가 자기 실제 작업을 가져오게 할 것인가, 도구가 표준 과제 팩을 제공할 것인가.
  전자는 관련성이 높고 후자는 비교 가능성이 높다.
- 모델 접근은 사용자 키(BYOK)인가 도구 크레딧인가. 벤더별 레이트리밋과 가격 차이가 실험 설계를 제약한다.

## 레퍼런스·서비스

확인일: 2026-08-08. 아래는 빠른 스캔이며 1차 검증은 하지 않았다.

- [Inspect (UK AISI)](https://inspect.aisi.org.uk/) — 1차. AISI의 오픈소스 eval 프레임워크. Docker/K8s
  샌드박스가 내장이고 Claude Code·Codex CLI 같은 **외부 에이전트를 그대로 태울 수 있다**고 밝히고 있어,
  이 아이디어의 실행 계층 후보이자 가장 가까운 경쟁자다.
- [inspect_evals (UKGovernmentBEIS)](https://github.com/UKGovernmentBEIS/inspect_evals) — 1차.
  Inspect용 eval 모음 저장소. 과제 팩을 직접 만들지 않고 빌려올 수 있는지 확인할 지점.
- [Harness-Bench (arXiv 2605.27922)](https://arxiv.org/html/2605.27922v1) — 1차(원논문). 여러 하네스 ×
  여러 모델 백엔드로 하네스 효과를 통제 측정한 벤치마크. 이 아이디어가 재발명이 아닌지 판단할 때 먼저 읽을 것.
- [terminal-bench (harbor-framework)](https://github.com/harbor-framework/terminal-bench) — 1차.
  터미널 과제 벤치마크 정본 저장소. Terminus 2 하네스 + 샌드박스 실행 구조가 참고 설계다.
- [Terminal-Bench 리더보드](https://www.tbench.ai/leaderboard/terminal-bench/2.0) — 1차.
  Agent Org / Model Org를 분리 표기하고 궤적을 공개한다. "모델 승리 ≠ 하네스 승리" 분리 표기의 선례.
- [Terminal-Bench v2.1 (Artificial Analysis)](https://artificialanalysis.ai/evaluations/terminalbench-v2-1)
  — 2차. Terminus 2 + e2b 샌드박스, pass@1 3회 평균이라는 실행 규약을 요약해 둔 페이지. 반복 횟수 관행의 근거.
- [Braintrust](https://www.braintrust.dev/) — 1차(벤더). 데이터셋 우선·모델 무관 실험 플랫폼,
  샌드박스 커스텀 스코어러 제공. 상용 대체재 라인의 기준점.
- [promptfoo](https://www.promptfoo.dev/) — 1차(벤더). 오픈소스 CLI로 프롬프트·모델 매트릭스 비교와
  CI 통합. 비교 UX의 참고 대상. (2026년 인수 관련 언급을 2차 자료에서 봤으나 미확인 — 인용 전 확인 필요.)
- [LLM eval 프레임워크 비교 (aiml.qa)](https://aiml.qa/llm-evaluation-framework-benchmark-2026/) — 2차.
  DeepEval·RAGAS·promptfoo·Braintrust·LangSmith 포지셔닝 개괄. 시장 지도 용도로만.
- [Agent 시스템·하네스 설계 서베이 (arXiv 2606.20683)](https://arxiv.org/pdf/2606.20683) — 1차(서베이 논문).
  하네스 설계 공간 정리. "하네스"의 경계를 정의할 때 쓸 어휘 출처.
