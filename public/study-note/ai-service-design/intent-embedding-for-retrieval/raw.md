
> 한 줄: 검색은 질의 벡터와 저장 벡터의 유사도로 일어나므로, **의도로 묻는다면 저장 대상도 의도의 언어로 임베딩돼 있어야** 같은 의미 공간에서 만난다 — 구조(무엇으로 이뤄졌나)는 벡터가 아니라 메타데이터로 빠진다.

## 큰 그림

같은 대상을 두 방식으로 임베딩하면 질의와 만나는지가 갈린다.

```text
질의: "결제 실패를 알리고 재시도를 유도하는 화면"   (자연어 의도)
                    │ 유사도
     ┌──────────────┴──────────────┐
     ▼                             ▼
저장 벡터 A                    저장 벡터 B
"Modal, Primary Button,       "결제가 실패했을 때 원인을 알리고
 Body Text"                    즉시 재시도를 유도하는 경고형 모달…"
   = 구조의 언어                  = 의도의 언어
   → 다른 의미 공간, 안 걸림        → 매칭됨
```

## 핵심

도서관에서 "슬플 때 읽을 책"을 물었는데 목록이 **판형·쪽수·표지 색**으로만 정리돼 있으면 답을 찾을 수 없다. 물음의 언어와 목록의 언어가 다르기 때문이다. 임베딩 검색도 똑같다 — 기획자가 의도·용도로 묻는다면, 저장된 컴포넌트 조합도 생김새·코드가 아니라 **"그 조합이 어떤 상황에서 무슨 목적으로 쓰이는가"**라는 의도 서술로 임베딩돼야 한다.

메커니즘은 **query-document 정렬** 문제다. 유사도는 두 벡터가 같은 의미 공간에 있을 때만 의미를 가진다. 저장 벡터가 `Modal + Button + Text` 같은 구조로 만들어져 있으면 자연어 의도 질의와 다른 공간이라 점수가 맞지 않는다. 그래서 손댈 곳은 검색 알고리즘이 아니라 **벡터화 대상 자체**다 — 대상을 의미가 담긴 텍스트로 바꾼 뒤 임베딩하는, 상품을 문장으로 만들어 임베딩하던 것과 같은 수법이다.

임베딩할 텍스트에 담을 것 네 가지.

| 넣을 것 | 예 |
| --- | --- |
| 용도·맥락 | 어떤 플로우·화면·사용자 상태에서 쓰나 |
| 기획 의도 | 전환 유도 / 경고 / 확인 / 안심 등 목적 |
| 조합의 UX 의미 | 개별 컴포넌트가 아니라 **조합이 만드는 경험** |
| 제약(do/don't) | 언제 쓰면 안 되는가 |

최소 예시 — "결제 실패 다이얼로그".

- **나쁜 벡터화:** `"Modal, Primary Button, Body Text"` (구조만) → "결제 실패 알림" 질의에 안 걸린다.
- **좋은 벡터화:** `"결제가 실패했을 때 원인을 알리고 즉시 재시도나 카드 변경을 유도하는 경고형 모달. 부정적 상황이라 강한 주 액션 1개 + 보조 액션. 성공·축하 맥락엔 쓰지 않음."` → 기획자의 의도 질의와 정확히 매칭된다.

구조(어떤 컴포넌트로 이뤄졌나)는 벡터에 넣지 않고 메타데이터로 따로 둬 **필터**에 쓴다.

## 깊이

**가장 중요한 함정 — 구조 유사 ≠ 의도 유사.** 시각적으로 똑같은 모달이 "가입 축하"와 "계정 삭제 경고"라는 **정반대 의도**일 수 있다. 생김새로 벡터화하면 이 둘이 벡터 공간에서 가까워져 오작동한다. 뒤집어 말하면, 의도가 벡터에 담기지 않은 상태에서 "의도대로 동작"하기를 기대하는 것은 튜닝 부족이 아니라 **원리적으로 불가능**하다. 검색 품질이 안 나올 때 임베딩 모델을 바꾸기 전에 무엇을 텍스트로 써 넣었는지를 먼저 본다.

**세 용도 축이 설계를 갈라놓는다.** 무엇을 하려는지에 따라 필요한 장치가 다르다.

- **Retriever(검색)** — "이 의도에 맞는 기존 조합 찾아줘" → 의도 임베딩의 유사도 검색.
- **Decision(판단)** — "이 맥락엔 A조합 vs B조합 중 뭐?" → 의도 벡터 + 규칙·분류.
- **Generation(생성)** — "이 의도 서술로 조합을 만들어줘" → LLM이 의도를 받아 컴포넌트를 조립.

**실무 답은 대개 하이브리드다.** 의도(벡터 검색) + 구조·토큰·플랫폼(메타데이터 필터) + do/don't 규칙(재랭킹·게이트)을 겹친다. 이유는 하나의 벡터가 감당할 수 있는 축이 하나이기 때문이다 — 벡터 하나에 의도·구조·제약을 다 밀어넣으면 셋 다 흐려진다. 필터는 "이 플랫폼에서 쓸 수 있는 것"처럼 참·거짓이 분명한 조건을, 재랭킹은 "이 맥락에선 쓰지 말라"는 제약을 각각 자기 방식으로 처리하는 편이 정확하다.

**갈림길 — 질의를 자유서술로 볼 것인가 정해진 축으로 볼 것인가.** 이 선택이 설계 전체를 가른다. 기획자가 자연어 의도로 묻는다고 상정하면 **임베딩 중심**(의도 서술 품질이 곧 검색 품질)이 되고, 목적=경고·강도=높음 같은 정해진 축·태그로 묻는다고 상정하면 **구조화 태그 + 필터 중심**이 된다. 둘은 필요한 데이터 작업이 다르므로(전자는 조합마다 의도 서술 작성, 후자는 태그 체계 합의) 먼저 정하지 않으면 양쪽을 반씩 만들다 끝난다.

**대가 — 의도 서술은 사람이 써야 한다.** 구조는 코드에서 자동 추출할 수 있지만 "무슨 목적으로 쓰이는가"는 대체로 추출되지 않는다. 그래서 이 설계의 실제 비용은 벡터 DB가 아니라 **조합마다 의도 서술을 쓰고 유지하는 작업**이고, 서술이 낡으면 검색은 조용히 틀린 것을 잘 찾아 준다.

## 용어 풀이

- **질의·문서 정렬(query-document alignment)** — 질의와 저장 문서가 같은 의미 공간·같은 언어로 표현돼야 유사도가 성립하는 조건. 깨짐: 검색 실패를 모델 성능 문제로만 보면 이 조건을 점검하지 않는다.
- **의도 서술(intent description)** — 대상의 용도·목적·맥락·제약을 사람이 쓰는 자연어 서술. 깨짐: 컴포넌트 설명 문서와 동일시. 임베딩 대상은 "무엇인가"가 아니라 "언제 왜 쓰나"다.
- **메타데이터 필터(metadata filter)** — 벡터가 아닌 구조·플랫폼·토큰 값으로 후보를 참·거짓으로 걸러내는 것. 깨짐: 벡터에 함께 넣으면 필터의 정확성과 의도 유사도가 둘 다 흐려진다.
- **재랭킹(reranking)** — 1차 검색 결과를 규칙이나 별도 모델로 다시 정렬·차단하는 단계. 깨짐: 유사도 임계값 조정으로 대체 가능하다고 보면 do/don't 같은 조건부 제약을 표현할 수 없다.
- **하이브리드 검색(hybrid retrieval)** — 벡터 검색과 필터·규칙을 겹쳐 쓰는 구성.

## 확인 질문

1. 의도 질의에 컴포넌트 조합이 안 걸릴 때, 임베딩 모델 교체보다 먼저 볼 곳은? <details><summary>답</summary>무엇을 텍스트로 써서 임베딩했는지. 저장 벡터가 구조(컴포넌트 목록·코드)의 언어로 만들어져 있으면 질의와 다른 의미 공간이라 어떤 모델을 써도 정렬되지 않는다. 용도·기획 의도·조합의 UX 의미·제약을 서술로 넣는 것이 선행 조건이다.</details>
2. "가입 축하 모달"과 "계정 삭제 경고 모달"이 검색에서 서로 섞여 나온다. 무슨 일이 일어난 것인가? <details><summary>답</summary>구조·생김새 기준으로 벡터화돼 있다는 신호다. 두 조합은 구조가 거의 같지만 의도가 정반대이므로, 구조 임베딩에서는 가까울 수밖에 없다. 의도 서술을 벡터에 담고 구조는 메타데이터로 내려야 갈라진다.</details>
3. (본문 밖) 팀이 "의도, 구조, 플랫폼, do/don't를 한 문단으로 합쳐 임베딩했더니 검색이 전반적으로 애매해졌다"고 한다. 왜 그렇고 어떻게 나누겠나? <details><summary>답</summary>한 벡터가 여러 축을 동시에 표현하면 축들이 서로 상쇄되어 어느 축으로도 선명하지 않다. 의도만 벡터에 남기고, 플랫폼·구조처럼 참·거짓이 분명한 조건은 메타데이터 필터로, do/don't 제약은 재랭킹·게이트 단계로 분리한다.</details>
