### 독립적 문제 분할이 유지보수와 바이브 코딩의 오류 범위를 줄이는 구조

**핵심:** 문제를 독립적으로 변경하고 검증할 수 있는 작은 단위로 나누면 한 변경의 영향 범위가 제한되어 유지보수가 쉬워진다. 바이브 코딩에서는 AI가 한 번에 추론해야 할 맥락과 가정도 줄어들어 생성 오류를 발견하고 되돌리기 쉬워진다.

#### 유지보수 효과

유지보수의 어려움은 코드의 양보다 한 부분을 바꿨을 때 어디까지 함께 바뀌는지 알기 어렵다는 데서 생긴다. 입력·출력과 책임이 명확한 독립 단위는 변경 범위를 경계 안에 가두어 다음을 가능하게 한다.

1. **변경 전파 제한:** 한 구현의 변경이 무관한 코드까지 번지지 않는다.
2. **국소적 이해:** 전체 시스템을 머리에 올리지 않고도 한 부분을 고칠 수 있다.
3. **독립적 검증:** 작은 입력과 기대 출력으로 테스트할 수 있다.
4. **부분 교체와 복구:** 실패한 단위만 교체하거나 이전 상태로 되돌릴 수 있다.

#### 주문 기능 예시

```text
가격 계산: 장바구니와 할인 정책 → 최종 금액
주문 저장: 주문 객체 → 저장 결과
결제 실행: 결제 요청 → 승인 또는 실패
화면 표시: 주문 결과 → 사용자에게 보여 줄 정보
```

각 단위의 계약이 명확하면 할인 정책이 바뀔 때 가격 계산과 해당 테스트만 수정할 수 있다. 결제 업체를 바꾸더라도 화면이나 할인 규칙은 결제 업체의 응답 형식을 몰라도 되며, 문제가 생기면 어느 경계에서 잘못됐는지 좁혀 볼 수 있다.

#### 바이브 코딩에서 중요한 이유

LLM은 명세를 엄밀하게 실행하는 컴파일러가 아니라 주어진 맥락에서 빈칸을 확률적으로 메우는 생성기다. “주문 기능 전체를 만들어 줘”처럼 범위가 크면 데이터 구조, 오류 처리, 상태 관리, 외부 API 형식까지 많은 결정을 동시에 추측한다. 이 추측들이 서로 의존하면 초반의 작은 오해가 뒤 코드의 전제가 된다.

반대로 한 번에 하나의 독립된 문제와 판정 기준을 주면 작업 범위가 명확해진다.

```text
요청: 할인 정책에 따라 최종 금액을 계산한다
계약: Cart와 DiscountPolicy를 받고 Money를 반환한다
판정: 정상 할인, 중복 할인, 최소 금액 경계 테스트를 통과한다
수정 범위: 가격 계산 모듈과 해당 테스트
```

이 범위에서는 AI가 추측할 것이 적고 사람도 결과 전체를 검토할 수 있다. 실패 원인을 해당 단위에서 찾고 잘못 생성된 변경만 버릴 수 있다. 따라서 작은 독립 문제는 AI의 성능을 높이는 기법이라기보다 **AI가 틀릴 수 있다는 전제 아래 오류의 발생 범위와 검증 비용을 제한하는 운영 방식**이다.

#### 좋은 분할의 판정 기준

함수나 파일을 많이 만드는 것만으로 독립성이 생기지는 않는다. 여러 단위가 같은 전역 상태를 몰래 바꾸거나 한 변경에 여러 파일을 항상 함께 고쳐야 한다면 이름만 나뉜 것이다. 반대로 지나치게 잘게 나누면 파일 탐색과 연결부가 늘어 이해가 더 어려워질 수 있다.

> 이 단위의 내부 구현이 바뀌어도 소비자는 작은 계약만 알면 되는가? 그리고 이 단위 하나만 따로 검증할 수 있는가?

두 질문에 모두 그렇다고 답할 수 있을 때 유지보수와 바이브 코딩에 유효한 분할에 가깝다.

### 독립적 모듈 설계와 관련 방법론의 범위별 지도

**핵심:** 변경될 가능성이 있는 설계 결정이 다른 부분에 드러나지 않도록 시스템을 나누는 **정보 은닉 기반 모듈화**가 독립적 변경·검증 단위라는 생각에 가장 가까운 기존 개념이다. 명시적 계약과 테스트까지 포함해 표현하면 **계약과 독립 검증을 갖춘 모듈 설계**라고 부를 수 있다.

#### 중심 개념

David Parnas는 시스템을 처리 순서가 아니라 변경될 가능성이 있는 설계 결정을 숨기는 기준으로 모듈화해야 한다고 설명했다. 이 기준은 구현의 변화가 모듈 경계 밖으로 전파되지 않게 한다.

- [Parnas, 「On the Criteria To Be Used in Decomposing Systems into Modules」](https://doi.org/10.1145/361598.361623) — 1차 자료, 1972년 원문, 2026-08-13 확인.

#### 방법론별 적용 범위

| 범위 | 관련 개념·방법론 | 맡는 역할 |
| --- | --- | --- |
| 구현 구조 | 정보 은닉, 높은 응집도·낮은 결합도 | 변경될 지식을 모듈 내부에 모으고 변경 전파를 제한한다. |
| 모듈 간 경계 | Design by Contract | 입력, 출력, 사전·사후 조건을 명시해 소비자가 알아야 할 계약을 고정한다. |
| 구현·검증 과정 | TDD | 독립된 작은 동작을 테스트로 먼저 규정하고 구현한다. |
| 기능 분할 | Vertical Slicing | 사용자에게 의미 있는 기능을 작고 완결된 단위로 구현한다. |
| 큰 도메인의 경계 | DDD의 Bounded Context | 큰 모델을 내부적으로 일관된 여러 문맥으로 나눈다. |

관련 근거는 다음과 같다.

- [Bertrand Meyer의 Design by Contract 논문](https://www.kth.se/social/files/59526bfb56be5b4f17000807/meyer-92-contracts.pdf) — 1차 자료, 1992년 원문, 2026-08-13 확인.
- [Agile Alliance의 Vertical Slicing 사례](https://agilealliance.org/resources/experience-reports/a-tale-of-slicing-and-imagination/) — 2차 자료, 2026-08-13 확인.
- [Martin Fowler의 Bounded Context 설명](https://martinfowler.com/bliki/BoundedContext.html) — 2차 자료, 2014-01-15 게시본, 2026-08-13 확인.

#### 이름 선택

하나의 표현으로 묶으면 **계약과 독립 검증을 갖춘 모듈 설계**, 기존 용어로 더 짧게 부르면 **정보 은닉 기반 모듈화**가 가장 정확하다. SOLID의 단일 책임 원칙도 관련 있지만 전체 개념을 대표하기에는 범위가 더 좁다.
