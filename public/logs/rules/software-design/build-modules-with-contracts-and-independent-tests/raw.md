
**규칙:** 각 기능을 변경 가능성이 같은 책임끼리 묶고, 명시적 입출력 계약과 독립 테스트를 갖춘 모듈로 구현하라

## 왜

유지보수 비용은 코드의 양보다 한 변경이 어디까지 전파되는지 알기 어려울 때 커진다. 변할 이유가 같은 책임을 한 모듈 안에 모으고 내부 구현을 계약 뒤에 숨기면, 변경의 영향 범위를 해당 모듈로 제한할 수 있다. 입력과 출력이 명시되어 있고 모듈만 따로 테스트할 수 있으면 전체 시스템을 이해하지 않고도 수정·검증·교체·복구할 수 있다.

이 규칙은 **정보 은닉에 기반한 모듈 설계**를 중심으로 **Design by Contract**와 **TDD**의 검증 방식을 결합한다. 사용자 가치 단위로 작업을 나눌 때는 **Vertical Slicing**, 큰 도메인의 모델 경계를 나눌 때는 **DDD의 Bounded Context**로 확장할 수 있다.

바이브 코딩에서는 이 경계가 더 중요하다. AI가 한 번에 추측해야 할 데이터 구조, 상태, 예외 처리와 외부 표현을 줄이고, 생성 결과의 합격 여부를 작은 테스트로 판정할 수 있기 때문이다. 독립된 모듈은 AI가 틀리지 않게 만드는 장치가 아니라 오류의 발생 범위와 검증 비용을 제한하는 장치다.

## 예시

(구성한 예) 주문 기능을 가격 계산, 주문 저장, 결제 실행, 화면 표시 모듈로 나눈다. 가격 계산 모듈은 `Cart`와 `DiscountPolicy`를 받아 `Money`를 반환하며, 정상 할인·중복 할인·최소 금액 경계 테스트를 단독으로 통과해야 한다. 할인 정책이 바뀌면 이 모듈과 테스트만 수정하고, 결제 업체의 응답 형식은 결제 모듈 밖으로 노출하지 않는다.

## 비예시

(구성한 예) 주문 기능을 여러 함수와 파일로 나눴지만 모두 같은 전역 상태와 결제 업체의 원본 응답을 직접 읽는다. 할인 정책이나 결제 업체가 바뀔 때 화면·저장·계산 코드를 함께 수정해야 하고, 각 부분을 따로 실행하거나 테스트할 수 없다. 파일은 작아졌지만 변경 경계는 생기지 않았다.

## 적용 범위·예외

지속적으로 변경되는 제품 코드와 여러 소비자가 공유하는 기능에 적용한다. 한 번 쓰고 버리는 짧은 스크립트나 항상 하나의 원자적 동작으로 함께 바뀌는 코드까지 억지로 분할하지 않는다. 모듈의 줄 수나 함수 수가 아니라 **내부 변경이 계약 밖으로 전파되는지**와 **독립 검증이 가능한지**로 경계를 판단한다.

## 확인 방법

- 모듈의 입력, 출력과 실패 조건을 소비자의 목적 언어로 설명할 수 있는가?
- 내부 구현이나 외부 응답 형식을 바꿔도 소비자 코드를 수정하지 않아도 되는가?
- 전체 시스템 없이 해당 모듈의 정상·경계·실패 동작을 테스트할 수 있는가?
- 한 요구사항 변경 때문에 서로 무관한 모듈을 함께 수정하고 있지는 않은가?
