### 모듈러 모놀리스 / 개발 단위 vs 배포 단위 / 폴더는 경계가 아니다 — 이걸 다루는 이론·개념이 있나

**한 줄**
있습니다 — "코드를 어떻게 나누나"와 "무엇을 한 덩어리로 배포하나"를 **서로 다른 구조**로 취급하는 게 아키텍처 이론의 기본이고, 폴더가 경계가 아닌 이유는 Parnas가 1972년에 "숨긴다는 건 못 들어온다는 뜻"이라고 정의해 둔 데서 나옵니다.

**쉽게 — 커튼, 잠긴 문, 그리고 건물**

집으로 바꿔 보면 한 번에 잡힙니다.

- **커튼으로 나눈 방** = 폴더(`src/billing/`, `src/search/`). 나뉘어 보이긴 합니다. 근데 아무나 걷고 지나갑니다. 지키는 건 예의뿐입니다.
- **잠긴 문이 달린 방** = package + `exports`. 열어 준 문으로만 들어옵니다. 나머지는 진짜로 못 들어옵니다.
- **건물** = 배포 단위. 방을 몇 개로 나눴든, 정전되면 **모든 방이 같이 어둡습니다.**

여기서 세 문장이 따라 나옵니다.

1. **방 나누기와 건물 세기는 다른 질문입니다.** 방 5개를 한 건물에 둘 수도 있고, 5개 건물에 하나씩 둘 수도 있습니다. 둘을 하나로 착각하는 게 가장 흔한 실수입니다.
2. **커튼은 방을 나눈 게 아닙니다.** → 폴더는 경계가 아닙니다.
3. **문을 잠가도 정전은 같이 당합니다.** → 패키지 경계는 고장 격리를 주지 않습니다.

**왜 그렇게 되는가 — 경계는 "막혔다"로만 증명됩니다**

Parnas의 기준은 "모듈은 무엇을 **숨기는가**로 정의된다"입니다. 그리고 숨겼다는 주장은 **다른 쪽이 손을 못 넣는다는 사실**로만 증명됩니다. 폴더는 아무도 막지 않으니 증명할 게 없고, 그래서 이론상 모듈이 아닙니다. `exports`나 import 검사가 하는 일은 그 "막혔다"를 실제로 만들어 주는 것뿐입니다.

**이름표만 모아 보면**

| 지금 얘기한 것 | 찾아볼 이름 |
|---|---|
| 방 나누기와 건물 세기를 따로 보기 | module structure vs allocation structure (SEI) · 4+1 view model |
| 한 건물 안에 잠긴 방 여러 개 | **modular monolith** (modulith, majestic monolith) |
| "이건 한 덩어리로 나간다"의 단위 | **architecture quantum** |
| 폴더는 경계가 아니다 | **information hiding** (Parnas, 1972) |
| 규칙을 검사로 강제하기 | **architectural fitness function** |
| 도메인은 바깥을 모른다 | **Dependency Rule** (Hexagonal · Onion · Clean) |
| 경계 없이 두면 생기는 일 | **architectural erosion** |

**가깝지만 아닌 것 — Bounded Context vs 배포 단위**

둘 다 "여기까지가 하나"를 말해서 붙여 읽기 쉽습니다. 다른 점은 딱 하나입니다. Bounded Context는 **말이 통하는 범위**(같은 용어가 같은 뜻인 영역)이고, 배포 단위는 **같이 나가는 범위**입니다. 그래서 Bounded Context 3개를 한 건물에 넣는 건 완전히 정상입니다.

**흔히 잘못 이해하는 지점 — "나눴으니 안전해졌다"**

패키지로 잘 쪼개고 나면 격리까지 얻은 것처럼 느껴집니다. 실제로 얻은 건 **바꾸기 쉬움** 하나입니다. 한 프로세스에 같이 살면 메모리·이벤트 루프·DB 커넥션을 공유하니, 하나가 무너지면 같이 무너집니다. 이 오해가 생기는 이유는 "경계"라는 한 단어가 빌드타임 경계와 런타임 경계를 같이 덮어 버리기 때문입니다. 가용성이 필요하면 건물을 나눠야 하고(프로세스 분리), 그건 값이 다른 선택입니다.

**확인 질문**
서비스를 전부 package로 쪼개고 경계 검사도 초록불인데, 한 서비스에 무한 루프 버그가 들어갔습니다. 나머지 서비스는 계속 응답할까요? 왜 그런지 한 줄로.

### (같은 질문의 상세 버전) 모듈러 모놀리스 / 개발 단위 vs 배포 단위 / 폴더는 경계가 아니다 — 이론·개념의 출처까지

네, 있습니다. 그것도 거의 한 문장 한 문장에 대응하는 이름이 있습니다. 정리하면 이렇습니다.

## 가장 정확한 앵커: 아키텍처 "구조"의 3분류

Bass·Clements·Kazman의 *Software Architecture in Practice*(SEI)가 아키텍처 구조를 셋으로 나눕니다.

| 분류 | 무엇을 말하는가 | 질문의 축 |
|---|---|---|
| **Module structures** | 코드를 정적으로 어떻게 쪼갰는가 (컴파일·개발 시점) | 개발 단위 |
| **Component-and-connector structures** | 런타임에 무엇이 무엇과 말하는가 | (프로세스 구조) |
| **Allocation structures** | 그것이 환경에 어떻게 배치되는가 (deployment, work assignment) | 배포 단위, 누가 고치나 |

"두 축이 섞였다"는 관찰이 바로 이겁니다 — **module structure와 allocation structure는 서로 다른 구조이고, 동형(isomorphic)일 필요가 없다.** 초보 설계에서 가장 흔한 실수가 이 둘을 하나로 붙여 버리는 것이고, 이 책은 애초에 "구조는 여러 개이며 하나의 그림으로 합칠 수 없다"에서 출발합니다.

같은 얘기의 더 유명한 버전이 Kruchten의 **4+1 view model**(1995)입니다. **Development view**(모듈·소스 조직)와 **Physical/Deployment view**(배포 토폴로지)가 별개의 뷰로 잡혀 있습니다. 뷰가 나뉘어 있다는 사실 자체가 "같을 필요 없다"는 주장입니다.

## 축 1 — 개발 단위 ≠ 배포 단위

- **Component = unit of deployment.** Robert C. Martin의 *Clean Architecture*가 component를 "배포 가능한 최소 단위"로 **정의**합니다. 소스 조직과 배포 단위를 어휘 수준에서 분리합니다.
- **Architecture quantum.** Richards·Ford(*Fundamentals of Software Architecture*, *Software Architecture: The Hard Parts*)의 용어로, "독립 배포 가능하고 기능적 응집도가 높으며 내부가 동기적으로 결합된 산출물"입니다. (a)는 양자 N개, (b)는 양자 1개입니다. 여기서 **static coupling**(부팅에 필요한 것)과 **dynamic coupling**(런타임 호출)을 구분하는데, 이 구분이 "package 경계는 빌드타임 개념"이라는 말의 정식 표현입니다.
- **Independent deployability.** Sam Newman은 마이크로서비스를 "독립적으로 배포 가능하며 비즈니스 도메인을 중심으로 모델링된 서비스"로 정의합니다. 정의가 곧 비용 청구서입니다 — **독립 배포성이 필요 없으면 값을 치를 이유가 없다.** 그래서 그도, Fowler(**MonolithFirst**, 2015)도 모듈러 모놀리스부터 시작하라고 씁니다.
- **Bounded Context**(Evans, DDD)는 **모델의 경계**이고 배포 단위가 아닙니다. `service-billing`/`service-search`는 bounded context이며, 함께 배포되는지는 **독립된 결정**입니다. DDD에서 가장 흔한 오독이 "bounded context = 서비스 = 컨테이너"입니다.

## 축 2 — 폴더는 경계가 아니다 (이론적으로 가장 단단한 부분)

**Parnas, "On the Criteria To Be Used in Decomposing Systems into Modules"(1972)** 가 정면으로 다룹니다. 핵심 주장은 모듈을 **정보 은닉**으로 정의한다는 것이고, 여기서 결정적인 대목은 은닉의 기준이 *의도*가 아니라 *접근 불가능성*이라는 점입니다. 다른 모듈이 손을 넣을 수 있으면 그건 숨겨진 게 아니고, 따라서 모듈 경계가 아닙니다.

`apps/api/src/billing/`은 이 기준을 통과하지 못합니다. 아무나 import할 수 있으니 숨긴 것이 없고, 그러면 Parnas 기준에서 **모듈이 아닙니다.**

파생 개념들:

- **REP (Reuse/Release Equivalence Principle)** — "재사용의 granule은 릴리스의 granule이다." 독립적으로 쓰일 단위라면 공개 표면과 식별자를 가진 릴리스 단위여야 한다는 뜻이고, 폴더는 그게 될 수 없습니다.
- **Logical separation vs enforced separation.** Simon Brown이 모듈러 모놀리스 강연에서 계속 두드리는 구분입니다. 그림에서만 나뉜 것과 컴파일러가 막아 주는 것은 다릅니다.
- **명시적 모듈 인터페이스**가 그 수단의 일반형입니다. Java 9 **JPMS**의 `module-info.java`(`exports`/`requires`), .NET 어셈블리의 `internal`, Rust crate의 `pub`, OSGi bundle — 전부 같은 설계입니다. `package.json`의 `exports` + 선언된 dependencies는 **JS 생태계의 같은 물건**입니다.
- 강제하지 않으면 무슨 일이 생기는지에도 이름이 있습니다 — **architectural erosion / drift**(Perry & Wolf, 1992). 설계된 아키텍처와 실제 코드가 갈라지는 현상이고, 강제 장치가 없는 경계의 기본 운명입니다.

## (b) 형태의 이름

**Modular monolith**입니다. 별칭으로 **modulith**(Oliver Drotbohm, Spring Modulith 프로젝트), **majestic monolith**(DHH, 2016). Spring Modulith는 정확히 같은 아이디어의 Java 구현체입니다 — 한 배포 단위 안에서 모듈 경계를 선언하고 **테스트로 검증**합니다.

## "검사로 강제한다"의 이름

**Architectural fitness function** — Ford·Parsons·Kua, *Building Evolutionary Architectures*(2017). 아키텍처 특성을 자동으로 지키는 객관적 검사를 말합니다. CI에서 도는 `turbo boundaries`는 교과서적인 fitness function입니다. 같은 계열 도구로 **ArchUnit**(Java), **dependency-cruiser**·**eslint-plugin-boundaries**(JS), **NetArchTest**(.NET)가 있습니다.

## tag 규칙("domain은 app을 모른다")의 이름

**Dependency Rule** — 의존은 항상 안쪽으로. **DIP**(의존 역전), **Hexagonal/Ports & Adapters**(Cockburn, 2005), **Onion**(Palermo, 2008), **Clean Architecture**가 모두 같은 규칙의 변형입니다. 컴포넌트 수준으로 올리면 **ADP**(순환 금지), **SDP**(안정된 쪽으로 의존), **SAP**(안정된 것은 추상적이어야)입니다.

## 이론이 덧붙여 주는 것 세 개

**1. monorepo는 고전 이론이 묶어 둔 것을 풀어 놨습니다.** REP는 "경계 = 릴리스 단위"라고 말하는데, `workspace:*` 내부 패키지는 **독립 릴리스 없이 경계만** 가집니다. 고전 component 이론은 경계·버전·릴리스 주기를 한 덩어리로 봤고, monorepo는 거기서 **강제되는 경계**만 떼어 왔습니다. 그래서 "패키지로 나누면 버전 관리가 늘어난다"는 반사적 걱정은 monorepo에선 적용되지 않습니다.

**2. 모듈 경계는 실패 경계가 아닙니다.** (b)는 양자 1개, 즉 운명 공동체입니다. 한 서비스가 이벤트 루프를 막거나 메모리를 태우면 전부 같이 갑니다. 정적 결합은 끊었지만 동적 결합·자원 결합은 그대로입니다. (b)가 사는 것은 **변경 가능성**이고, **가용성**은 (a)에서만 팝니다.

**3. "개발 단위"에는 조직 축이 하나 더 붙어 있습니다.** Bass et al.의 allocation structure에 **work assignment**가 들어 있고, 이게 **Conway's Law**와 *Team Topologies*(Skelton·Pais)의 영역입니다. 실무에서 (a)를 고르는 진짜 이유는 기술이 아니라 팀이 나뉘어 있어서인 경우가 많습니다. **개인 프로젝트에서는 이 압력이 0이므로 (a)를 고를 이유가 하나 통째로 사라집니다.**

## 읽을 순서 추천

### 근데 그럼 한 아키텍처에 레이어가 세 개 있는건가? 개발 단위 / (프로세스 구조) / 배포 단위

**한 줄**
층(layer)이 아니라 **뷰(view)** 셋입니다 — 같은 시스템 하나를 다른 각도에서 찍은 사진이고, 위아래로 쌓인 게 아닙니다. 개수도 셋으로 고정된 게 아닙니다(SEI는 3개 **범주**, Kruchten은 5개 뷰).

**쉽게 — 집 도면 세 장**

같은 집 한 채를 두고 도면을 세 장 그립니다.

| 도면 | 무엇을 보나 | 이름 |
|---|---|---|
| **평면도** | 방이 어떻게 나뉘어 있나 | module structure (개발 단위) |
| **배관·전기 계통도** | 무엇이 무엇과 이어져 흐르나 | component-and-connector (런타임·프로세스) |
| **지적도·주소** | 이 집이 어느 필지·건물에 놓였나 | allocation (배포 단위) |

세 장은 층이 아닙니다. **집은 한 채고, 도면이 세 장**입니다. 그래서 "몇 층인가"가 아니라 "지금 **어느 도면**을 보고 있나"가 맞는 질문입니다.

**왜 층이 아닌가 — 매핑이 자유롭기 때문**

층이라면 아래가 위를 결정해야 합니다. 그런데 이 셋은 서로를 결정하지 않습니다. package 5개(평면도)를 프로세스 1개에 넣고 이미지 1개로 배포할 수도 있고, 같은 5개를 프로세스 5개·이미지 5개로 흩을 수도 있습니다. **그 매핑 자체가 설계 결정**이고, 자유도가 있다는 게 곧 층이 아니라는 증거입니다.

**가깝지만 아닌 것 — 레이어드 아키텍처**

헷갈리는 게 당연합니다. "레이어"는 이미 아키텍처에서 확고한 다른 뜻이 있으니까요 — presentation / domain / data 처럼 쌓는 **layered architecture**. 다른 점은 하나입니다: 그 레이어들은 **module structure 안에서** 코드를 나누는 한 가지 스타일입니다. 즉 레이어는 이 셋과 나란히 있는 게 아니라 **첫 번째 도면 안에 들어갑니다.** 우리가 쓰는 `domain`/`shared`/`app` 태그도 전부 첫 번째 도면 얘기입니다.

**우리 프로젝트로 확인**

- **평면도** — `@platform/web`·`api`·`core`·`contracts`·`tsconfig` 5개와 그 의존 방향. `turbo boundaries`가 검사하는 게 정확히 이 도면입니다.
- **계통도** — 지금은 node 프로세스 하나(Nest)와 브라우저 하나. 아직 서로 이어져 있지 않아서 화면에 "health 미확인"이 뜹니다.
- **지적도** — 아직 없습니다. M07에서 이미지 하나로 정해집니다.

### 축2 - 디렉토리는 경계가 아니라고 하는데, LLM 바이브 코딩에서는 디렉토리 자체도 경계로 나뉘어야 맥락 파악에 경계가 있어서 구분이 잘 되지 않아?

**한 줄**
디렉토리는 **신호**(signal)이고 package는 **신호 + 강제**입니다. 원래 주장은 "디렉토리를 나누지 말라"가 아니라 "디렉토리만으로는 경계라고 부를 수 없다"였고, LLM 코딩에서는 신호가 더 중요해지므로 **그 신호가 거짓이 되지 않게 지키는 장치**도 같이 더 중요해집니다.

**두 개념을 떼어 놓기**

| | 디렉토리만 | package (디렉토리 + manifest + 검사) |
|---|---|---|
| 읽는 쪽에 구조를 알려주나 | **예** ← 당신이 말한 이득 |  예 |
| 넘어가면 막히나 | 아니오 | 예 |
| 시간이 지나도 사실로 남나 | **아니오** | 예 |

세 번째 줄이 핵심입니다. 강제가 없는 신호는 **썩습니다.** 6개월 뒤 `src/billing/`이 `src/search/internal/`을 세 군데서 import하고 있으면, 그 디렉토리 구조는 이제 **거짓말하는 라벨**입니다. 그리고 LLM은 그 거짓 라벨을 그대로 믿고 다음 코드를 씁니다 — 사람보다 더 순진하게요. 이 현상의 이름이 architectural erosion이고, 강제 장치의 존재 이유가 정확히 그겁니다.

**LLM 코딩에서 package가 오히려 더 유리한 이유 셋**

**1. 프롬프트 예산이 0이 됩니다.** 폴더로만 나누면 규칙이 `CLAUDE.md`/`AGENTS.md`에 텍스트로 살아야 합니다 — "billing에서 search 내부를 import하지 마라". 이건 매 세션 토큰을 먹고, 컨텍스트가 길어지면 잊히고, 어겨도 아무 일이 안 일어납니다. package 경계는 도구가 강제하니 프롬프트에 한 글자도 안 씁니다. **LLM은 지침을 잊지만 실패하는 명령은 못 무시합니다.**

**2. `exports`가 곧 LLM용 요약 인터페이스입니다.** 우리 프로젝트로 보면, `@platform/core`를 쓰려는 코드는 public surface가 **함수 하나 + 타입 하나**뿐이라는 걸 `dist/index.d.ts` 두 줄로 압니다. 폴더였다면 "여기서 뭘 부를 수 있나"를 알려면 `src/` 전체를 훑어야 합니다. `package.json`의 dependencies도 같은 일을 합니다 — **"이 코드가 볼 수 있는 세계"의 확정된 목록**이라, LLM이 탐색 범위를 추측하지 않습니다. 컨텍스트 절약은 부수 효과고 본질은 **추측 제거**입니다.

**3. 틀린 편집이 즉시 되돌아옵니다.** LLM이 경계를 넘는 import를 쓰면 `typecheck`/`turbo boundaries`가 그 자리에서 틀렸다고 말합니다. 자율적으로 도는 에이전트에게 이건 리뷰어보다 값싼 교정 루프입니다. 게다가 package 단위라 `--affected`로 검증 범위도 좁아집니다.

**당신 관찰이 옳은 부분에도 이름이 있습니다**
